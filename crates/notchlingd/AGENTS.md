# notchlingd: notes for agents

## Why the code is this way

The code carries no comments (see [AGENTS.md](../../AGENTS.md)). What a change could break without knowing it, by file:

- `src/codex_children.rs`: Owns the Codex child index (`daemon/codex-children.db`): a 30-day backfill in the background at the first start, `platform::watch` batches after that, and a sweep of the rows of files that are gone; `codex.children` answers from it and is `APP_QUIET` (the Details Panel asks every few seconds).
- `src/every_session.rs`: The phone's list leaves out Codex children (`is_child`) and the rows of delegated jobs (`delegate_jobs::hidden`), as Chat's Sidebar does.
- `src/accounts_late.rs`: Accounts ops that can outlast the client's 5 s call answer `{state: "working", ticket, op}`; the result is kept for `accounts.result` and also sent as `accounts.done`, so a reconnected client never loses it.
- `src/accounts_late_tests.rs::config write failure`: If the live Keychain write lands and then `~/.claude.json` fails, the switch must put the Keychain item back; a switch is never left half done.
- `src/accounts_signin.rs`: One browser sign-in at a time on a 127.0.0.1 listener; it stops at once when cancelled or `accounts` goes off, and the code is exchanged and the login saved only while the switch is on.
- `src/accounts_ops_log_tests.rs`: Every way the daemon changes or notices Claude Code's login must leave an `account.switched` event (and `account.login`, `lane.changed` for the rest), since cost goes to the account active at a message's time: `accounts.switch`, `accounts.list` with `sync`, the limits auto-switch (`ClaudeLimits::switch_for_limit`, with the limit window and percent) and Move All's main-login switch. `account_history.rs::DbSwitches` reads the `account.switched` rows back from `events.db` for `cost::account_log::merge`, so a new path that sets the login without `ClaudeAccounts::switch_for` or `sync` needs a test here. Engine code that runs on a worker thread (`slow()`) carries the op scope into the thread, or its events lose their `op_id` and actor.
- `src/acting_ops_tests.rs::interrupt`: A stop sends one Esc only if the session still works a moment later: a second Esc on an idle prompt opens rewind.
- `src/acting_ops_tests.rs::FakePty`: The fake terminal is the engine's `FakePrompt` over the test's screen, so a reply in a test is ok only when the fake prompt took the message; `Setup::deaf` makes its Enter do nothing. `session.reply` answers `{"sent": true}` only after the session's input box let go of the text: every other end is an error (`failed`, with what happened), which the app shows while it puts the text back in the reply box.
- `src/reply_attempts.rs`: The last five texts a reply tried to put in each session's input box without the box being seen to let go of them (12 hours, 64 sessions, in memory), kept by job row id. `acting_ops.rs::play_inner` hands them to the executor as `Clearing::earlier` for any reply plan (a held flush too), notes a text after every failure but `NotCleared` and a pty error, and forgets the session's list after a send that went through, since the clear keys have emptied the box by then. `session.reply {clear_box: true}` is `Clearing::any`; it reaches `play_inner` only through `reply_or_hold` (a reply that is held waits for the turn as before). A reply refused as `not_cleared` carries `data {why, box?}` on the error (`box` cut at `BOX_SHOWN_MAX`), never in a file or log.
- `src/reply_screen.rs`: A reply that fails for anything but a pty error leaves `<data>/reply-screen.txt` (0600, one file, written over by the next failure; `acting_ops.rs::keep_screen` writes it and `permission-screen.txt`): the job, the failure, the message's length, the cursor, the engine's trail of what each wait saw, and the last screen with the input box's text masked. Never the message's text (a menu it opened above the box can show), and never more than that one screen. A reply that goes in keeps none. `Setup::starting` makes the fake attach show Claude Code's wait for a session that is starting first.
- `src/acting_permission_tests.rs`: The permission dialog reader was written from made-up screens (no real recording exists); a screen it refuses is kept, private, so a real one can become the fixture (`docs/recording.md`).
- `src/activity_ops.rs`: `activity.list` is app tier, read only and `OpSpec::APP_QUIET`: it reads `daemon/events.db` through `notchling_engine::activity` and answers rows with the old fields (`kind`, `op`, `who`, `result`, `detail`) and the new ones (`event`, `group`, `title`, `outcome`, `refs`, `seq`, `audit_n`). A row's fields come from the event's own fields by allow-list (`activity/reply.rs`): a new field reaches a screen only by being added there on purpose, and none holds text. The first start imports the old files once (`import_once`) into legacy rows.
- `src/agy_ops_limits_tests.rs::session/new`: After `session/new` is answered acting may go off as the reply is made; the first message must not reopen the session it would be sent to.
- `src/agy_phone.rs`, `src/every_session.rs::live`: The phone's Antigravity state and chat (`Sources::foreign_live`) are read only and start nothing, so no switch is needed beyond the phone's own chat path. `AgyOps::phone_read` takes, in order: the session open and loaded in Notchling's own `agy acp` (its working flag and held conversation), a session another `agy` holds that the app already found (`Elsewhere::watched`, never a fresh `lsof` from the phone's path), else the session's own log (`brain/<id>/.system_generated/logs/transcript.jsonl`, the engine's `from_log_file`, a 4 MB tail) with the working flag from the summaries row's `RUNNING`, since a log that ends mid-turn may belong to a run that died. Every result is cut to the newest 512 KB (`CONVERSATION_BYTES`, as `agy.conversation`); the phone protocol has no `truncated` field, so the cut is silent there. A log is parsed again only when its size or time changes (`LogReads`, 64 kept). A list of several rows reads only rows from the last 6 hours (the rest keep the row's flag and an empty chat in the list); a single-row call, which is what opening a chat is, reads any age. Permission prompts of an `agy acp` session still do not reach the phone.
- `src/agy_sink.rs::options`: A session's model and thinking-level options go to the catalog before the change is announced, so a client that reacts to the event and then asks sees them.
- `src/awake_loop.rs`: The daemon holds the Mac's power assertion (decision 0004) but, as the Swift app did, only while an app is attached (`room.can_answer()`, an app-tier client of kind `App`): quitting Notchling lets go within one tick, even in Always On, and the next attach takes it again (a refusal reported before is reported again for the new run of the app). `pmset -g assertions` shows the process `notchling`, named "Notchling: keeping the Mac awake for running agents". Each change of the hold (taken, swapped between system and display, let go) is published as `awake.changed {holding}` on `settings` for the app's menu bar cup, and `awake.state` (`awake_ops.rs`, app tier, quiet) reads it; a refused hold announces nothing. It reads `mode` and `keepDisplayOn` from the store itself every 2 s (the app writes the store and never pushes them, unlike the limit modes), counts working sessions from the list `sessions.list` serves plus Notchling's own Codex turns and Antigravity sessions, and keeps what it holds when the store can't be read. Under a fixture root `power_for` gives a `FakePower`, so tests and dev runs never hold a real assertion. It is a Free setting (decision 0020): an agent's `settings.set mode` takes effect within one tick. A change of the setting is felt up to 2 s later, the Swift app's poll was about as slow.
- `src/wake_loop.rs`: Continue agents after sleep, the Swift `WakeResumer` run in the daemon. The Mac's wake comes from `platform::awake::PowerEvents` (only `HasPoweredOn` counts; none is started under a fixture root, `wakes_for`, so tests and dev runs never listen); every 2 s the loop notes a wake and, only while one is outstanding, the `continueAfterSleep` setting is on (read from the store each time, default on, a store it can't read means no nudge), `acting` is on and an app is attached, it reads the session list and asks `engine::control::WakeResumer` which jobs to nudge (20 s after the wake, within 30 minutes, background jobs whose last message is the sleep error, once per cut-off). The nudge types the prompt through `ActingOps::nudge`, the path a reply takes (`play`), one at a time, and a failure is logged with the job id and not retried for the same cut-off, as the Swift `try?`. Tests give it a fake wake source and, for the typing, `acting_ops_tests::setup`'s fake terminal: nothing here ever attaches to a real session. Differences from Swift: the daemon notes a wake whether or not it may act, so an app that attaches (and turns acting on) within the 30 minutes after a wake still resumes the cut-off jobs, where the Swift app, not running then, never saw that wake; a dark wake may count too (`HasPoweredOn` is sent for it); the tray has no Continue After the Mac Wakes item, only the Settings sheet's toggle.
- `src/bridge_backend.rs::pairing`: A pairing request is asked only of an app that follows the `bridge` topic; an app merely attached would not see it and the phone would wait out the whole time before being refused.
- `src/bridge_backend.rs::session.new`: The phone's `modelId` goes to `session.new` as given so the daemon's own catalog check applies again; the phone's family names (`opus`) map to the catalog's current id.
- `src/catalog_ops_tests.rs::fetch`: The live Claude model list is fetched with the main login's token only, never another saved account's expired slot (that would renew it); a refused token is not retried until it changes or a day passes, a 5xx holds off 15 minutes.
- `src/cli.rs::delegate`: `notchling delegate` takes everything after the subcommand as is, because the prompt may hold flags; the engine parses its own flags.
- `src/cluster_driver.rs`: One thread owns the `NodeCore`; links, local calls and hooks reach it through one channel, and whatever waits (a dial, a call from a node, a hook) runs on a thread of its own, so the driver never waits on I/O or holds a lock across it. A failed `cluster.db` save fails every waiting reply, records a `cluster.step` event (`save`), rebuilds the core from the last saved state and feeds `Linked` again for each open link. Replies go out only after the new status is stored and published, so a caller that reads `cluster.status` after its op sees the change. The node's tool versions are `VersionsOps`' last scan (read every minute), never a second hash of the binaries on the driver thread: hashing a large `claude` in a debug build held up the daemon's shutdown. `ClusterNode::close` waits at most 3 s for the thread.
- `src/cluster_cli.rs`: `notchling cluster join` takes the token from stdin only (`--token-stdin`); a token among the arguments is refused before anything connects, since arguments show in `ps` and shell history. Output goes through writers, not `println!`, so the file stays out of the one-writer lint's list.
- `src/cluster_join.rs`: A join on the home raises a fresh inbox id each time (`node-join:<node>:<ms>`). The responder and the 10-minute timer race through one flag, so exactly one of them acts: an answer applies `Approve` or `Deny`, the timer resolves the item Expired and denies the joiner, so a pending member never outlives its item. The joiner's name, OS and address come from an unapproved peer: control characters are dropped and the name is cut to 64.
- `src/inbox_ops.rs`: `InboxOps` persists through one `Store` (`notchling.db`, or `cluster.db` once the node is in a cluster). The writer thread owns the switch: `Hooks::in_cluster` (after a `Change::Cluster` is saved) and `load` at start queue a move behind earlier changes, so order holds and a failed move leaves the inbox where it was; `Hooks::wiped` moves the rows back to `notchling.db` before `cluster.db` is wiped, waiting at most 5 s; it returns false when the rows could not be moved back (or the wait ran out), and the driver then renames `cluster.db` and its side files to `cluster.db.inbox-left-<ms>` instead of deleting them. The store always ends on `notchling.db` after a leave. A failed move into the cluster is not retried until the daemon restarts; the inbox stays in `notchling.db` meanwhile. At start, readable cluster state moves the inbox in; a `cluster.db` with no state moves its inbox rows back to `notchling.db`; unreadable state with inbox rows in `cluster.db` keeps reading and writing them there. A row present in both databases keeps the one with the larger `updated_ms`.
- `src/cluster_node.rs::Hooks`: Each hook runs on its own thread and may block; `Submit::send` never waits, so a responder under the inbox lock can use it.
- `src/cluster_ops.rs::join`: The `cluster` switch is off at every start. `settings.set_switch` (app tier) turns it on, and so does `cluster.join` from the app, or from an agent only while no app is attached (a headless node that Machines joins over ssh). With an app attached an agent's join is refused with the off message: a joined node runs what its home sends. Every switch turned on by a join is a `switch.changed` event (cause `user` for the app, `cluster_join` for a headless join). An agent's join with no app attached is headless: the joiner says so and the home records the member `headless`, which is what lets it rejoin by itself after a restart (`cluster_wiring.rs::rejoin_on_start`). An app-tier join is never headless.
- `src/cluster_switches.rs`: Only `acting`, `bridge` and `install` follow the home (`policy::cluster_may_set`), and only while no app is attached; with an app the app owns its switches. A change goes through the same ops the app calls (as the app tier, `ClientKind::Node`), only when the value differs, and is recorded as a `switch.changed` event (cause `cluster_node`); the home is the `peer` of the `cluster.step` `call` event for `node.switch.set`. `node.switch.set` is answered here, before `Ops`, since it is a node-only op with no local API name.
- `src/cluster_wiring.rs::rejoin_on_start`: The one start-time exception to "off at every start" (decision 0007's note of 2026-11-14): a node whose loaded `cluster.db` says it is an active, headless, non-client member, with another active member as home (`ClusterState::rejoin_home`, read once in `Driver::new` before the thread runs), turns `cluster` on at daemon start if no app is attached, recorded as a `switch.changed` event (cause `cluster_rejoin`) and a `cluster.step` event (`rejoined`, the home as `peer`). The role is the home's record, replicated in `Members`; an agent that rewrites the local copy gains only a dial to the pinned home, and a rewritten home certificate or address fails the pin. Nothing else turns on here: `acting`, `bridge` and `install` still wait for the home's `Members`/`HelloOk` (`cluster_switches.rs`), and only while no app is attached. Call it after `follow_switch`, or the driver never hears the switch.
- `src/cluster_wiring.rs::DaemonCalls`: A call from another node runs through the same `Ops` the socket serves, with the socket's checks again (unknown op, app tier, approval needs an attached app), as `ClientKind::Node`, and at the app tier only for an App origin the core's policy allowed. `Ops` is held weakly. `NOTCHLING_CLUSTER_LOOPBACK=1` binds 127.0.0.1 instead of the Tailscale addresses, and only in a daemon run from a cargo target folder; under a fixture root without it nothing listens or dials.
- `src/cluster_forward.rs`: `Ops::call` asks `Forward` first. An op whose policy rule has an `id_field` holding `<node id>/<id>` of another node goes to that node with the bare id, as the app tier with this node as the origin; everything else stays local. Only an app-tier caller forwards (an agent gets `forbidden` here, no round trip), and a call that itself came from a node (`ClientKind::Node`) never forwards again, so a hostile peer can't make this node relay a call to a third one. An unknown or offline node is an error, never a local fallback. The receiver's `check` decides what a Worker may do; a Worker that forwards is refused there and audited (`cluster.refused`). `PromptFollowers` is the lease behind `Room::can_answer_prompts`: a client node that sent `node.follow {topic: "prompts"}` within 60 s makes `hook.request` on a node with no app wait for an answer instead of passing at once. Only `hook.request` asks `can_answer_prompts`; `can_answer` still means an app is attached, because the headless switches, the join and the approval checks rely on that.
- `src/cluster_sessions.rs`: Only a client node (its own member record has `client: true`, read at use time) pulls remote rows; a Worker sends no `node.sessions` and its lists never carry another node's sessions, so agents on a Worker can't see the maintainer's. Remote rows are each linked member's `node.sessions` (the owner's own `sessions.list {tools: all}`, which never carries remote rows for a `ClientKind::Node` caller, so lists can't loop). They are asked when a node comes online, when its `sessions.changed` event arrives (`Msg::Event`, which the core stamps with the real sender in `data.from`, whatever the sender wrote) and when 30 s old; a failed ask keeps the last rows and retries in 5 s. A row must deserialize as `engine::sessions::Agent`; it is re-serialized (unknown fields dropped) and keeps its `tool`. `sessions.list` and `sessions.changed` carry only rows whose tool is `claude` or missing, unless the caller asked `tools: "all"`. `sessions.changed` goes out through one `Publisher`, which reads the local list when its turn comes and skips a list it already sent. A row is qualified (`<node>/<id>`), carries `host` = the node id and `node {id, name, online}`; an offline node keeps its rows with `online: false`, a node that left the member list loses them. `transcriptPath` is the mirror file once it exists and null before, never the owner's path. `node.tail` reads only a transcript named by a row of this node's own list (the path never comes from the caller), at most 512 KB a call; `reset` means the file is shorter than `from` or is another file (`gen`, device and inode); a replaced longer file is only noticed when the caller passes the `gen` it saw. `node.sessions`, `node.tail` and `node.follow` are answered in `SessionCalls` before `Ops`, since they have no local API name (like `node.switch.set`); a peer's `sessions.changed` event is consumed by the driver and never republished to the local room.
- `src/cluster_main.rs`: Every 2 s the primary reads its own session list (`HandlerRows::complete_rows`, Node client, so no remote rows) and sends it to the core as `LocalCmd::MainSeen`; a list that can't be read, or that the daemon marks `partial` (the Claude monitor hasn't landed yet), sends nothing, so a monitor that isn't ready never makes every session look ended. `Originators` reads only the first line of a Codex rollout (at most 64 KB, a line without a newline yet is unknown) and keeps the answer per path; the ids whose `session_meta.payload.originator` is `codex_exec` go to the core as `codex_exec`, and an unreadable rollout is not main. `cluster.main.set {id, main}` (app tier) goes to the primary like `cluster.member.set`; `cluster.status` carries `main` (ids) and `kept`.
- `src/cluster_mirror.rs`: `cluster.follow {id}` (app tier) leases a mirror of one remote session for 10 minutes (at most 16 at once); the mirror thread pulls `node.tail` every 2 s and when the owner announces a change, appending to `<cluster dir>/mirror/<node id>/<name>` (0600, folder 0700, `O_NOFOLLOW`). `<cluster dir>`, `mirror` and `<node id>` must each be a real directory, checked with `symlink_metadata` before every write, and before every read of the file (the length a pull starts from, the `transcriptPath` shown); a link at any of them (or a link or folder in place of the file) refuses the write and the row's `transcriptPath` stays null. `<name>` is the first 16 hex characters of the sha256 of the qualified id plus the owner's file extension (when it is up to 8 letters or numbers), so nothing the owner sent picks it. A file never passes 256 MiB: the pull that would pass it stops that follow, logs once and deletes or truncates nothing. The last `gen` per file outlives a lapsed follow, so a follow that starts again resumes by appending from the file's length (and a replaced file is still noticed): transcripts only grow, and a shorter or replaced file is a `reset` that rewrites it. A node that is wiped (removed from its cluster) stops the follows first (a pull under way writes nothing after that), then deletes the mirror folder with the rest of its cluster state. A peer's event on a topic other than `sessions` is dropped in the core.
- `src/cluster_dispatch.rs`: `cluster.dispatch` (agent tier; only a delegate spec is allowed below the app) and `shell.stop` (app tier, accepts this node's qualified id) are `OpGroup` ops. `shell.run` and `delegate.run` are node-only: `DispatchCalls` answers them (and a forwarded `shell.stop`) before `SessionCalls`, so no local API name exists and the socket can't reach them. Job ids and key dedupe come only from the core (ruling R8): this file builds the `JobSpec` from the caller's arguments (`build`) and sends `LocalCmd::Dispatch`. Codex and secrets are refused here and again in the core's peer path (R7), since a spec can arrive by either door. A delegate waits up to `DELEGATE_WAIT` (36 min plus slack), a start `LOCAL_WAIT` plus one more `CALL_MS` (a client's call goes through the home).
- `src/cluster_dispatch_delegate.rs`: `delegate.run` runs the engine's own `delegate::command::run` on this node (`RealDelegate`: this node's folders and PATH, depth 1 so the job can't delegate again, no recorder) and returns `{exit, out, err}`, each output cut at 256 KB. It runs only when this node's own member record has `acceptsDelegation`, and `check` refuses `--write`, `--out`, `--prompt-file` (they would read or write this machine's files for a remote caller), Codex, a missing `--folder` and a timeout over 2100 s (under the 36-minute call). `notchling delegate --machine <node>` (`run_remote`) parses and checks the arguments on the caller's machine, resolves the node by name or id, sends one `cluster.dispatch` with a random key, prints the cluster's warning to stderr first, then the job's output, and exits with the command's code (2 for a bad command or unknown node, 1 for a refusal).
- `src/shell_jobs.rs`: A shell job is `/bin/sh -c <command>` in its own process group (`process_group(0)`), `NOTCHLING_*` and `CLAUDE_CODE_*` removed from its environment (`shell_plan.env_remove`), stdout and stderr to one log, 0600 and created with `create_new` and `O_NOFOLLOW` under `<data>/cluster/jobs/`, whose two folders are checked as real directories (not links) before each open. Stop sends SIGTERM to the group, then SIGKILL after 2 s through a timer thread woken by a `Condvar` when the watcher reaps the child, so every child is waited for and nothing polls. A job's id is its job name from the core, so a second `shell.run` for the same job answers the first and starts nothing. Jobs are not persisted: a restarted Worker has no record of them, and the home keeps them `running` (nothing marks a job `lost` yet). The list is capped at 50 (finished ones are dropped first); the log files are never pruned. The state change reaches the home as a `jobs` event `job.state` through `NodeReporter` (`tell` to the peers, plus `LocalCmd::JobEvent` for the case where this node is the home), only for done, failed or interrupted.
- `src/cluster_blobs.rs`: `node.put {transfer, offset, data}` and `node.put.end {transfer, sha256}` write `<cluster dir>/incoming/<transfer>.part` (0600, `create_new`, `O_NOFOLLOW`) through an `Incoming` and rename it to `<transfer>` only when the hash matches. `<cluster dir>` and `incoming` are checked with `symlink_metadata` before every use (a link or a file in their place refuses the write), a link planted at the part's name is removed, not followed, and a finished file that is a link is never served. At most 8 files arrive at once; a file starts at offset 0 (a second offset 0 restarts it), parts and finished files older than an hour are deleted whenever a new transfer starts, and a node that is wiped removes `incoming` and `outgoing`. Only the Notchling app (or the home) may send these ops (`policy::RULES`): a Worker never sends one to another node.
- `src/snap_send.rs`, `src/snap_recv.rs`: the primary's `SnapSender` takes `offer(manifest, staged_dir)` (Task 7's entry point after `stage_set`) and `tick()` (a target back online, or a failed send past `RETRY`, gets the newest set). A target is a member that is active, online, Can Be Master and passes the `ready` predicate, and only when this node is the primary (`facts`), so after a handover the new primary sends to the others. One slot per target: one set in flight, the newest queued set replaces an older queued one, never the one in flight. Each target is sent from its own acknowledged lengths (`for_target` re-slices and re-hashes a Tail, and refuses one that is behind the staged `from`; the offer's reply carries the Standby's real lengths and one re-offer follows if they differ from the book). Parts go over `node.put` chunks (a folder part as one transfer per file), then `snap.part`, then `snap.commit`; the Standby answers `snap.offer` with the parts it still lacks, so a cut resumes. `snap.*` ops use the long call deadline like `workspace.*`. `SnapNode` is the Standby side plus the primary's `snap.ack` handler: it refuses a sender that isn't the primary, a primary or a non-Can-Be-Master receiver, and an ack from anything but a Can Be Master standby. The `ready` predicate is `snap_ready::predicate`: it reads `cluster.status`, runs the engine's `ready_in` on each member's reported `Versions.host` and the size of the newest set (`snap_ready::LastSet`: on the primary `SnapSender::last_set_bytes`, the newest offer or else the largest total of acknowledged transcript lengths; on a Standby the sum of part lengths of its own current set for that primary in its `StandbyStore`, so a Standby doesn't call itself ready on the 5 GB floor alone), and unknown facts are not ready, so nothing is sent without the disk-encryption check.
- `src/snap_observe.rs`, `src/snap_run.rs`: every 2 s the primary builds `Observed` from its session list and the `main` ids in `cluster.status` (a session that needs input counts as Working, one missing from the list as Ended), reads each main session's repository lock and transcript mtime, and sends it as `Input::Observed`; it also calls `SnapSender::tick`. A repository lock means a `*.lock` file directly in the repository's own folder or its common folder (`index.lock`, `HEAD.lock`, `config.lock`, `shallow.lock`) or anywhere under `<common>/refs` (up to 4000 entries, 8 deep), found with read-only directory listings and no child process; a linked worktree reads its own folder and its `commondir`. `Effect::Snapshot` reaches `Hooks::snapshot`, which only stores the newest ask for the `snap-stage` thread (never the driver thread): it reads repository state through the launcher (an `Err` is an absent key, so that session is No), runs `plan_set` with the smallest acknowledged lengths of the ready targets, `stage_set` into `<data>/cluster/outgoing`, `SnapSender::offer`, then prunes every set folder the sender no longer needs (the latest, one in flight or queued stay). A Busy stage is retried 3 times 2 s apart, then reported in `last_error`; the next trigger tries again. A set is planned and staged for every ready Can Be Master member, online or not (`SnapSender::ready_targets`), with tails from the smallest acknowledged length among them (a missing ack counts as 0), and always offered, so `tick` sends it when a target returns and no tail is planned past an offline target's ack. Nothing is staged only when no member is ready. The core's answer to `LocalCmd::Snapshot` is `{asked: seq}`, a request and not a staged set; `SnapRunner::outcome(seq)` says Staged(set), NoReadyTarget, Superseded (also for an ask replaced while still pending) or Failed, which Task 9's Final must read; `None` means the ask was dropped or evicted (only the last 16 are kept). A tail from 0 is whole only for a target that has nothing; `for_target` re-slices it for a target that has bytes, unless the part is marked `rewritten` (the file was replaced, so every target gets the whole file). Each ask re-copies the tails an offline ready target is missing on the stage thread, with no time bound while that target stays offline and ready.
- `src/snap_restore.rs`, `snap_restore_fs.rs`: `restore(&Request)` is the entry Task 9 and plan E call on the machine that takes over: it reads `StandbyStore::current()` for the primary, plans, and runs the steps in order, stopping at the first failure (earlier steps stay done; a second call plans again and skips what is already there). It needs two launchers: `read` for the probe (the sandboxed one, as `snap_run`) and `git` for clone, fetch and merge (a plain one like the workspace's: the sandbox denies the exec of `git-upload-pack` and `ssh`). Every write goes through `snap_restore_fs`: components below home may be links only if they resolve inside home, the final file is never a link, files are written to a `.nlrestore` temp then renamed (0600, folders 0700), and a stored file is hashed against the manifest before it is used. `DbHooks::close` is called after the new database is built and checked and before the rename, `reopen` after; the caller owns the connection. `devices.json` is merged under the bridge's own `FileLock`, by device id, and an unreadable local file is never written over. The driver's `reprobe` only clones the stored value (`None` until the first read, which counts as not ready), so a hung `fdesetup`, `lsblk` or `statvfs` on a network home never reaches the driver thread; the thread stops when the watch is dropped. `cluster.status` carries `ready {ok, reason, checks[]}` on every active Can Be Master member (added in `ClusterOps::status`, not in the core, because the space check needs the newest set's size); `reason` is the first failing check for the cluster view's "Not ready: ...". `SnapObserver` runs a `ReadyWatch` each tick: on the primary, a member that wasn't ready and now is gets `LocalCmd::Snapshot { trigger: Trigger::Ready(node) }` once (an edge, not every tick; a refused ask is tried again; a machine that isn't the primary forgets, so a new primary asks for every ready member at once) and then `SnapSender::tick`. `cluster.changed` events carry the status without `ready`; read `cluster.status` for it.
