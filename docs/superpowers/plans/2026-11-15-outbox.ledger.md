## Rulings

**R1** (2026-11-15, orchestrator). A new persisted state `in_queue` (`State::InQueue`; the wire and database word is `in_queue`). Its bubble says "Queued in the session", it has no buttons, and it is not a "needs you" state for the notch. It has no `why`.

**R2** (2026-11-15, orchestrator). Two counts. `count_since(path, message, since_ms) -> Option<Seen>` with `pub struct Seen { pub enqueued: usize, pub taken: usize }`. `enqueued` counts `queue-operation` `enqueue` lines naming the message. `taken` counts typed user lines (`typed_prompt` rules, `<bash-input>` included), `queued_command` attachments naming it, and for a command its `local_command` system line or older `<command-name>` user line. A `dequeue` line carries no text, so it counts only through the user line that follows it. A `popAll` or `remove` line is never a take (spec §15 already refused a `popAll` line as a delivery; `crates/AGENTS.md`: `popAll` is Up pulling the queue back into the box, so the text left the queue without the model reading it). Ruling: the maintainer's brief listed "dequeue/popAll naming it" as taken; `popAll` is treated as leaving the queue untaken, because that is what the Up key does, which is the safe side.

**R3** (2026-11-15, orchestrator). Baselines. The take stores both `seen_before` (the `taken` baseline) and a new column `queued_before INTEGER` (the `enqueued` baseline), both counted since `attempt_ms − 2 s`, through `OutboxStore::set_seen(id, seen: Seen)`. Spec §8 gets the column, and its row in the column table says what it is.

**R4** (2026-11-15, orchestrator). The verdict after Return (spec §10.6). During the 10 s watch and the 30 s look: `taken > seen_before` → Sent (the row is deleted); else `enqueued > queued_before` → `in_queue` (persisted at once; the row stays); else by 30 s → `unsure`/`not_found`. `Verdict { Sent, InQueue, Pending, Unsure }`. The 5 s safe-mode test is unchanged: a new enqueue or taken line within 5 s of Return.

**R5** (2026-11-15, orchestrator). An `in_queue` head blocks the session's later rows (it is the head; B3). The postman keeps watching it (on the tick, re-reading when the transcript's size changes): a new taken line → Sent (delete, `outbox.removed {why: "sent"}`, `session.outbox` `sent`). It goes to `unsure` with a new `Why::Dropped` (`dropped`) when Claude Code's queue no longer holds it and no taken line appeared within `VERIFY_LOOK_MS` (30 s) of first seeing that: `queue_state` no longer lists the entry (a `remove`, a `popAll`, the lost-queue rule after a Claude Code restart, a later `turn_duration` with no take), or the job is stopped, or gone, or its Claude Code process changed (pid or start time from the job files, if they record one; kept in memory only). A pure function in `verdict.rs`, such as `queued_verdict(seen: Option<Seen>, before: Seen, still_listed: bool, gone_since_ms: Option<i64>, now_ms: i64) -> QueuedVerdict { Sent, Stay, Unsure }`; the Task 5 implementer may refine the signature.

**R6** (2026-11-15, orchestrator). `outbox.edit` and `outbox.remove` on an `in_queue` row answer `failed("It's in the session's queue.")` (`Change::Busy`). `outbox.discard` and the 7-day notice's Discard remove it (an explicit action). The 7-day notice counts `in_queue` rows; its Send leaves them unchanged.

**R7** (2026-11-15, orchestrator). Daemon start (`OutboxOps::load`, spec §10.6, §7.4). A `sending` Claude Code row: taken grew → Sent; else enqueued grew → `in_queue`; else (or `None`) → `unsure`/`restart`. An `in_queue` row stays `in_queue` and its postman resumes watching it (R5). A Claude Code restart while the daemon was down is caught only by the queue read (the lost-queue rule) or the job's state, so spec §16 gets the risk: a Claude Code restart that writes nothing leaves the row `in_queue` until the job's process is seen to change while the daemon runs, or the 7-day notice.

**R8** (2026-11-15, orchestrator). Events: `OutboxThen` gains `InQueue` (`in_queue`). The `why` words of `outbox.removed` are unchanged.

**R9** (2026-11-15, orchestrator). `session.reply` (spec §11.3, B16): a row that reaches `in_queue` answers at once with today's queued shape, `{"sent": true, "state": "queued", "waiting": <position>, "outboxId"}`, and the row stays.

**R10** (2026-11-15, orchestrator). Chat (spec §14.1): an `in_queue` row's status line is "Queued in the session" (`chat-outbox-in-queue = Queued in the session`), with no buttons. Since Chat's own `Conversation::queued` also shows that entry from the transcript, Chat draws the Outbox row and hides one matching entry of `Conversation::queued` (the same squeezed text, the first match), so there is one bubble. The §14.1 sentence "an Outbox row that is Sent at its enqueue line becomes one of those" is replaced. `Status` gains `QueuedInSession`.

**R11** (2026-11-15, orchestrator). Codex and Antigravity are unchanged: Sent when the runner starts the turn.
