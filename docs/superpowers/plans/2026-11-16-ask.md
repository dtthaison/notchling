# Ask Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An agent runs `notchling ask "…"`; Notchling saves the question, shows a card naming the agent, its branch and how long it has waited in Chat, the notch and the Inbox (so also on the phone), and hands the person's answer straight back to the waiting command, across daemon restarts, without the main model relaying anything.

**Architecture:** A pure core in `engine::ask` (rows and their SQLite store, the shell-word and transcript matching that finds who asked, the answer rules, the Inbox item, the skill text). `notchlingd` serves additive `ask.*` ops and an app-tier `asks` topic from `AskOps`, finds the asker off the op thread from kernel facts and transcripts, raises one Inbox item per open question, and keeps waiting commands' long polls; `notchling ask`, `asks` and `answer` are thin clients that reconnect with the same id. The app draws cards from the topic; the phone uses the Inbox it already has.

**Tech Stack:** Rust (engine, notchlingd, local-api, events, platform `watch`, GPUI app), rusqlite, Fluent locale files, the protocol schema's generator.

**Spec:** `docs/superpowers/specs/2026-11-16-ask-design.md`. Every task's implementer reads the sections its task names. Section 7 is decided; "Builder's call" items are settled and not reopened. Items M1 to M7 under "Needs the maintainer" are built as recommended unless the ledger records the maintainer's other answer; Task 15's Antigravity allow waits for M3 and Task 20 for M6.

**Base and branch:** build on a branch `agent/ask` from the latest `origin/agent-run-oss` (at least 0a32aaca). Never commit to `agent-run-oss` or `main`.

## Global Constraints

- Packages: `notchling-engine`, `notchling-notchlingd`, `notchling-local-api`, `notchling-events`, `notchling-app`. One test filter per `cargo test` run.
- No comments in code, doc comments included (`python3 tools/strip_comments.py --check`); the why goes in the crate's `AGENTS.md`.
- Files under 1,000 lines (600 warns). Tests in `<module>_tests.rs` beside the module. `daemon_wiring.rs` (967 lines), `acting_ops.rs` (888) and `session_source.rs` (600) get at most a few lines each: new code goes in new files.
- Every new folder under `crates/*/src/` gets its `docs/feature-map.md` row in the task that makes it (`PYTHONPATH=tools/guard python3 -m guard featuremap`).
- The local API changes additively only: new names in a new block at the end of `wire.rs`'s `ops` and `topics`. The phone protocol gets no new field or op; only two schema descriptions gain words (Task 6).
- Never write question or answer text to the Audit, Activity, events, `notchlingd.log` or any log; counts only (`LINT-LOG-NO-TEXT`). The text lives in the `asks` row, on the app-tier `asks` topic, in `ask.wait`'s reply to the asking process, and (question only, cut) in the Inbox item.
- Tests never read `~/.claude`, `~/.codex`, `~/.gemini` or Keychain, and never run `claude`, `codex` or `agy`. Kernel facts come through `vault_caller::Processes` with a fake; transcripts from fixtures in temp folders (`testutil::Scratch`).
- Never hold a lock across I/O, a pipe or a socket call. The store's mutex covers one statement or one `BEGIN IMMEDIATE` transaction. An Inbox responder only takes the answer mark and queues the write.
- Values from the spec, all in `engine::ask::model`: `MAX_QUESTION_CHARS = 2_000`, `MIN_CHOICES = 2`, `MAX_CHOICES = 6`, `MAX_CHOICE_CHARS = 120`, `MAX_ANSWER_BYTES = 10 * 1024`, `MAX_OPEN_PER_SESSION = 20`, `MAX_OPEN = 100`, `KEEP_CLOSED_MS = 86_400_000`, `WAIT_MS_MAX = 50_000`, `FIND_MS = 10_000`, `FIND_WINDOW_MS = 600_000`, `FIND_MAX_FILES = 64`, `FIND_TAIL_BYTES = 256 * 1024`, `MAIN_FIND_MS = 5_000`, `TITLE_CHARS = 80`, `DETAIL_CHARS = 400`, `CHOICE_LABEL_CHARS = 60`, `WAIT_DEFAULT_S = 900`, `DEADLINE_MARGIN_MS = 60_000`, `DEADLINE_VARIABLE = "NOTCHLING_DELEGATE_DEADLINE_MS"`. Daemon: tick 1 s, sweep hourly. CLI: client timeout 60 s per `ask.wait`, reconnect after 1, 2, 5, 10 s then every 10 s, first open retried for 60 s. App: a closed card stays one line for 600,000 ms.
- Cutting text to N characters cuts on a `char` boundary, never a byte index.
- User-facing words short and plain, buttons in Title Case, in `locales/en/mac/*.ftl` (`python3 tools/locale/gen.py --check`).
- Never run `./build.sh --install`; only the maintainer installs and merges.

## Review Focus

1. The daemon restarts while a background `ask` waits, and you answer while the command is reconnecting: the same command prints your answer with the same id; nothing is asked twice. (Task 10 `load_keeps_open_and_answered_rows`, `answer_given_with_no_waiter_is_handed_over_next_wait`; Task 14 `restart_keeps_the_same_question`.)
2. An agent tries to answer a question meant for you, by every path: `notchling answer` from the asking subagent, from a sibling, from another session, on a question without `--main-may-answer`, on a main session's own question. Every one is refused with "Only the person answers this question." and the question stays open. (Task 6 `may_answer_*`; Task 13 `subagent_answer_is_refused`, `other_session_is_refused`, `main_cannot_answer_person_only`.)
3. You answer the same question on the Mac and the phone in the same instant: one answer wins, the asker gets that one, the Inbox shows it, and the other sees "Already answered · Phone". (Task 9 `first_answer_wins_under_race`; Task 11 `inbox_and_chat_race_one_wins`.)
4. Two subagents run the same `ask` command in the same second: no card ever names the wrong agent; background asks are told apart by their output files, blocking ones fall back to "This session or one of its subagents". (Task 5 `same_command_two_subagents_is_unknown`, `output_file_tells_identical_commands_apart`.)
5. The asking agent is stopped (its session stopped, the job removed, the machine restarted) while nothing is connected: the card says Stopped waiting and the Inbox item goes, and a pid reused by another process is not taken for the asker. (Task 10 `dead_asker_is_gone`, `reused_pid_is_gone`.)
