# The cluster

Nodes, the node tier, forwarding, dispatch, standbys and the handover. What to do when the laptop is gone is [cluster-failover.md](../cluster-failover.md).

Part of the Rust app's notes, moved from `crates/AGENTS.md`; the index is in the root `AGENTS.md`. Keep it true: change the note with the code, and add what bites you under Things that bit before.

- **Cluster** (`engine/src/cluster/`, `cluster-net/`, `notchlingd/src/cluster_*.rs`, `shell_jobs.rs`, `bridge_cluster.rs`, `app/src/cluster/`; decision XXXX cluster-v1-nodes, [the design](../superpowers/specs/2026-11-13-notchling-cluster-design.md), the ops in [docs/local-api-ops.md](../local-api-ops.md)). Machines join one cluster over Tailscale; a node is a daemon, the maintainer's own machines only. One primary (the home), Standbys and Workers; a client node is a Mac with the app.
  - The core. `engine::cluster` is pure: `NodeCore::step(Input) -> Vec<Effect>` does no I/O, `ClusterState` (members, jobs, term, home) changes only through `apply` and is journaled in `<data>/cluster/cluster.db`, and a seeded simulator (`cluster/sim/`) replays delays, duplicates, partitions, crashes and clock drift against invariants. Ids are the first 16 hex characters of the certificate's SHA-256; a session on another node is `<node>/<id>` (decision 0012).
  - The driver. `notchlingd` runs the core on one thread (`cluster_driver*.rs`); `cluster-net` carries its lines over TLS 1.3 pinned by fingerprint on both ends, Tailscale addresses only (`NOTCHLING_CLUSTER_LOOPBACK` is for cargo-target builds). The `cluster` switch is off at every start, except a headless member that rejoins (`cluster_wiring.rs::rejoin_on_start`). Joins need the maintainer's Allow in the Inbox and a one-time token.
  - The node tier. What one node may ask of another is the closed table `cluster::policy::RULES` (the sender's role, the origin's tier, `origin.node` equal to the sender), checked by the core and again by `Ops` with the socket's own checks. Control (members, dispatch) goes through the home; data (transcript tails, replies, prompts) goes straight to the owner. The ops with no local API name (`node.*`, `workspace.*`, `shell.run`, `delegate.run`) are daemon consts, listed in `docs/local-api-ops.md`.
  - Forwarding, rows, mirror. `cluster_forward.rs` sends an op whose id is `<node>/<id>` to that node (app tier only, never relayed twice, an unknown or offline node is an error). A client merges every member's `sessions.list` rows (`cluster_sessions.rs`) and mirrors the transcript Chat opens (`cluster_mirror.rs`, `cluster.follow`, files 0600 under `<data>/cluster/mirror/`). The phone reaches the same through the daemon (`bridge_cluster.rs`).
  - Remote prompts. A client with an app asks each owner for `node.follow {topic: "prompts"}` (a 60 s lease) and republishes the owner's prompts with qualified ids (`cluster_prompts*.rs`); `canAlwaysAllow` is false and an owner refuses "always" from a node.
  - Dispatch, shell jobs, code. `cluster.dispatch` (home only; Codex and secrets refused in v1) starts Claude Code, Antigravity, a shell job (`shell_jobs.rs`) or a delegate on a node; `code: "send"` sends the repository by git (`cluster_workspace*.rs`, `cluster_blobs.rs`) and `cluster.return` fetches the commits back into a branch, never merging. An app's dispatch (not a delegate) and `shell.stop` need this Mac's acting switch; `cluster.return` and `cluster.follow` only copy into this Mac and don't.
  - Standbys and the handover (plan D, decision XXXX cluster-standby-and-handover). The primary sends its main sessions to every ready Can Be Master member as sets at each turn end (`engine/src/cluster/snapshot/`, `standby_store.rs`, `notchlingd/src/snap_*.rs`; readiness in `cluster/ready.rs`). Code never travels in a set: only a session whose repository is clean and pushed may move, and the machine that takes it fetches from `origin`. Move to <machine> Now is the saga in `cluster/move_home.rs`, run by `notchlingd/src/cluster_move*.rs` and gated off by `RESUME_PROOF_RECORDED` until the maintainer's proof. A Standby's bridge relays the phone's commands to the primary or holds them (`bridge/relay.rs`, `cluster/held.rs`, `notchlingd/src/cluster_relay*.rs`), and the phone falls back to it pinned (`apps/flutter/lib/core/net/bridge_client.dart`).
  - The app. `app/src/cluster/` is the cluster sheet (with the replication lines and the Move sheet), `chat/remote*.rs` the remote rows and `sheets/run_on.rs` Run On in New Session; Machines adds a machine as a node (`engine/src/machines/steps_node*.rs`) and checks a Can Be Master one (`steps_master.rs`).
  - Add Machine over SSH (decision XXXX ssh-join, [the design](../superpowers/specs/2026-11-16-ssh-join-design.md)). The Cluster sheet's Add Machine takes `user@host`, checks it over ssh, saves the machine once it is reachable and supported, and shows one plan: Worker user, Stays Awake, Git, Tailscale (on Linux, Install and Sign In are two optional Fixes; the sign-in link is shown once and scrubbed from the log), Notchling installed (the binary from this Mac's cluster dist folder, which `tools/build-node.sh` fills for Linux and Intel Macs, checked by its hash; a same-arch Mac gets this Mac's own daemon), Notchling service, Reaches the Primary (`notchling cluster reach` on the new machine) and Joined. The shipped app runs these Fixes over ssh, each with its commands shown first; the admin password, when a step needs it, is asked once and never stored. A Mac runs the headless daemon as a LaunchDaemon as the node user (`/Library/LaunchDaemons/dev.notchling.node.plist`, no app, so it stays online with nobody logged in); a Linux machine runs a user service with linger on. Join Cluster on a machine already in Machines (an sd worker such as m1 or vps-sing-1) checks and plans only the node steps and never touches the worker's steps, files or service (`steps_node::is_sd_join_step`); a node-only machine also has its own Tool Versions and Self-Update Off steps. Added machines run the daemon only: Can Be Master is on only for a Mac with FileVault on and the same user and home as the primary, and Acting is on by default as a visible choice in the sheet.
  - The invite. The join step asks this Mac's daemon for `cluster.invite {node, name, canBeMaster, acting}` (a non-primary Mac forwards it to the primary) and sends the token to the new machine on the stdin of one ssh call. The token is bound to that machine's node id (read from the machine's own daemon first), lives 10 minutes and works once; the primary admits the machine with no Add click and raises a notice. The primary's `cluster.status` lists open invites without the token. Join tokens and invites never reach the CLI, an agent or a terminal on either machine (lane E's rule).
  - Update N Machines. When this Mac's build id (`NOTCHLING_BUILD`, in `Versions.build`) differs from a member's, the Cluster sheet and the Machines window offer Update N Machines (`engine/src/machines/node_updates.rs`, `engine_update.rs`, `app/src/cluster/updates*.rs`). It runs each machine's Notchling Fix one at a time over ssh and stops at the first failure; a machine with a shell job running or a move under way is Busy and updates only with Update Anyway, and a Linux or Intel Mac build missing from the dist folder says to run `tools/build-node.sh` first. A Mac's update needs its admin password (it restarts a system service), asked once per Mac.
  - Taking a machine out. Remove it in the Cluster sheet first. Then on a Mac: `sudo launchctl bootout system/dev.notchling.node; sudo rm /Library/LaunchDaemons/dev.notchling.node.plist; rm -rf ~/.local/share/notchling/Notchling.app ~/.local/bin/notchling`. On Linux: `systemctl --user disable --now notchlingd.service; rm ~/.config/systemd/user/notchlingd.service ~/.local/bin/notchling`. Notchling adds no uninstall step; the data folder (`~/Library/Application Support/Notchling` or `~/.local/share/notchling`) and the machine's cluster identity stay until you delete them.
  - What crosses machines is in [docs/policies/privacy.md](../policies/privacy.md). Each crate's `AGENTS.md` has what a change could break, by file.
