# notchlingd: notes for agents

## Why the code is this way

The code carries no comments (see [AGENTS.md](../../AGENTS.md)). What a change could break without knowing it, by file:

- `src/codex_children.rs`: Owns the Codex child index (`daemon/codex-children.db`): a 30-day backfill in the background at the first start, `platform::watch` batches after that, and a sweep of the rows of files that are gone; `codex.children` answers from it and is `APP_QUIET` (the Details Panel asks every few seconds).
- `src/every_session.rs`: The phone's list leaves out Codex children (`is_child`) and the rows of delegated jobs (`delegate_jobs::hidden`), as Chat's Sidebar does.
- `src/accounts_late.rs`: Accounts ops that can outlast the client's 5 s call answer `{state: "working", ticket, op}`; the result is kept for `accounts.result` and also sent as `accounts.done`, so a reconnected client never loses it.
- `src/accounts_late_tests.rs::config write failure`: If the live Keychain write lands and then `~/.claude.json` fails, the switch must put the Keychain item back; a switch is never left half done.
- `src/accounts_signin.rs`: One browser sign-in at a time on a 127.0.0.1 listener; it stops at once when cancelled or `accounts` goes off, and the code is exchanged and the login saved only while the switch is on.
- `src/accounts_ops_log_tests.rs`: Every way the daemon changes or notices Claude Code's login must leave an `account.switched` event (and `account.login`, `lane.changed` for the rest), since cost goes to the account active at a message's time: `accounts.switch`, `accounts.list` with `sync`, the limits auto-switch (`ClaudeLimits::switch_for_limit`, with the limit window and percent) and Move All's main-login switch. `account_history.rs::DbSwitches` reads the `account.switched` rows back from `events.db` for `cost::account_log::merge`, so a new path that sets the login without `ClaudeAccounts::switch_for` or `sync` needs a test here. Engine code that runs on a worker thread (`slow()`) carries the op scope into the thread, or its events lose their `op_id` and actor.
- `src/acting_ops_tests.rs::interrupt`: A stop sends one Esc only if the session still works a moment later: a second Esc on an idle prompt opens rewind.
- `src/acting_permission_tests.rs`: The permission dialog reader was written from made-up screens (no real recording exists); a screen it refuses is kept, private, so a real one can become the fixture (`docs/recording.md`).
- `src/activity_ops.rs`: `activity.list` is app tier, read only and `OpSpec::APP_QUIET`: it reads `daemon/events.db` through `notchling_engine::activity` and answers rows with the old fields (`kind`, `op`, `who`, `result`, `detail`) and the new ones (`event`, `group`, `title`, `outcome`, `refs`, `seq`, `audit_n`). A row's fields come from the event's own fields by allow-list (`activity/reply.rs`): a new field reaches a screen only by being added there on purpose, and none holds text. The first start imports the old files once (`import_once`) into legacy rows.
- `src/agy_ops_limits_tests.rs::session/new`: After `session/new` is answered acting may go off as the reply is made; the first message must not reopen the session it would be sent to.
- `src/agy_phone.rs`, `src/every_session.rs::live`: The phone's Antigravity state and chat (`Sources::foreign_live`) are read only and start nothing, so no switch is needed beyond the phone's own chat path. `AgyOps::phone_read` takes, in order: the session open and loaded in Notchling's own `agy acp` (its working flag and held conversation), a session another `agy` holds that the app already found (`Elsewhere::watched`, never a fresh `lsof` from the phone's path), else the session's own log (`brain/<id>/.system_generated/logs/transcript.jsonl`, the engine's `from_log_file`, a 4 MB tail) with the working flag from the summaries row's `RUNNING`, since a log that ends mid-turn may belong to a run that died. Every result is cut to the newest 512 KB (`CONVERSATION_BYTES`, as `agy.conversation`); the phone protocol has no `truncated` field, so the cut is silent there. A log is parsed again only when its size or time changes (`LogReads`, 64 kept). A list of several rows reads only rows from the last 6 hours (the rest keep the row's flag and an empty chat in the list); a single-row call, which is what opening a chat is, reads any age. Permission prompts of an `agy acp` session still do not reach the phone.
- `src/agy_sink.rs::options`: A session's model and thinking-level options go to the catalog before the change is announced, so a client that reacts to the event and then asks sees them.
- `src/awake_loop.rs`: The daemon holds the Mac's power assertion (decision 0004) but, as the Swift app did, only while an app is attached (`room.can_answer()`, an app-tier client of kind `App`): quitting Notchling lets go within one tick, even in Always On, and the next attach takes it again (a refusal reported before is reported again for the new run of the app). `pmset -g assertions` shows the process `notchling`, named "Notchling: keeping the Mac awake for running agents". Each change of the hold (taken, swapped between system and display, let go) is published as `awake.changed {holding}` on `settings` for the app's menu bar cup, and `awake.state` (`awake_ops.rs`, app tier, quiet) reads it; a refused hold announces nothing. It reads `mode` and `keepDisplayOn` from the store itself every 2 s (the app writes the store and never pushes them, unlike the limit modes), counts working sessions from the list `sessions.list` serves plus Notchling's own Codex turns and Antigravity sessions, and keeps what it holds when the store can't be read. Under a fixture root `power_for` gives a `FakePower`, so tests and dev runs never hold a real assertion. It is a Free setting (decision 0020): an agent's `settings.set mode` takes effect within one tick. A change of the setting is felt up to 2 s later, the Swift app's poll was about as slow.
- `src/wake_loop.rs`: Continue agents after sleep, the Swift `WakeResumer` run in the daemon. The Mac's wake comes from `platform::awake::PowerEvents` (only `HasPoweredOn` counts; none is started under a fixture root, `wakes_for`, so tests and dev runs never listen); every 2 s the loop notes a wake and, only while one is outstanding, the `continueAfterSleep` setting is on (read from the store each time, default on, a store it can't read means no nudge), `acting` is on and an app is attached, it reads the session list and asks `engine::control::WakeResumer` which jobs to nudge (20 s after the wake, within 30 minutes, background jobs whose last message is the sleep error, once per cut-off). The nudge types the prompt through `ActingOps::nudge`, the path a reply takes (`play`), one at a time, and a failure is logged with the job id and not retried for the same cut-off, as the Swift `try?`. Tests give it a fake wake source and, for the typing, `acting_ops_tests::setup`'s fake terminal: nothing here ever attaches to a real session. Differences from Swift: the daemon notes a wake whether or not it may act, so an app that attaches (and turns acting on) within the 30 minutes after a wake still resumes the cut-off jobs, where the Swift app, not running then, never saw that wake; a dark wake may count too (`HasPoweredOn` is sent for it); the tray has no Continue After the Mac Wakes item, only the Settings sheet's toggle.
- `src/bridge_backend.rs::pairing`: A pairing request is asked only of an app that follows the `bridge` topic; an app merely attached would not see it and the phone would wait out the whole time before being refused.
- `src/bridge_backend.rs::session.new`: The phone's `modelId` goes to `session.new` as given so the daemon's own catalog check applies again; the phone's family names (`opus`) map to the catalog's current id.
- `src/catalog_ops_tests.rs::fetch`: The live Claude model list is fetched with the main login's token only, never another saved account's expired slot (that would renew it); a refused token is not retried until it changes or a day passes, a 5xx holds off 15 minutes.
- `src/cli.rs::delegate`: `notchling delegate` takes everything after the subcommand as is, because the prompt may hold flags; the engine parses its own flags.
- `src/cluster_driver.rs`: One thread owns the `NodeCore`; links, local calls and hooks reach it through one channel, and whatever waits (a dial, a call from a node, a hook) runs on a thread of its own, so the driver never waits on I/O or holds a lock across it. A failed `cluster.db` save fails every waiting reply, records a `cluster.step` event (`save`), rebuilds the core from the last saved state and feeds `Linked` again for each open link. Replies go out only after the new status is stored and published, so a caller that reads `cluster.status` after its op sees the change. The node's tool versions are `VersionsOps`' last scan (read every minute), never a second hash of the binaries on the driver thread: hashing a large `claude` in a debug build held up the daemon's shutdown. `ClusterNode::close` waits at most 3 s for the thread.
- `src/cluster_cli.rs`: `notchling cluster join` takes the token from stdin only (`--token-stdin`); a token among the arguments is refused before anything connects, since arguments show in `ps` and shell history. Output goes through writers, not `println!`, so the file stays out of the one-writer lint's list.
- `src/cluster_join.rs`: A join on the home raises a fresh inbox id each time (`node-join:<node>:<ms>`). The responder and the 10-minute timer race through one flag, so exactly one of them acts: an answer applies `Approve` or `Deny`, the timer resolves the item Expired and denies the joiner, so a pending member never outlives its item. The joiner's name, OS and address come from an unapproved peer: control characters are dropped and the name is cut to 64.
- `src/cluster_node.rs::Hooks`: Each hook runs on its own thread and may block; `Submit::send` never waits, so a responder under the inbox lock can use it.
- `src/cluster_ops.rs::join`: The `cluster` switch is off at every start. `settings.set_switch` (app tier) turns it on, and so does `cluster.join` from the app, or from an agent only while no app is attached (a headless node that Machines joins over ssh). With an app attached an agent's join is refused with the off message: a joined node runs what its home sends. Every switch turned on by a join is a `switch.changed` event (cause `user` for the app, `cluster_join` for a headless join). An agent's join with no app attached is headless: the joiner says so and the home records the member `headless`, which is what lets it rejoin by itself after a restart (`cluster_wiring.rs::rejoin_on_start`). An app-tier join is never headless.
- `src/cluster_switches.rs`: Only `acting`, `bridge` and `install` follow the home (`policy::cluster_may_set`), and only while no app is attached; with an app the app owns its switches. A change goes through the same ops the app calls (as the app tier, `ClientKind::Node`), only when the value differs, and is recorded as a `switch.changed` event (cause `cluster_node`); the home is the `peer` of the `cluster.step` `call` event for `node.switch.set`. `node.switch.set` is answered here, before `Ops`, since it is a node-only op with no local API name.
- `src/cluster_wiring.rs::rejoin_on_start`: The one start-time exception to "off at every start" (decision 0007's note of 2026-11-14): a node whose loaded `cluster.db` says it is an active, headless, non-client member, with another active member as home (`ClusterState::rejoin_home`, read once in `Driver::new` before the thread runs), turns `cluster` on at daemon start if no app is attached, recorded as a `switch.changed` event (cause `cluster_rejoin`) and a `cluster.step` event (`rejoined`, the home as `peer`). The role is the home's record, replicated in `Members`; an agent that rewrites the local copy gains only a dial to the pinned home, and a rewritten home certificate or address fails the pin. Nothing else turns on here: `acting`, `bridge` and `install` still wait for the home's `Members`/`HelloOk` (`cluster_switches.rs`), and only while no app is attached. Call it after `follow_switch`, or the driver never hears the switch.
- `src/cluster_wiring.rs::DaemonCalls`: A call from another node runs through the same `Ops` the socket serves, with the socket's checks again (unknown op, app tier, approval needs an attached app), as `ClientKind::Node`, and at the app tier only for an App origin the core's policy allowed. `Ops` is held weakly. `NOTCHLING_CLUSTER_LOOPBACK=1` binds 127.0.0.1 instead of the Tailscale addresses, and only in a daemon run from a cargo target folder; under a fixture root without it nothing listens or dials.
- `src/codex_acting_tests.rs::set_acting(false)`: If acting goes off while a Codex process is starting, `stop_all` finds nothing, so the start itself must re-check the switch and abandon.
- `src/codex_slow.rs::delete`: Before `codex delete --force` the turn is stopped and its waiting messages dropped, with a moment to release the rollout file the delete removes; late ends carry the caller's `draft` row id.
- `src/control_ops_tests.rs::session.new`: `session.new` passes only `--model <allowed model>` to `claude`; nothing that changes what the session may do. Trust Folder refuses non-absolute, missing, root and home folders, and a refusal older than ten minutes.
- `src/daemon.rs::read_list`: One read of the session list runs under catch-unwind: a panic in a reader keeps the last good list and the daemon serving every client.
- `src/daemon.rs::scan`: A list read is stored before `sessions.changed` is sent, and the watcher starts before the first read; clients subscribe, then list, and lose no change that way.
- `src/daemon_wiring.rs::bridge folder`: The bridge keeps its files in `AgentConsole` beside the data folder (the Swift app's, so paired phones carry over; `<root>/AgentConsole` under a fixture root); nothing is bound or written until `bridge.set`.
- `src/daemon_wiring.rs::sessions.list`: A `sessions.list` answered before the first read adds `"partial": true` beside `ok` while the result stays a bare list, which every client reads as one.
- `src/delegate_cli.rs::run`: Delegation sets `NOTCHLING_DELEGATE_DEPTH` one level deeper for the tools' own processes, resolves `~` to the real home even over a fixture root, and reads `~/.claude.json` from the root, never the real one.
- `src/delegate_cli.rs::signals, src/signals.rs`: Signal handlers only do an atomic store (async-signal-safe); a watcher thread or the main loop does the stopping and the socket cleanup.
- `src/every_session.rs`: Codex and Antigravity rows for `sessions.list {tools: "all"}` and for the phone (`DaemonSources::foreign_rows`) come from the same read-only list, cached 2 s, whatever the bridge switch and with or without an app, so the phone through the daemon lists every tool. No argument still means Claude Code only: the app's session source and the `sessions` topic read that list and add their own Codex and Antigravity rows, so adding the others there would show each twice. A Codex child rollout is skipped by its first `session_meta` (`parent_thread_id`, `thread_source: "subagent"`), since `transcript::codex::meta` reads the last one and a child would list under its parent's id; the child index of the provider contract's phase 1 replaces that check.- `src/git_ops.rs`: `git.status`, `git.diff` and the branch ops (`git.branch_diff_stat`, `git.branch_diff_file`, `git.branches`: the Changes panel, shapes in docs/local-api-ops.md) are app tier and read only, with no switch, so the checks are the whole defence: `cwd` must be a known session's folder or below it (the session list, Antigravity's rows, recent Codex rollouts; the list is cached 5 s and read again only when stale, never on a miss, so a session that just began is served up to 5 s late, and a refused `cwd` costs no scan; `git` then runs in the canonical path that was checked), and `path` stays inside the repository and is exactly a current changed file (`notchling_engine::git::guard`, `read_diff`). All five ops are `OpSpec::APP_QUIET`: the app polls every 5 s (the stat with each status), and an audit line per success would rotate out the refusals and the vault's entries; failures are still audited. Never add a way to run any other `git` subcommand or to pass an option through. The launcher it gets is `SandboxedLauncher` over `RealLauncher` (`daemon_wiring.rs`): git runs under `sandbox-exec` with every exec but git's own denied, because the `-c` nulling alone races a repository whose config is rewritten between two runs; never give `GitOps` a plain launcher in production. Only a root-owned git (not group or world writable, nor any parent) is allowed to run: in practice the Command Line Tools' git. A Mac with only Xcode.app and no Command Line Tools answers `can't read this repo safely`. Off macOS both ops answer `unimplemented`. LFS files with a changed timestamp may show as modified with a binary diff (the filter can't start), accepted.
- `src/held_ops.rs`: `session.reply` to a working Claude Code job is held, not typed (one entry per session, later messages join it with a blank line; engine `reply::held` is the pure part). Typing into a busy Claude Code puts the message in its own queue, which is lost when the session restarts and which Claude Code injects mid-turn. `flush_held` runs on a 1 s thread (`spawn_held_loop`, stopped in `close`), types only while `acting` is on, only for a `completed` row that `can_reply()`, and only 20 s after the last send (the row stays `completed` for a moment after a send, and a second send then would queue in Claude Code). A failed send is put back in front. Held text is memory only. The app shows it as one queued bubble from `session.held`; a client that connects later does not see it.
- `src/hook_output.rs::answer`: A hook answer's `updatedInput` replaces the whole tool input, so an AskUserQuestion answer sends the questions back with the answers.
- `src/install_ops_tests.rs::lock`: Install ops read the `install` switch only after taking the install lock, so a call that waited behind another change still honors a switch turned off meanwhile.
- `src/late_reply.rs::Late::run`: A job that outlasts its call's budget hands its result to exactly one of the reply or the `finish` event: never both, never neither, even when it ends right at the budget.
- `src/layout.rs::agy_copy`: The copy of Antigravity's summaries database lives in `<data dir>/daemon`, never `<data dir>/antigravity`, where the Swift app keeps the same file names and the daemon would delete and rewrite its copy.
- `src/layout.rs::cluster_dir`: `<data dir>/cluster` holds `cluster.db` and the node identity in `node/`, made at the daemon's first start; a wipe removes the database only, never the identity.
- `src/layout.rs::from_args`: The app always passes `--socket`; naming the usual socket is not choosing another, so the daemon still keeps its documents in the data folder. A relative `CODEX_HOME` is ignored.
- `src/layout.rs::vault_path`: The daemon's vault list and search index are its own (`daemon/vault` doc in `notchling.db`, `daemon/` folder), never the Swift app's `vault.json` or pages index, until the maintainer hands them over.
- `src/lib.rs, src/main.rs::hook`: `notchling hook` always exits 0 with no output on trouble or odd arguments: Claude Code reads exit 2 as "block the tool".
- `src/limits_sources.rs`: Watcher sources read each account's usage with its own token and never renew a token in use (main login or lane), and re-check `accounts` themselves; a nudge also needs `acting`, as it types into a session.
- `src/log_rotate.rs`: `notchlingd.log` is opened by `ensure_daemon` or launchd, not by the daemon, so rotation is a rename and then dup2 of a new file onto fds 1 and 2. It adopts the fds only if fd 2 is that same file (device and inode), checks at start and every minute, keeps one `.1`, and a log someone deleted is just opened again. `tests/log_rotate_e2e.rs` starts a real daemon over a log past 5 MB.
- `src/log_bus.rs`, `log_queue.rs`, `log_audit.rs`, `log_activity.rs`, `log_start.rs`: The daemon is the only writer. Every `Emit::push` goes into one of two queues (`Always` kinds and `Toggle` kinds, `log_queue.rs`) and one thread stamps the envelope (`EnvMaker`: `seq`, `host`, `proc`, `pid`, `boot`) and hands it to the sinks in turn; a `commit` waits for its line to be written and flushed (Audit) and returns an error when it can't be, so the caller refuses its effect. A full queue drops an event and counts it by class (`log.dropped`, `queue_full`, reported to the Audit for the sink it cost), and the `Always` queue is the one that is kept. `AuditSink` checks the real length of the finished line against the 4 KB rule (`Fields::fit` shortens lists and refs first) and counts an oversize event instead of writing a broken line; it seals each line with the previous seal, writes unsealed lines (`"unsealed":"key_missing"`) when the key can't be read, and starts a new chain only on `log.chain.start`, which the app sends after the user confirms. The month is the line's own time, so a clock step never reopens an old file. `ActivitySink` writes the row to `events.db` and publishes it on the `log` topic. `log_start::start` runs before the socket is served: legacy move, salt, key, import, then the bus; `chain_started` can come before `daemon.started` on a first run.
- `src/log_checks.rs`, `log_retention.rs`, `log_ops.rs`: `log.verify` checks the whole chain (`events::audit_check`), at start, hourly and on request, and an Inbox warning is raised when the log changed outside Notchling (a cut tail, an edited line, a missing month) and cleared when the user starts a new chain. With `n` it also returns one line's `kind`, `outcome`, `ts` and fields, which the Activity row's Check Against the Audit Log compares. A fresh daemon answers `sealing: "starting"` until the key is read, and a test must wait for it to change. Retention (`log_retention.rs`) keeps a year by default (90 days and 2 years are the other choices), caps the folder at 500 MB and prunes only whole months from the oldest, writing an `audit.pruned` seal first so the next check knows where the chain went on; `log.audit.delete` is the user's own delete and asks the app tier.
- `src/op_kinds.rs`: Every op in `wire.rs` has a `Home`: the kind that records it (`Home::Kind`), the generic `op.called` (`Called`) or none because it is a quiet poll (`Quiet`). A test fails for an op with no home, so a new op names its kind there. An area records its own event inside the op (commit first for a secret, a setting or a session) and marks the op's scope recorded (`Scope::mark_recorded`) so the server doesn't write `op.called` as well. The agent tier's read ops are `Quiet`.
- `src/late_emit.rs`: An area built before the log exists (the daemon builds `OpGroup`s first) takes a `late_emit::Events`, which holds nothing until `set_log` binds the bus, so no area knows the order. Tests use `MemorySink` through the same type. An event emitted before the bind is queued and delivered after it.
- `layout.rs::audit_path`: the old `audit.jsonl`, kept only to move and import it. New code uses `audit_dir`.
- `src/prompts.rs::Kind`: In auto mode an AskUserQuestion also arrives as a permission request once the PreToolUse hook passes, so a prompt of either kind may need to be found by session id.
- `src/providers_add.rs::list_waiting`: An add flow is listed as waiting before its reply goes out, under the lock `close` reads after setting `closing`, so exactly one of them cancels it; an abandoned flow never writes a login.
- `src/providers_gate.rs`: The provider effects (Keychain, network, processes, apps) are gated on `accounts` besides each op's check; off, reads find nothing, writes fail, and every app counts as running so a switch refuses.
- `src/quiet_ops.rs`: `QUIET_READS` are the app-tier read-only polls whose `OpSpec::APP` becomes `APP_QUIET` in `Ops::spec`; `loud` puts a call with `sync` or `refresh` true back in the audit. `quiet_ops_tests.rs` lists every op name in `wire.rs` as quiet or never quiet, so a new op must be classified and an acting, writing or vault op can't be in the quiet list.
- `src/service.rs::plist`: The LaunchAgent uses `KeepAlive` `Crashed`, not `SuccessfulExit = false`: the daemon exits 0 when stopped or when another serves, and non-zero only on setup errors a restart would retry every 10 s.
- `src/settings_asks.rs`: An ask's inbox responder runs under the inbox lock, so it only marks the ask and hands it to the ask thread, which writes the value, audits the end, expires overdue asks (closing their items) and withdraws those still waiting at `close`. An allowed ask is written even after the agent's call stopped waiting: the user's Allow is the change.
- `src/settings_cli.rs`: `notchling settings set` exits 0 set, 1 refused (unknown key, bad value, a switch or a `never` key), 2 trouble (no daemon, bad arguments, a withdrawn ask), 3 not allowed (denied, unanswered, no app to ask); the `notchling-settings` skill text says the same, so change both together. An `ask` key is sent with `wait: 0` and then polled with `settings.asked`, 25 s a call, so no one call outlasts the client's timeout.
- `src/settings_ops.rs`: A key's class for agents is data next to it in `engine/src/settings/keys.rs` (`.free`, `.ask`, `.never`); a key without one is `never` here, and `settings/agents_tests.rs` fails until it has one. No tier sets a switch or a `never` key through these ops: the switches stay with `settings.set_acting`, `bridge.set` and `settings.set_switch` (decision 0007, kept by 0020), and the app writes its own records itself. An agent never gets a `never` key's value. The server audits only app-tier ops, so every `settings.set` is audited here.
- `src/switches.rs::SwitchFlag`: Switch listeners run on the switch's own thread, after the flag flips, in order; `set` waits at most `LISTENER_WAIT`, and a listener must never set its own switch.
- `src/vault_args.rs`: Vault argument parsing returns fixed error texts, never serde's, because serde errors can quote the text read, which may be a secret value.
- `src/vault_caller.rs`: An ask-first approval shows `verified {exe, pid, cwd, parents, folder_matches}` taken from the socket's peer credentials and the OS, never from the request; the caller's claimed folder and command are only claims.
- `src/vault_cli.rs`: `notchling secrets/secret/secret-request` never touch the Keychain or a vault file; `--json` output is read through `VaultEntry`, which has no field for a value, and a refusal leaves stdout empty.
- `src/vault_ops_lock_tests.rs`: Turning the vault off must answer at once even while a Keychain read waits on a prompt; the read that was in flight answers "off" and its values are dropped, so the next use reads the item again.
- `src/vault_wait.rs`: Vault approval and form ids are 128 random bits from the OS (no randomness, no wait); only the app follows the topic; waits are capped; every timeout, departure, switch-off or stop is a "no".
- `src/versions_ops.rs`: The Mac's tool versions come from files (`engine::versions::mac::detect`) on a watcher thread over `watch_paths` and a rescan every 10 minutes; nothing under `~/.claude`, `~/.codex` or `~/.local` is written, and no `--version` runs for Claude Code, Codex or Notchling. `agy --version` (`CAP-PROCESS`) runs at most every 10 minutes and only when no file gives agy's version, never from a `versions.get`. `versions.get` is agent tier, `versions.workers` app tier and quiet (it is asked by Settings); the `versions` topic sends `versions.changed`. A version seen for the first time is a `tool.version_seen` event through `versions::record::Recorder` (`AuditRecorder`); the other facts (changed, drift, self-update, checked, load failed) have no kind yet and are not recorded. No version text from a worker is logged. A tool-version mismatch warns and never refuses (cluster b, coordinator's call C1).
- `src/versions_check.rs`, `versions_update.rs`: A new Mac version is checked by itself after a rescan and again on `versions.check` (app tier): the commands run through the launcher with a timeout and a capped output (`CAP-PROCESS`), the strict transcript pass reads the newest 20 files at most 4 MB each, and a second `CantTell` 120 s after the first fails the version with the part "version" and the reason "it didn't start". Checks are off unless the data root is real (`Checks::set_enabled(!layout.fixture)`), so no fixture root ever runs a binary. Notchling's own check runs in process over compiled-in fixtures. `versions.latest` (app tier, quiet) reads the vendor's newest version with `curl --proto =https` through the launcher (`CAP-NETWORK`), kept an hour and a failure five minutes; the error names the host only. `versions.update_local` (app tier, `install` switch) runs the method's update with the installed binary's own path (npm and Homebrew resolve their program) and answers at once; `versions.updated` follows, then a rescan checks the new version. The soak pass runs every 10 minutes from the run loop. Inbox notices (`Kind::VersionCheckFailed`) get a fresh id per failure and expire by the clock.
- `src/versions_drift.rs`: `Drifts::pass` runs after every rescan and once a minute (`VersionsOps::drift_pass`): it reads the `versions/workers` document Machines writes, takes the Mac's reference only for a tool whose installed binary is the checked one (`Book::usable`), and raises or withdraws `version_drift` notices from `plan_notices`; `versions/drift-noticed` keeps what was noticed so a restart does not raise it again (an Open item loads as Withdrawn after a restart, by design). It needs an inbox (`set_inbox`) and does nothing without one. The same pass copies new `versions/selfupdate-log` entries into the recorder once. Nothing here starts a process or touches a worker.
