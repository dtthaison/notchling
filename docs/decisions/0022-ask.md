# 0022: Ask, an agent asks the person and gets the answer back

## Context

When an agent needs a decision today it stops and reports to the main session, which relays the question to the person. With several agents asking at once the questions pile up in the main chat, the main model spends tokens relaying, the asking agent has ended and must be started again with the answer, and an agent on a Worker can't ask at all ([the design](../superpowers/specs/2026-11-16-ask-design.md), §1).

Facts as of 2026-11-17:

- A Claude Code background subagent that starts a command with `run_in_background` and ends its turn is woken when the command exits (wake test 2026-11-16; plan Task 1, ruling P3, for a `claude -p` main thread). Current Claude Code has no foreground subagent. A woken subagent's result reaches its caller only through SubagentHandback called again.
- Codex and Antigravity have no such wake; a command they run under `notchling delegate` can block for minutes (P4).
- The kernel tells which Claude Code session a process descends from (the hook's check). Which agent inside the session ran a command is written only in transcripts, which any agent of that session can write ([0007](0007-local-api-tiers.md): files at rest are not a tier boundary).
- The maintainer accepted the design's calls M1 to M7 as recommended on 2026-11-16.

## Decision

- An agent asks with `notchling ask`; the question is a Node-class `asks` row in `notchling.db`; the answer goes to the waiting command, never through the main model.
- Claude Code agents wait in a background command whose exit wakes them; delegated Codex and Antigravity jobs block with `--wait` inside the delegate's limit.
- The session comes from the kernel; who inside it asked comes from transcripts and is a label, not proof.
- Only the person answers, except the main session for its own subagents' and jobs' questions that allow it; agents never answer the person's questions.
- A question survives daemon restarts; the command reconnects with the same id; first answer wins.
- One Inbox item per open question carries it to the Mac's Inbox and the phone; a Worker's reaches the home's Inbox by the existing mirror, answered by a choice.

## Consequences

- M1: the main session's answer rests on the kernel (same session) and the transcript (it is the main session, not a subagent). One agent of a session could forge a transcript line and answer a sibling's question that allowed the main session to answer. Accepted for v1: only questions whose asker opted in, only from inside the same session; the card says "Answered · main session" and the event records `by: main`. No agent can answer a question meant for the person.
- M2: the question text, cut to 400 characters, is in the Inbox item, so it reaches the phone and, in a cluster, `cluster.db`, the Standbys and the home (for a Worker's question). The answer text never leaves the asking node's `asks` row and the asking command. `docs/policies/privacy.md` says so.
- M3: the agy delegate gains one allow: a terminal command that is exactly this `notchling` binary followed by `ask --wait` and words, with no shell operator, substitution or redirection, is allowed once; every other request is declined as before.
- M4: Codex's sandbox is unchanged. A read-only Codex job can't reach the daemon's socket (P4), so `ask` exits 3 there; the skill says to ask only from `--write` jobs.
- M5: Notchling never types into the main session to wake it; a main session that wants its subagents' questions runs `notchling asks --wait` in the background.
- M6: Worker questions are in v1, choices only, through the inbox mirror.
- M7: a new skill, `notchling-ask`, is installed into Claude Code, Codex and Antigravity like the other `notchling-*` skills.
- Only counts reach the Audit, Activity and events (`session.ask`); question and answer text never do.
- Built on branch `agent/ask`. The plan is [2026-11-16-ask](../superpowers/plans/2026-11-16-ask.md).
