# Notchling: notes for Claude

A macOS menu bar app (Swift, AppKit + SwiftUI) that shows Claude Code agents in the camera notch and keeps the Mac awake. See README.md for what it does from the user's side.

## Build, install, run

- `./build.sh` builds `build/Notchling.app`; `./build.sh --install` replaces `/Applications/Notchling.app` and relaunches it. Always install after a change the user should see; they test on their own screen.
- Code lives in feature folders under `Sources/Notchling/` (App, Notch, Agents, Hook, Accounts, Limits, Lanes, Chat, DesignKit, Pages, Search, Terminal, Phone). `build.sh` compiles every file there with swiftc, after building `Sources/ConsoleCore` (the phone bridge engine, session host client and transcript/session readers) as a static module per architecture that Notchling and `Sources/hostd` import; `Package.swift` exists for `swift test`, which runs `Tests/NotchlingTests` (`@testable import Notchling`, fixtures in `Fixtures/`) and `Tests/ConsoleCoreTests`. Run `swift test` after a change to logic, and add a test with any new pure logic or parser. The restructuring plan is in `docs/architecture.md`.
- Bundle id `local.notchling`; settings live in its UserDefaults. `AppDelegate.migrateFromAwake()` copies keys from the old `local.awake.menubar` domain (the app used to be called Awake). When adding a setting, add its key to that list.

## Phone (the old Agent Console, now inside Notchling)

Notchling is the only Mac app. `Sources/Notchling/Phone/` runs the phone bridge (TLS :47821, tunnel origin on loopback :47822 behind the Cloudflare Access JWT check, pairing, rate limit, audit log; the engine is `ConsoleCore`'s `BridgeCore`/`BridgeRouter`, protocol `agentconsole.v1` is what `mobile/` speaks, so don't change it casually). `PhoneService.shared` starts it at launch; `PhoneModel` is what the bridge asks of the app (sessions, hostd terminals, takeover, prompt answers); `PhonePanel.swift` is the pairing UI, a popover from the Phone button at the top right of Chat's header (QR and one-time code, paired phones, bridge switch, tunnel status). Data stays in `~/Library/Application Support/AgentConsole` (certificate, tokens, tunnel settings), so a paired phone and the Cloudflare setup survive. `agentconsole://open[?phones=1]` is handled by `AppDelegate.application(_:open:)`. Terminal sessions whose pty lives in hostd (`agent-console-hostd`, a LaunchAgent started from `Contents/Helpers`) take replies from Chat: `ReplySender.send(_:to:)` types through `HostTerminals` (set by `PhoneService`), so the Mac and the phone share one terminal; the notch's own reply path is unchanged. Moving from the old two-app setup: `tools/migrate-and-install.sh` (read its header first, it ends the old sessions and resumes them). Additive ops and fields the phone uses (older phones and Macs ignore them): `activity` and `facts` (context tokens/window, the active account's 5h and Week limits) on each session, filled in by `LiveBridgeBackend.enrich` from `TranscriptReader`/`ConversationReader`; `kind` (shell, compaction), `steps` (tool calls with output and an Edit/Write diff) and `output` on chat messages, parsed by `ChatTranscript`; `commands.list {sessionId}` (Notchling's `SlashCommands`); and `session.image.begin/chunk/end` (a photo in 96 KB base64 pieces because a bridge message is capped at 256 KB; saved 0600 under `~/Library/Caches/AgentConsole/phone-images`, pruned after a day, and its path typed into the session with the caption, the way a dragged-in image reaches claude). Archiving a session is a phone-side preference (a JSON file on the phone). The phone app's look is `mobile/DESIGN.md`, taken from Chat's kit. `ConsoleCore` must stay free of Notchling types and of macOS 14 APIs (Notchling's minimum is 13: `SessionStore` is an `ObservableObject`, not `@Observable`).

## Checking UI changes

This environment can't take screenshots, and screenshots the user pastes from the thumbnail live in a temp folder that is usually unreadable or already deleted. Ask for them to be saved to the Desktop instead. To see a view or menu yourself, use the `render-notch-view` skill.

README GIFs come from the real views with made-up data: `Demo/make-demo.sh` (notch, `docs/demo.gif`) and `Demo/make-demo.sh accounts` (`docs/accounts.gif`). The renderer is built with `-D DEMO`, which turns on the stores' `#if DEMO` setters; the app build never includes them.

## Architecture in one pass

- `NotchModel.size(for:)` is the single source of truth for the black shape's size per state. `NotchController` keeps a transparent canvas (screen-wide, resized only when the display changes) centred on the camera and toggles `ignoresMouseEvents` by testing the mouse against that shape, so clicks outside fall through.
- Question and permission cards report their real height through `CardHeightKey` → `model.cardHeight`; don't go back to estimating heights.
- `PetView` keeps its position in a `Walk` object between frames; its path is computed from the shape, not from the clock.
- The hook (`Notchling --hook`) is a separate short-lived process. It talks to the app only through files in `~/Library/Application Support/Notchling/` and must always exit with a valid answer or a pass, never hang Claude Code beyond its 300 s timeout.
- The Chat window (`ChatWindow.swift`, menu bar > Chat…) is the full-size view of a session: sidebar from `notch.model.agents`, history from `ConversationReader.read` (items: user/assistant text, thinking, tool steps with output and diffs, turn ends, notices; plus tasks and session facts for the inspector), drawn by `ChatParts.swift` and `ChatMarkdown.swift` (tables need no `|---|` row; links go through `ChatModel.open`, which opens a saved artifact in `PagePanel` beside the chat, reusing the Artifacts window's `PagePreview`). Prose (headings, paragraphs, lists) is one `ProseText` NSTextView per run, because SwiftUI's selectable `Text` can't select across views; tables and code stay SwiftUI, replies through `ReplySender` like the notch. Questions and permissions go through `NotchModel.choose`/`decide` so the notch and the window share one answered state. Terminal sessions are read-only there. Each session's account comes from `ChatModel.account(for:)`: the lane whose folder the session was found in (`Agent.configDir`, set by `AgentMonitor`, which scans every `LaneStore.configDirs()` entry), else the main login. `ReplySender`, `AgentActions` and `claude rm` find a job's lane with `AgentMonitor.configDir(forJob:)` and run `claude` with its `CLAUDE_CONFIG_DIR`. The header's account menu (`AccountMenu`, an NSMenu since a macOS 13 SwiftUI Menu drops custom labels) asks one thing, which account this session uses (picking another moves only it; where it then runs is Notchling's choice, so targets are plain emails), plus a Move All Sessions To submenu, Add Account… and Codex Accounts… (also at the bottom of New Session). Both open `AccountsSheet` over Chat (`AddAccountSheet.swift`, tabs Claude Code / Codex): the Accounts window's `SignInModel` browser sign-in, or the `CodexStore` list with Switch and Add Account. The user wants account work doable from Chat, not only the menu bar. Switching the main login or a whole lane is in the menu bar. It moves one background session (`ChatModel.moveSession`: `claude stop`, then `claude --bg --resume <transcript id>` with the target's `CLAUDE_CONFIG_DIR` and the job's `respawnFlags`; the old stopped job stays in the folder it left under the same id, so `AgentMonitor` lists only the current copy (not stopped first, then latest `updatedAt`; never `createdAt`, since waking an old copy keeps it), `configDir(forJob:)` picks that one, and Remove runs `claude rm` on every copy), puts every session on one account (`MoveAllPlan` in `MoveAll.swift`: background sessions in lanes stop and resume on the main login, the lane holding the account closes, the main login switches to it; stopped sessions stay, terminal sessions in the closed lane are signed out), and opens new terminal sessions in a lane; limit switches show as a banner in the sessions they moved. Design notes: `docs/chat-design.md` (BAMA's mac-design/ux-design passes). Its look is a design kit in `ChatKit.swift` (spec `docs/chat-kit.md`): views use `KitInk`/`KitType`/`KitMetric`/`KitMotion`/`KitIcon` and the kit's button and row styles, never raw colors or sizes; `KitGallery` shows every part in every state for a probe render. The ? button (sidebar, bottom left) names every part on screen, in Chat and the notch, from `.part("Name")` tags. When the user names a part ("the Context Meter"), grep for `.part("Context Meter"`. Tag new views too. Paths and commands in messages (`ChatPaths`): a path that exists becomes a link (a folder opens in Finder; a file opens in `FilePanel` where the page panel goes, viewer by `FilePreviewKind`: markdown rendered, HTML/SVG in a web view, text and code monospaced, images, PDFKit, AVKit, Quick Look for the rest; it reloads when the file changes; Quick Look, PDF and video don't show in a `cacheDisplay` probe, so check those by their loaded state), with relative paths read against folders the same message names, then the session's; a shell code block gets Run, and a command in inline code is a link that asks first. Both run in the terminal sheet (`TerminalSession(run:in:)`, the user's `zsh -ilc`, in the folder where the command's relative paths exist), not as a session `!` command, whose time limit a long render outlasts. The inspector's Git section comes from `GitInfo.read` (`git --no-optional-locks status --porcelain=v1 --branch`, `diff --numstat HEAD`, `log -1`, every 5 s while open, so it never holds the index lock the session's own git needs). The composer's `ModelPicker` switches the model by sending `/model <full id>` (`ModelPicker.choices`: Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5; update it when models change). Prose is measured by a `TextMeasurer` apart from the live text view, whose container follows its current frame and would never report a wider size. The header shows the session's context (`SessionFacts.contextTokens`, the latest request's input+output; `ChatFormat.contextWindow` knows only Opus 5.5 = 400k, others show no percentage) and the account's 5h/week limits (`ChatModel.usage(for:)`). `EffortPicker` sends `/effort <level>` (Claude Code also saves it as the default for new sessions); the current level is the `effort` field on assistant lines. Stop and Esc stop a working background session's turn (`ReplySender.interrupt`: Esc through `claude attach`, sent after a short settle since a busy screen never goes quiet; never on an idle session, where Esc twice opens rewind). After that the live status is `idle` while `state.json` still says `working`, so `AgentMonitor` trusts the live status. Edit on the newest queued message takes it back (`ReplySender.takeBackQueued`: clear the box, Up, which pulls the whole queue into the box and logs one `popAll` per message, then clear it and re-queue the older ones). Up on an empty box with no queue recalls your last prompt instead, often the same words, so success is read from the transcript's `popAll`, never the screen. New Session stays open until `claude --bg` starts; a folder Claude Code hasn't trusted is refused ("Workspace not trusted"), and Trust Folder and Start accepts its trust prompt in a hidden pty (`ReplySender.trustFolder`; "No, exit" is the default, so it's Down then Enter).
- New Session (`NewSessionSheet.swift`, from the sidebar's + and the empty screen) is a sheet: an account column (every Claude Code account from `sessionTargets`, every Codex account, an Add row per tool that signs in in place), a folder column, then Start. Choices are `SessionChoice`; Antigravity CLI is the next case to add. Claude starts `claude --bg` as before. Codex adds a draft row (`codex-new:<uuid>`, `.codex(sessionID: "")`), and its first message starts it. A non-active Codex account switches Codex first, since Codex has one login.
- Codex sessions in Chat (`CodexSessions.swift`, `CodexRunner.swift`): rows come from `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` (14 days; `.zst` ones are skipped), target `.codex(sessionID:)`, id `codex:<id>`. Only Chat shows them (`ChatModel.allAgents`), not the notch. `CodexReader` maps `response_item` messages, reasoning, calls and outputs (`exec_command` → shell, `apply_patch` → edit with diff) and `event_msg` `task_started`/`task_complete`/`token_count` onto `Conversation`. Codex's injected user messages (`<environment_context>`, `# AGENTS.md`) are skipped. A turn is its own `codex exec --json` process (`resume <id>` after the first) in the workspace-write sandbox, since exec can't ask for approval. `thread.started` gives a new session's id. Messages typed mid-turn wait in the outbox for the next turn, and Stop sends SIGINT. Exec has no slash commands (`CodexCommands.swift`, Codex 0.166's list plus `~/.codex/prompts/*.md` as `/prompts:<name>`): /model opens `CodexModelPicker`, /new and /clear start a session in the same folder, /delete runs `codex delete`, and the rest open the terminal sheet on `codex resume <id>` (`TerminalSession(program:…)`, keys typed one by one so Codex's popup takes them), refused while a Chat turn runs on that session. The header's limit bars for a Codex session are the active Codex login's first group (`ChatModel.limits(for:)`).
- Search (`SearchPanel.swift`): ⌘⇧P is a Carbon hot key (`GlobalHotKey`, no Accessibility permission) that shows a borderless non-activating `SearchPanel` near the top of the screen. It activates the app (a panel only gets keys while its app is active) and reactivates the previous app on Esc. Results are `PageLibrary.find(_:in:)`; Return opens the page in Chat's `PagePanel` through `ChatWindowController.showPage(folder:)`, as the menu's Artifacts items do. The Artifacts window is only for All Artifacts… and the panel's window button.
- Accounts are four providers off one window (a tab each: Claude Code, Claude Desktop, Codex, Antigravity) and four menu sections. Antigravity and Codex limits are `GroupedUsage` (named groups of bars), drawn by `GroupedLimits` in the window and `GroupedUsageRowView` in the menu. Every account card is the shared `AccountRow` view in `AccountsWindow.swift` (avatar, email, subtitle, In Use/Switch, ⋯ menu, and a `content` closure for limits/cost) — reuse it, don't hand-roll another card. Everything clickable shows the pointing hand: buttons use a kit style (`.kit(...)`, `.kitPlain` instead of `.plain`, the row and option styles), which brings it; other clickable SwiftUI views (`onTapGesture` rows) get `.pointerCursor()` (balanced push/pop, off while disabled); AppKit controls, including the ones SwiftUI draws with them (switches, pop-ups, segmented pickers, default buttons), get it from `PointerCursors.install()` at launch; custom NSViews (the menu rows) get `resetCursorRects` with `.pointingHand`.

## Things that bit before

- macOS 26 adds an icon to menu items with standard actions such as `terminate:`, which shifts every item in that group right. Use our own selectors.
- Transcripts can hold huge base64 image lines. `TranscriptReader` reads only the last 2 MB and skips lines over 100 KB.
- `CostTracker` scans several roots with a channel tag each: `~/.claude/projects` (Claude Code) and the Claude desktop app's `local-agent-mode-sessions`/`claude-code-sessions` (Desktop). Desktop transcripts carry the account in their path (`…/<accountUuid>/<orgUuid>/…`); the CLI's come from `AccountLog`. It keeps per-model token totals too, scans the whole history (no date filter) so "All Time" is real, and publishes a summary per window (7 / 30 / all) in `ranged`/`rangedByAccount`. It dedupes by `message.id|requestId`, so totals are lower than Claude Code's `/stats` (which counts messages copied into new transcripts on compaction/resume). Changing the cache's stored fields means bumping `Cache.current` (forces a full re-read).
- Claude Code 2.1.31x logs slash commands and their output as `type: "system", subtype: "local_command"` lines (older builds used user lines with `<command-name>`/`<local-command-stdout>`); `ConversationReader` reads both. `!` shell commands are user lines `<bash-input>…</bash-input>`, then `<bash-stdout>…</bash-stdout><bash-stderr>…</bash-stderr>`; Chat shows them as "! command" and its output. Sending `!cmd` from Chat needs nothing special: the pasted text still enters shell mode (checked on 2.1.316). `/clear` in a background job starts a new transcript, but `state.json` keeps the old one in `linkScanPath` until its next link scan, so `TranscriptReader.successor` follows it: a newer file in the same folder that starts with the job's `agentName` and a `SessionStart:clear` hook.
- Commands that open a menu (`/plugin`, `/mcp`, `/agents`…, `SlashCommands.menuCommands`) write nothing to the transcript, and a hidden attach detaches before the menu draws. Chat runs them in its terminal sheet (`Terminal/`): `TerminalSession` runs `claude attach` in a pty, `TerminalScreen` is a small emulator tested against recorded bytes (`Fixtures/terminal`), `TerminalCanvas` draws it. What it took: `forkpty`, not `posix_spawn` (with posix_spawn the child got SIGWINCH but never repainted for the new size); no answers to device-attribute queries (`CSI c`, `CSI > q`: answered, Claude Code dropped its colors and the answer landed in its input box); drop an inherited `NO_COLOR`; pauses between the clear keys, the paste and Enter (in one burst they read as a paste with "invisible characters"); on resize keep rows in place, since Claude Code repaints only what changed. `ZLiveReplyTests/testTerminal` checks it against a real session.
- Subagents (`Subagents.swift`): each Agent call's transcript is `<session>/subagents/agent-<id>.jsonl` (all lines `isSidechain`, so `ConversationReader.readSubagent` reads them; the session reader skips them) with `agent-<id>.meta.json` (`description`, `agentType`, `model`, `effort`, `toolUseId`, `requestShape: "background"`). A background one's Agent result is only `status: "async_launched"`; it ends with a `<task-notification>` (`<task-id>` = agent id, `<status>`) in the session's transcript (`Conversation.finishedAgents`), and its own last step is a tool result "Report delivered to your caller" (`handedBack`, for notices older than the 4 MB read). Chat lists them in the Details panel and opens one read-only in place of the conversation (`ChatModel.subagentID`; Esc or ⌘[ goes back); an Agent step has Open. The notch row shows a badge for those written to in the last 90 s.
- Secret Vault (`Vault/`): credentials agents use without them going through a chat. The key button at the bottom of Chat's sidebar opens `VaultSheet` (add a token or a username and password, the URL it's for, its variable names and a note for agents; the URL also goes to the command as `$<NAME>_URL` and its host into the skill's description, so agents pick a secret by the site a task talks to). The list is `~/Library/Application Support/Notchling/vault.json` (0600, no values); each value is Keychain service `Notchling Vault`, account = lowercased name, base64 JSON. Agents run `Notchling --secrets` (names, variables, notes) and `Notchling --secret a,b -- <command>` (one argument runs through `sh -c`): the command gets the variables, its stdout/stderr pass through a `Redactor` that replaces every value (≥ 4 bytes) with `[secret:<name>]`, holding back only a tail that could start one. These are checked first in `main.swift`, before `--hook`/`--page`, which the wrapped command may contain. The `notchling-vault` skill (`VaultSkill`, names in its description) exists only while the vault has entries. Nothing stops an agent from reading the Keychain item with `security` itself; the skill tells it not to.
- `claude -p` sessions (entrypoint `sdk-cli`) are headless: the hook must ignore them, and they can't be replied to.
- A background job with `template: "exec"` runs a shell command (sd autopilot's lane scripts), not a conversation: no transcript, no replies. `Agent.command` holds its `intent`; Chat shows it with `CommandJobView` and the tail of the file its output is redirected to (`CommandJob.outputPath`).
- `lsof -p <pid> -iTCP` ORs its filters and lists every listener on the Mac; add `-a` to AND them (the Antigravity port probe had this bug).
- Limits change without notice. `/api/oauth/usage` returned `five_hour: null` for Max 20x from October 2026, so `session` can be nil on any account. Its `limits` list (`kind`, `group`, `percent`, `resets_at`, `scope`) is the fuller source: `AccountStore.apply(limits:to:)` maps it onto `session`/`week`/`models`/`other`, and `other` counts toward switching. Keep the fixed keys as a fallback.
- A real account switch changes the user's live login, so test `LimitLogic` through a harness (all Sources except main.swift plus a test main), never by switching.
- Background job text replies go through `claude attach` in a pty with bracketed paste; question answers are typed as digits, with options.count + 1 as the free-text option. The session's input box keeps a draft across attaches, so a reply first clears it (`ReplySender.clearInput`: Ctrl+E, Ctrl+U, Backspace per line; never Ctrl+K, which a burst inserts as a literal vertical tab that stops Enter submitting, and never Esc/Ctrl+C, which interrupt). A reply sent while the session works is a `queue-operation` enqueue, then either a user line after `dequeue` or, taken in mid-turn, an `attachment` of type `queued_command` with no user line; `ConversationReader` shows both (`Conversation.queued`, "Queued" bubbles while live). A reply that shows up nowhere after `ChatModel.deliveryWait` comes back to the box with an error. Before typing, `ReplySender` reads the attach screen into a `TerminalScreen` and refuses (`Failure.dialog`) when a question or permission dialog is open (`dialogOpen`, fixture `question-open.bin`): a reply typed there becomes its answer, and a multi-question AskUserQuestion in a background job reaches Chat only as a "needs" summary it can't show. Chat then opens the terminal sheet. Replies sent while one is still going out wait in `ChatModel.outbox` and go one attach at a time.
- Account switching touches the user's real login. Replace only `claudeAiOauth` in the `Claude Code-credentials` item (it also holds MCP logins) and only `oauthAccount` in `~/.claude.json`. Never refresh the token of the active account: refresh tokens rotate, so it would sign Claude Code out. Keychain goes through `/usr/bin/security` (hex on stdin), never the Security framework: an ad hoc signed build loses access on every rebuild.
- Antigravity's real login is the Keychain item service `gemini` account `antigravity` (go-keyring: value is `go-keyring-base64:` + base64 of the JSON). It restores from there at launch; `~/.gemini/jetski-standalone-oauth-token` is only a mirror the standalone language server reads. So switching must set BOTH, and Add Account must delete the Keychain item (not just the file) to reach the sign-in screen. Update the item in place so Antigravity keeps read access. Both apps read at launch, so quit them first.
- Codex (`Codex.swift`, CLI 0.166): the CLI, its managed app-server daemon and the ChatGPT app (bundle `com.openai.codex`, named ChatGPT.app) share `~/.codex/auth.json`. Accounts are keyed `<chatgpt_user_id>:<chatgpt_account_id>` from the id token. Saved copies live in Keychain `Notchling Codex` as base64, because `security -w` prints a value containing newlines as hex. A switch saves the live file back, writes under a flock on `auth.lock`, then runs `codex app-server daemon restart` with output to /dev/null (a daemon holding a pipe would hang the read). Add runs `codex login -c cli_auth_credentials_store="file"` with a scratch `CODEX_HOME`. Limits are `GET chatgpt.com/backend-api/wham/usage` (Bearer access token, `ChatGPT-Account-Id`). Never renew a Codex token: refresh tokens rotate, and an open session still holding the old one would be signed out.
- Antigravity limits come from its local language server, not Google's APIs (those refuse consumer accounts). Port is random (`lsof`), CSRF token is `--csrf_token` in its args, header `x-codeium-csrf-token`, Connect JSON over self-signed HTTPS. Only works while Antigravity runs.
- Claude Desktop (`com.anthropic.claudefordesktop`) is a separate login from Claude Code, but the OAuth tokens are the same system (same client id). What decides its active account is the claude.ai **web session cookies** in `~/Library/Application Support/Claude/Cookies`, not the token — injecting a token does nothing (Desktop reverts to the cookie's account on restart). So switching, like Antigravity, captures the whole Cookies file while an account is active and restores it to switch, also setting `lastKnownAccountUuid`/`bootSideSessions` in config.json. Accounts match the Claude Code list by account UUID (id before the org). An account can only be switched to after it has been signed in to in Desktop once (the only way its cookies exist). Cookies backup: `Cookies.notchling-backup`; captured copies in `~/Library/Application Support/Notchling/desktop/<uuid>.cookies`. Quit the app before swapping; cookie DB format could change across Desktop updates.
- Artifacts (`claude.ai/artifact/...`) are per-login: after an account switch the old pages return 404, and their source file is often in a job's tmp folder that disappears with the job. `PageLibrary` keeps a local copy of each publish from a `PostToolUse(Artifact)` hook (same `--hook` process, handled before the "app running" check, 10 s timeout, installed separately from the prompt hooks via `setPagesInstalled`). Published pages are fragments without a doctype, so the copy is wrapped to render from disk; `pages.json` is written under a flock because sessions publish concurrently. A page's `account` is its first publisher and stays that on republish, since only that account can republish it. `PagesWindow.swift` is the window over the library: a separate resizable window, because the Accounts window is fixed at 460×540. The app has no main menu while it's menu-bar-only, so `EditingWindow` forwards ⌘C/V/X/A/W itself. While a titled window (Chat, Artifacts, Accounts) is open, `DockPresence` makes it a regular app (Dock icon, ⌘Tab, a small main menu with no Hide, which would hide the notch) and drops back to `.accessory` when the last one closes. `cacheDisplay` doesn't draw WKWebView, so a probe needs `takeSnapshot` for the page. Agents reach the library through `Notchling --page <link|id|words>` / `--pages`, the `notchling-pages` skill (`PageSkill`, written to `~/.claude/skills` with the page hook), a `PreToolUse(Artifact)` hook that denies a whole-page `read` of a saved link with a reason naming the local copy (unsaved links pass through; `path: "index.html"` still reads live), and a `PostToolUseFailure(Artifact)` hook that points a failed `read` at the local copy. The prompt hooks also live on `PreToolUse`, so install/remove/detect tell the two apart by the `Artifact` matcher. The same `PreToolUse(Artifact)` hook (60 s timeout) publishes to a page owned by another saved account through `OwnerPublish`: `POST https://api.anthropic.com/api/frame/deploy/direct` with that account's saved OAuth token, body `{slug: <uuid>, baseVersion: <live>, content, title}`. A link's 22-char id is the UUID in base58. The live version comes from `GET /api/frame/perm/<uuid>?org=<org>` (owner only; 404 for anyone else). Sharing can't replace this: personal accounts may only be owner-only or public, and a grant to another organization's account reads as 404 until it is accepted as an email invite. The library keeps each publish's `version` so a publish over a newer claude.ai version is refused unless `force`.
- Lanes (`Lanes.swift`): a lane is a Claude Code config folder `~/.claude-lanes/<name>` used with `CLAUDE_CONFIG_DIR=<path>`. Claude Code then keeps the login in Keychain item `Claude Code-credentials-<sha256(path)[:8]>`, the profile in `<path>/.claude.json` (so `/status` names the lane's account), and runs a background host of its own (`claude --bg` works in a lane; its `sessions` and `jobs` are in the lane folder, see `LaneStore.configDirs()`). `LaneStore.shared` entries (settings, CLAUDE.md, skills, plugins, projects, history, file-history, tasks…) are symlinks to ~/.claude; `relink` restores one an atomic save replaced (newer copy wins, the other kept as `.lane-backup`/`.lane-old-*`). Lanes are listed in `lanes.json` (the hook reads it; `LaneStore.current()` finds a hook's lane from its inherited `CLAUDE_CONFIG_DIR`). Rules: an account is live in one place (main or one lane), because renewing a login retires the old refresh token; an account in a lane takes its token from the lane's item and Notchling never renews it; switching a lane first copies its (maybe renewed) login back to the saved slot after checking the profile endpoint, then sets the new login and the lane's `oauthAccount`; the main switch refuses an account in a lane. After a switch, only the jobs it moved (main or that lane, by `Agent.configDir`) are respawned and nudged, with the lane's `CLAUDE_CONFIG_DIR`.
- macOS can refuse notifications from an ad hoc signed build (`UNErrorDomain` 1, "Notifications are not allowed for this application"). `UserNotifier` then uses `NoticeBanner`. Never use `osascript`: its notifications show Script Editor's name and icon.
- Editing `~/.claude/settings.json` is the user's real config. Change only our own hook entries (match on the `--hook` command), keep a backup, and keep their other hooks.

## Style

- Match the surrounding code: short doc comments that explain why, `guard` early, no force-unwraps outside probes.
- User-facing text is short and plain. Menu titles use Title Case.
- The user prefers short replies and "just build it"; ask only when a decision is genuinely theirs (accounts, tokens, anything outward-facing).
