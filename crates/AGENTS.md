# The Rust app: notes for agents

The Cargo workspace in `crates/` is Notchling now: a GPUI app (`notchling-app`) over an always-on daemon (`notchling daemon`), both built on one engine library. Since 2026-11-11 it is `/Applications/Notchling.app` on the maintainer's Mac and owns every resource in decision 0011's table; the Swift app in `legacy/macos/` is retired and stays the reference for behavior a port matches ([its notes](../legacy/macos/Sources/AGENTS.md), read on demand). The root [AGENTS.md](../AGENTS.md) has the layers, checks, the line and safety rules; [ARCHITECTURE.md](../ARCHITECTURE.md) and [docs/decisions/](../docs/decisions/) say why; [docs/feature-map.md](../docs/feature-map.md) names each feature's files and tests. Keep these notes true: when you change what a note describes, change the note, and when something bites you, add it under Things that bit before.

## Crates

| Crate (package) | What it is | Builds | Used by |
| --- | --- | --- | --- |
| `protocol` (`notchling-protocol`) | The phone bridge's wire types, `src/generated.rs`, written by `python3 tools/protocol/gen.py` from `protocol/agentconsole.v1.schema.json`. Never edit it by hand (`GUARD-PROTOCOL-GEN`; skill `add-protocol-field`) | library | engine |
| `platform` (`notchling-platform`) | OS adapters behind `cfg`: data folders (`paths`), file watching (`watch`), keep awake, notifications, private writes (`files`), running apps (`apps`); a missing one returns `Error::Unsupported` | library | engine, local-api, notchlingd, app |
| `engine` (`notchling-engine`) | Everything with no UI, half the code (below) | library | notchlingd, ptyhost, app |
| `local-api` (`notchling-local-api`) | Daemon to client socket: framing, peer identity, tiers, audit log, `Client`, `ensure_daemon` (decision 0007) | library | notchlingd, app |
| `notchlingd` (`notchling-notchlingd`) | The daemon and the command line (decision 0004) | `notchling` | bundled beside the app |
| `ptyhost` (`notchling-ptyhost`) | Terminal host, a port of the Swift `agent-console-hostd` with its `hostd.sock` contract | `notchling-ptyhost` | bundled in `Contents/Helpers` |
| `kit` (`notchling-kit`) | Design kit: tokens (every system), GPUI widgets and `KitGallery` (macOS) | library | app |
| `app` (`notchling-app`) | The GPUI app, and the Machines window | `notchling-app`, `notchling-machines` | nothing |

GPUI 0.2.2 (with `runtime_shaders`: no Metal Toolchain here) is a dependency of `kit` and `app` only under `[target.'cfg(target_os = "macos")'.dependencies]` (`LINT-GPUI-MACOS-ONLY`); everything else builds and is tested on macOS, Linux and Windows, and off macOS `notchling-app` says it isn't supported and exits 0. `[patch.crates-io]` swaps in `vendor/gpui/` (one fix, `vendor/gpui/NOTCHLING.md`). Rust 1.99.1 is pinned; `deny.toml` allows only permissive licenses (decision 0008). `app` and `kit` deny `unwrap`/`expect` outside tests. Files stay under 1,000 lines, 600 with a warning (`LINT-FILE-SIZE`): tests go in `<module>_tests.rs` or `tests_<area>.rs`.

## Build, run, test

```sh
cargo test --workspace --locked             # CI runs it on macOS, Linux and Windows
cargo clippy --workspace --all-targets -- -D warnings   # CI's clippy runs on Linux and never sees GPUI code: run it on the Mac
cargo fmt --all --check
cargo deny check
cargo test -p notchling-app -- --ignored    # the render tests: they open windows (a Mac with a display)
cargo build --release -p notchling-app -p notchling-notchlingd -p notchling-ptyhost
cargo run -p notchling-notchlingd --bin notchling -- daemon   # the `notchling` binary; set NOTCHLING_DATA_ROOT first (below)
```

- Look at and click GPUI only in a release build: debug GPUI is far too slow to judge. Unit tests are fine in debug.
- The target folder may not be `target/`: a `build.target-dir` in `~/.cargo/config.toml` can share one across checkouts, and two builds then wait on one lock. Give each parallel agent its own `CARGO_TARGET_DIR`; find binaries with `cargo metadata --format-version 1 --no-deps` (`target_directory`). Paths below assume the default.
- A picture of a view: `notchling-app --render <view> --out /tmp/v.png` (`--help` lists them; each area's `renders.rs` adds its own), over `--data-root <dir>`, else `NOTCHLING_DATA_ROOT`, else `crates/app/fixtures/`, never `~/.claude`. `NOTCHLING_RENDER_APPEARANCE=light|dark`; other `NOTCHLING_RENDER_*` variables force a state (grep `crates/app/src`).
- Chat's bench: `NOTCHLING_RENDER_BENCH=<seconds> NOTCHLING_RENDER_BENCH_MODE=<mode> notchling-app --render chat` over a generated 200-turn root (`chat::bench_fixture`) keeps the window up, drives one kind of activity into it (`mac/bench.rs`, `bench_events.rs`) and prints a `bench:` line and one `bench-json:` line with frames, CPU and the counters: draws of the root, conversation, Sidebar and Details Panel, rows built, bytes parsed, `at_end`, `forced`. Modes: `idle`, `scroll`, `scroll-fade`, `hover`, `select`, `typing`, `terminal`, `reload`, `menu` (`append` is `idle` while the test adds a line every 500 ms). `crates/app/tests/bench_chat.rs` runs them and holds the counts (ignored by default; a Mac with a display): `cargo test --release --locked -p notchling-app --test bench_chat -- --ignored --nocapture --test-threads=1`, in release and one at a time, since the numbers are CPU time. `NOTCHLING_BENCH_SECONDS` sets each mode's length. Judge a change by the counts; `ms/frame` moves with the Mac's load. Results and what each phase of decision 0018 changed: `docs/perf/chat-state-split-bench.md`. Smoothness of a scroll is held as counts too (`tests/bench_scroll.rs`, modes `scroll-start`, `scroll-slow`, `scroll-fling`, `scroll-momentum`, same command with `--test bench_scroll`): a recorder (`chat/view/scroll_probe.rs`, judged by `chat/scroll_trace.rs`) notes where every row painted in each draw and compares it with the wheel steps the bench injected (stalls, jumps, reversals, drifts, lost frames), and times each draw in the main thread's CPU time (`draws` in the `scroll` object: over 8.3 ms misses a 120 Hz frame, over 16.7 ms a 60 Hz one, with rows built and what the draw cost before the end of the list's layout). A script runs all its steps however late the Mac gets to them. `NOTCHLING_BENCH_SCROLL_DUMP=<file>` writes every frame (and `<file>.draws` every draw); `NOTCHLING_BENCH_REAL=<transcript>` runs `a_real_transcript_scrolls_by_the_wheel` over a copy of a real session (copied to the temp folder, never printed). `tests/render_blocks.rs` runs `NOTCHLING_RENDER_CHECK_BLOCKS=1` (the selectable texts against the model's blocks) and `tests/render_list_probe.rs` the list probe (`--render chat-list-probe`, gates G1 to G7); both ignored by default.
- A locked screen or a sleeping display sends a window no frames, so a bench reads `frames: 0` and a `--render` shows what loaded after its first frame never. The bench then draws frames itself, on a timer, through AppKit's `displayLayer:` (`bench_events::FrameDriver`; `NOTCHLING_BENCH_FORCE_FRAMES=1` always, `0` never; the line says `"forced":true`). A plain `--render chat` needs `NOTCHLING_RENDER_FORCE_FRAMES=1` there. Forced frames cost more, so compare counts, not `ms/frame`, between forced and unforced runs. A busy Mac adds a stray draw of every part now and then: repeat a run before believing a single 1.
- `notchling-app --data-root crates/app/fixtures/chat --open-chat` runs the app over a fixture; a fixture root and every render read files only, never a daemon. Over the real folders the app starts the `notchling` beside it and turns back on every switch the user had on (`switches/restart.rs`), so a dev app there acts on real sessions: the maintainer's call. Its menu bar item often hides behind the notch; `--open-chat` opens Chat.
- Stop a dev app with `pkill -x notchling-app`. `-f` matches whole command lines, so it also kills a shell whose command names the app, such as one running the daemon with `NOTCHLING_APP_TIER_PATHS=…/notchling-app`.
- `tools/bundle-next.sh` builds `build/next/Notchling.app` (signed ad hoc, bundle id `local.notchling.next`). Never pass `--install`: it quits the running app and replaces `/Applications/Notchling.app`. Only the maintainer installs.

The `notchling` binary (`crates/notchlingd`) is the daemon (`notchling daemon`), its clients (`notchling status`, `notchling sessions [--json]`, `pages`, `page`, `secrets`, `secret`, `secret-request`, `delegate`, `delegate-models`; all but `secret` and `secret-request` take `--json` for machine-readable output) and `notchling service install|uninstall|print [--dir <folder>]`. In dev, run the daemon over a copy of a fixture, never over your real folders: `cp -R crates/app/fixtures/notch /tmp/nl-root`, then `NOTCHLING_DATA_ROOT=/tmp/nl-root` for the daemon and the clients alike (socket, lock and `audit.jsonl` land in `/tmp/nl-root/notchling`). `--socket <path>` moves the socket and puts its lock and the audit log beside it; over the real folders the daemon still locks `notchlingd.lock` in the data folder, one daemon per data folder. `NOTCHLING_APP_TIER_PATHS` (read once at daemon start, and only by a daemon run from a cargo target folder) lists executables that get the app tier; `ensure_daemon` never passes it on. `service install` only writes the file and prints the `launchctl`/`systemctl`/`schtasks` command; don't run that command, and in tests always pass `--dir`.

`notchling hook [--socket <path>]` is Claude Code's hook under the daemon: it reads the hook JSON on stdin, asks the daemon (`hook.request`) and prints what the Swift `--hook` prints, or nothing (a pass, exit 0) when there's no daemon, no app attached, a socket error, a `claude -p` session, its 290 s deadline, an event over the local API's 1 MiB line (a Write of a big file: Claude Code then asks in its own terminal; the cap stays 1 MiB for every op, `hook.request` included), the daemon refusing it (its process must descend from the Claude Code process whose `sessions/<pid>.json` holds the event's session, read from the socket's peer, never from arguments), or the daemon's `acting` switch off. Acting is off at every daemon start, whatever any file says, until the app sends `settings.set_acting` (decision 0007's note of 2026-11-08); since the handover (decision 0011's note of 2026-11-11) the app sends it by itself when the user had it on. Only the app's Install Hook (Welcome, through `install.apply`) writes the hook into `~/.claude/settings.json`: never add it yourself (E13, M6). The code that can (`notchling_engine::install`, behind the daemon's `install` switch, which is off at every start: `install.plan` reads only, `install.apply` and `install.remove` answer the dry run) is tested against temp copies only; its roots are parameters, so a test never reaches the real `~/.claude`, `~/.codex` or `~/.gemini`. Try it with a fixture event: `NOTCHLING_DATA_ROOT=/tmp/nl-root target/debug/notchling hook < crates/notchlingd/tests/fixtures/hook/permission-request.json`. The Artifact tool's events (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`) never reach the daemon: `notchling hook` answers them itself (`notchlingd/src/hook_pages.rs`, over `engine::pages::hook`) from `<data dir>/pages`, the folder `notchling pages` and the pages window read, so saving a page needs no daemon, app or `acting` switch (the Swift hook handled them "before the app-running check" too). A publish is recorded under flock, a whole-page read of a saved link is denied with the local copy's path, and a failed read gets it as context; a first publish is saved under the lane's account (`CLAUDE_CONFIG_DIR` and `lanes.json`) or the main login (`~/.claude.json`). Any error, a panic or 8 s is a pass. Publishing to a page another saved account owns (`pages::owner`) is not wired: it has no login source or network yet, and the `accounts` switch lives only in the daemon, which a hook process can't ask without a new op.

## Architecture in one pass

- **Processes.** `notchling-app` (app tier) and `notchling daemon` talk over the local API; the hook and the command line are agent-tier clients. The app starts the daemon from the `notchling` beside it, or the `dev.notchling.daemon` LaunchAgent that `notchling service` writes does. Phones reach the daemon's bridge (TLS on 47821, the tunnel origin on loopback 47822). `notchling-ptyhost` holds terminal ptys under the `local.agentconsole.hostd` LaunchAgent, which nothing here installs. The daemon owns everything that acts or lives long; the app reads transcripts itself, read-only, for speed (decision 0004).
- **Local API.** `<data dir>/notchlingd.sock` (0600), one JSON object per line, `hello` first. The tier comes from the peer's executable (macOS: its audit token, read at accept, at `hello` and per app-tier request, against the exec race; Linux: `/proc/<pid>/exe`, best effort; Windows' pipe is a stub). Op and topic names are constants in `wire.rs` (`ops`, `topics`); each op has an `OpSpec`: `AGENT`, `APP`, or `APPROVAL` (fails closed with no app attached). Refusals and app-tier calls go to `audit.jsonl` (rotates at 5 MB). Calls wait `CALL_TIMEOUT` (5 s) and check who serves the socket (`server_trusted`) first; 64 clients, 4 kept for the app.
- **Daemon.** `daemon.rs` locks, binds, then reads the session list (`engine::sessions::Monitor` on `platform::watch` batches under `jobs/` and `sessions/`, and every 5 s) for `sessions.list` and `sessions.changed`. `daemon_wiring.rs` builds every area per run: acting (`acting_ops.rs`, `control_ops.rs`, the terminal in `attach.rs`, the hook in `hook_ops.rs`), `codex_ops.rs`, `agy_ops.rs`, `bridge_ops.rs`, `pages_ops.rs`, and `OpGroup`s (`op_group.rs`) for switches, accounts, install, providers, limits and cost, catalog and vault. Command-line modes: `clients.rs`, `pages_cli.rs`, `vault_cli.rs`, `delegate_cli.rs`, `hook.rs`, `service.rs`.
- **Switches.** Five, off at every daemon start whatever any file says, since an agent with a shell can write any file: `acting` (`settings.set_acting`: replies, answers, session control, Codex and Antigravity turns, the hook), the bridge (`bridge.set`: no port bound until on), and `accounts`, `vault`, `install` (`settings.set_switch`, `switches.rs`). Only an app-tier call in that run turns one on. An area checks its `SwitchFlag` before touching anything and answers `forbidden` with the off message. Under a fixture root every login effect is a fake or refused.
- **Engine.** Pure where it can be: planners return a plan; effects sit behind traits with fakes (`Launcher`, pty, Keychain, HTTP, spawners). `transcript` (Claude Code, Codex rollouts, ACP, the phone's chat view, subagents, shells; `locate` finds a file and its `/clear` successor), `sessions`, `terminal` (emulator, `ask_dialog`, `permission_dialog`, keys, `pty/`), `reply` (keys and timings pinned to the Swift app by `pin_tests.rs`), `control` (new, stop, remove, move, Move All, Trust Folder, slash commands), `tools` (`codex`, `agy` over `acp`), `delegate`, `bridge` (router, hub, `net/`) and `viz`, `pages`, `search` (`fts.rs`: `daemon/search.db`, FTS5, bm25), `accounts`, `providers`, `lanes`, `limits`, `cost`, `catalog` (`data/catalog.json` and live lists, decision 0016), `vault`, `machines`, `install`, `settings` (`keys.rs` lists every key), `store` (`notchling.db`) and `docfile` (decision 0014).
- **App.** Each area keeps a pure model, tested everywhere, beside GPUI views under `#[cfg(target_os = "macos")]` (`view*.rs`, `window.rs`) and `src/mac/` (shell, tray, Dock, hot key, `--render`). Areas: `chat/` (`chat/view/tool/`: one adapter per tool behind `ChatTool`, decision 0015), `notch/`, `search/` (⌘⇧P), `pages/` (`wry` windows and Chat's page panel, decision 0013), `accounts/`, `vault/`, `phone/` (pairing over `bridge.*`), `sheets/` (New Session, Settings, Second Opinion), `tools/` (Codex, Antigravity), `welcome/` (first run, About, updates, Install Hook), `switches/`, `machines/` (`notchling-machines`: no ssh or `gh` without `--live`, no vault value without `--vault`). `session_source.rs` gives Chat and the notch their rows from a background thread; UI threads never touch the socket. `actions.rs` sends ops; session calls wait `SESSION_CALL_TIMEOUT` (60 s). Daemon calls block: make them off the UI thread.
- **Chat's parts** (decision 0018, `chat/view/`). `ChatView` (`mod.rs`) is the controller: sessions, the selected row, drafts, tools and panels. `root.rs` is its draw (the header, panels, reply box, overlays) and `load.rs` its loads. Three parts are cached views drawn from their own model, and each draws only when that model differs from the last (`PartialEq`): the Sidebar and the Details Panel are `ModelPart`s (`pane.rs`) over `SidebarModel` (`chat/sidebar.rs`) and `DetailsModel` (`inspector.rs`), and the conversation is `ConversationView` (`conversation_view.rs`) over a `ConversationInput` and its own state (scroll and follow, open groups, hover, Copy's check, selection, the Markdown cache). A draw function reads its model, never `ChatView`; what a model can't see (the appearance, a fold) is redrawn on purpose through `redraw_parts`/`redraw_details`/`redraw_conversation`. `redraw_chrome` redraws only the window's outer parts (typing, terminal and simulator frames, the notch's state); `cx.notify()` on `ChatView` makes each part compute its model again. The conversation's rows are a GPUI list (`conversation_list.rs`, `ListRows`): a load's `chat::log::Change` becomes splices of the rows it touched, so the rest keep their measured heights, and a draw builds only the rows on screen plus 600 pt of overdraw. The engine hands out `Arc<Conversation>` (`transcript::conversation::read_shared`, `read` is an owned copy; an unchanged file is the same `Arc`), the loader diffs it with the last one off the main thread (`log::diff`: `Same`, `Items` splices, or `Reset` when ids don't line up) and the view only checks the pointer the change starts from. The open question is `Conversation::pending_question`, from the same read. Selection is anchored to the model: an end names a row id, a block and a byte (`row_select.rs`), `chat::blocks::plain_blocks` gives a row's selectable texts, `row_blocks.rs` feeds Copy from them, so rows not drawn are copied too. `view/select.rs` (draw-order notes) now serves only the file panel. Copy (⌘C, the Edit menu, the right-click menu `copy_menu.rs`) is the `Copy` action handled on `ChatView`'s root (`copy.rs`): the conversation's selection, else the file panel's, else the reply box's. GPUI sends a key or an action to the focused element's ancestors only, and with nothing focused (the reply box is off for a session the app can't type into, or was never clicked) that path is the window's outermost node, so a handler on the root never ran and nothing could be copied; `copy::Keys` is a focus handle on a zero-size child that takes the keyboard when nothing has it (the root can't track focus itself: an element that tracks focus takes it on every click inside it, pulling it out of the reply box). `NOTCHLING_RENDER_CHECK_COPY=key|action|menu` with `tests/render_copy.rs` checks the whole path in a real window. The kit's overlay scroll bar follows a div or a `ListState` (`kit/src/ui/scrollbar.rs`, `scrollbar_track.rs`, `scrollable_list`). Spinners in a part are slots a `SpinLayer` paints (`kit/src/ui/spin_layer.rs`).
- **Native spinners** (`kit/src/ui/spin_native.rs`, `app/src/mac/native_spin.rs`, `native_spin_geometry.rs`, `chat/view/native_spin.rs`). A working session's Activity Line spinner is a Core Animation ring, so it costs the window no frames (idle with a working session: about 100 root draws in 10 s became 10 to 11; `docs/perf/chat-state-split-bench.md`, "Native spinner spike").
  - Where it lives: `SpinLayer::native(hosts, sink, gate)` takes a `SpinSink` (the kit's trait; `mac::native_spin::CaSpinners` is the macOS one) and, each time the window draws, hands it the slots every host recorded. `CaSpinners` keeps a `CAShapeLayer` per slot as a sublayer of the window view's layer, above GPUI's Metal layer, inside a container clipped to the slot's mask (a mask on the ring would turn with it). `Parts::new` (`pane.rs`) builds it.
  - Keying: a slot's `key` is a hash of its element's path (`spin_layer::key_of`), mixed with its host's place (`mix_key`). A layer whose key is still there only moves and keeps its animation; `spin_native::diff` decides added, changed, removed (a key laid out twice in a frame counts once, by its last place, since a list row's autoscroll lays out twice). All native spinners start at `spin_phase()`, so they turn together.
  - Coordinates: slots are window points, origin top-left; the window view is not flipped, so the layer's y runs up (`native_spin_geometry::layer_y`/`placed`). Geometry is pure and tested; the AppKit calls are main thread only.
  - Overlay rule: layers sit above everything GPUI draws, so a sheet, a menu, a picker, the usage ring's card, the drop hint or the ? part names would be under them. `ChatView::render` clears `parts.native` (the `SpinGate`) from `native_spin::covered(Covers {..})` and the layer then paints and turns the slots itself, as before, removing the Core Animation layers once. A new thing drawn over the window needs a field in `Covers` and a line in `root.rs`.
  - Still on the timer (GPUI, ten frames a second): the reply box's sending spinner and every spinner not in a Chat part or the Activity Line (`ROOT_SPINNERS`: only `spin-activity` is taken at the root), the sheets and other windows, any spinner while an overlay covers the window, and the notch. A host takes a spinner by its element name: a new spinner that should be native needs its name in `ROOT_SPINNERS` or a part host; a short wait needs nothing.
  - The clock: the Activity Line's "(26s)" used to be redrawn by the spinner's frames. Now `ChatView::activity_drawn` notes when the composer drew the line and the tick (`load.rs`) calls `redraw_chrome` once a second (`activity::clock_due`). Anything else that rode on those frames needs its own redraw.
  - Off switch: `NOTCHLING_NATIVE_SPINNER=0` in the environment draws them the old way.
  - Testing locked: a locked screen sends no display-link frames, so count what the app asks for, not a rate: `bench_idle_working_requests_few_frames` asserts `root` (5 to 16 in 10 s: a loaded Mac drops some of the clock's once-a-second draws) and `native_rings >= 1` (`mac::native_spin::probe`, in the `bench-json:` line). `NOTCHLING_RENDER_NATIVE_PROBE=1` on `--render chat` prints each ring's place and rotation three times 150 ms apart. Pixels, and the ring under overlays, are checked by hand.
- **Kit.** Views use its tokens (`Ink`, `TypeRole`, `metric`, `Motion`, `Icon`), never a raw color or size. Icons are vendored Lucide SVGs (ISC), never SF Symbols, which may ship only on Apple's systems. Tag views with `.part("Name", …)` for the ? button; grep the name the user gives.
- **Render map.** While ? is on, Chat draws outlines and badges (`chat/view/render_map.rs`, pure half `kit/src/render_map.rs`): one color per region that draws alone (Sidebar, conversation, Details Panel), one shared color around what the root draws every frame (header, reply box, Tasks bar, terminal, simulator and page panels). A badge shows the region's draws since ? came on (the conversation's also the rows its last draw built) and flashes for 300 ms when it drew.
- The root draws the map, over the parts, never inside one (a badge in a cached part would draw it and falsify its count). The badge is a canvas that reads the `pane.rs` counters as it paints; one timer redraws only the chrome to clear a flash, and that draw is not counted. A new window-drawn panel gets `.window_region(a, cx)` before its part tag.
- `NOTCHLING_RENDER_PARTS=1` shows the map in `--render chat`; `NOTCHLING_RENDER_MAP=0` keeps the names but not the map, to compare. `bench_chat.rs` holds that the map changes no part's count.
- **Data.** `<data>` is `~/Library/Application Support/Notchling`. `notchling delegate` called from a Claude Code session (`CLAUDE_CODE_SESSION_ID`) also writes `<data>/delegations/<tool>-<session>.json` (`engine::delegate::record`; the command is its own short-lived writer, so the folder is neither the daemon's nor the app's): Chat lists those jobs as the session's subagents (`chat/delegated.rs`; matched by transcript id and the ones a `/clear` ended, `Subagent.origin`) and leaves their Codex/Antigravity rows out of the Sidebar and the notch (Search still finds them; opening one there uses it, which brings the row back). Before `agy acp` starts, a folder Claude Code trusts (`~/.claude.json` `hasTrustDialogAccepted`, itself or a parent) is added to agy's `trustedWorkspaces` (`delegate::agy_trust`). `notchling.db` holds settings, drafts, `docs` rows and the `inbox` table; the daemon's files go under `<data>/daemon/`, the app's under `<data>/app/`, apart from the Swift app's (`lanes.json`, `pages.json`, `vault.json` stay JSON, decision 0014). The bridge keeps `~/Library/Application Support/AgentConsole/` so paired phones survive. Panics go to `<data>/logs/crash.log`.
- **Phone inbox.** `inbox.list` and `inbox.answer` (`bridge/router_inbox.rs`) go through `BridgeBackend::inbox_items`/`inbox_answer` to `Sources` (`bridge/live.rs`), which the daemon implements on `InboxOps::items` and `InboxOps::decide(.., "phone")` (`bridge_backend.rs`): the same first-answer-wins and responder check as the app's, `open` is refused (the secret form opens on the Mac only), and `inbox.answer` is refused while acting is off (`ACTING_OFF`, as `session.image.*`). Allow Once and Always Allow on a `secret_approval` are taken from a phone (decision 0007's note of 2026-11-13); `InboxOps::decide` takes an allow on one only from `mac` or `phone`, under the inbox lock. Every phone `inbox.answer` is audited in `remote-log.jsonl`: `inbox.answer:<action>` when taken, `inbox.answer:refused:<reason>` (`acting_off`, `invalid`, `open`, `not_found`, `not_taken`, ...) when not, never the item id (it holds the vault's ticket). Pushes are not events from `InboxOps`: `Hub::tick` diffs `inbox_items` per connection that subscribed with `inbox: true` (`Subscription::known_inbox`), so the bridge switch and an old phone are untouched.
- **Inbox** (`engine/src/inbox/`, `notchlingd/src/inbox_ops.rs`, `vault_inbox.rs`, `app/src/inbox/`). What needs you, in one list: a vault approval or secret request (`vault_inbox.rs`) and a limit notice (the limits announcer). `Book` is the pure list (200 open items; done ones kept 7 days from when they closed, the newest 300 at most; text cut on raise and on load); `InboxOps` owns it and serves `inbox.list`, `inbox.answer`, `inbox.seen` and the `inbox` topic (`inbox.changed`, `inbox.removed`), to the app tier from the app itself (`ClientKind::App`, as `vault.approval.answer`).
  - Ids are fresh per event (`vault-approval:<ticket>`, `vault-request:<ticket>`, `limit:<id>`): raising an id that is no longer open changes nothing, so a reused id would lose its responder.
  - First answer wins. `inbox.answer` asks the item's `Responder` (the vault's waiter) under the inbox lock, and the `Responder` returns a bool; the book records the answer only on true, else the reply is `answered: false` with the item's state. The inbox never shows a decision that wasn't made. A responder only sets a slot, never blocks.
  - The producer owns its expiry. `InboxOps::tick` never expires an item that still has a responder (a sleep or a clock step would have shown a live wait as Expired and lost its answer); the producer closes it with `resolve` when its wait ends, with `answered_by` `mac` when the Mac's window answered. Items with no responder (limit notices, items loaded after a restart) expire and prune by the clock. The vault's producer holds a `Raised` (`vault_inbox.rs`) for the item it raised: closing it resolves the item, and if the op thread unwinds first its drop withdraws it. A cancel in the Mac's form resolves the request as Answered with Cancel by `mac` ("Cancelled · Mac", as a cancel from the inbox); Withdrawn is for an app gone or a switch off.
  - The vault's waits (`vault_wait.rs`, `Waiters`): ids are 128 random bits from the OS (no randomness, no wait); at most `max` wait at once; each keeps the event that announced it for `vault.pending`; a wait ends with a no at its deadline, when `still` says stop (the app left, the vault went off) or when `drain` drops every channel (the daemon stops), and an answer taken as it ends is still returned.
  - The book loads from `notchling.db` in `InboxOps::load`, which the daemon calls between `Server::bind` and `server.spawn()` (`Wired::load`), so the first `inbox.list` already sees it; `Wired::start` then starts the tick. The `Book` keeps the saved rows in insertion order (rowid), so prune's tie-break keeps the newer item after a restart too. After a restart an item that was Open loads as Withdrawn (its waiter died with the daemon) and is saved that way, so it ages out like any done item.
  - One writer thread: changes are sent to it under the Book lock, so persisting and publishing follow Book order and no lock is held across SQLite. `flush()` waits for it (tests, close). A save error is logged, never fails an op.
  - The phone's `inbox.answer` goes through the bridge backend to `InboxOps::decide` (`answered_by` is `phone`), and needs the bridge on and `acting` on. List and pushes don't. The phone never opens the secret form: Open Form shows as "Open on Mac"; only the Mac's form takes a secret. The phone may allow a secret: Allow Once, Always Allow, Deny and Cancel work from both, with the vault switch on too (a drained wait takes no answer). Pairing (`devices.json`) is a file an agent with a shell can write, so a forged device could answer: a risk the maintainer accepted until pairing has an anchor an agent can't write.
  - The app follows the topic in `inbox/feed.rs` (calls off the UI thread). System notifications fire only from an `inbox.changed` event, once per id for the app's life (a reconnect or reseed never repeats one), and go through one worker thread (`system::Detached`) so banners keep order. The notch shows the unread count as a badge when open, not when collapsed. A done row says what was decided and where (`Row::result`: "Allowed Once · Phone", "Denied · Mac", "Expired"), after its detail.
- **Where new things go.** An op: its name in `crates/local-api/src/wire.rs`, served from `crates/notchlingd/src/<area>_ops.rs` (an `OpGroup` added with `Ops::with_group` in `daemon_wiring.rs`) with the narrowest `OpSpec`, behind its switch, tested in `<area>_ops_tests.rs`, read in the app's `<area>/wire.rs`. Work that can outlast 5 s answers at once and sends its result as an event (`accounts.result`, `accounts.done`). The local API and the phone protocol change additively only. A view: a pure model, a GPUI view, a `ViewSpec` in its area's `renders.rs` and an arm in `mac/views.rs`. An engine part: pure planners, effects behind a trait. Skills: `port-swift-part`, `add-provider`, `fix-bug-reproduction-first`.

## Things that bit before

- GPUI 0.2.2's text element truncated its runs in place, so a resize measured an elided label again and sliced a string mid-character: a crash. `vendor/gpui` fixes it; its `NOTCHLING.md` says when to drop the patch.
- GPUI's `truncate()` never draws the ellipsis (`nowrap` keeps the first measurement). Use the kit's `elide()`.
- GPUI swaps a state's whole text style on hover and press, so a hover that set only a color made the words grow. Give each state the full style (kit buttons do).
- GPUI sets the arrow cursor after every draw when nothing asks. Clickable elements need `.cursor_pointer()` (kit buttons have it); resize cursors come from `kit::ui::resize_edges`.
- GPUI resigns a window that became key while the app wasn't active with the window's lock held: the app hung. Call `cx.activate(true)` before opening a window from the menu bar.
- Every pixel of a GPUI window is Metal drawables plus MSAA textures: a screen-wide notch canvas cost 93 MB. `notch::layout::canvas_size` sizes it to the largest shape.
- Polling lstat'ed every file each second, a third of a core on a real `~/.claude` (53k files). macOS uses FSEvents (`platform::watch`; `examples/watch_cpu.rs` measures). Its debounce restarts on every change, so steady writes flush only through `max_latency`; Chat coalesces reloads (`chat::reload::ReloadGate`) and watches a folder reached twice through lane symlinks once.
- The daemon has no main run loop, so `NSWorkspace`'s running apps go stale there. `platform::apps::is_running` reads the process table; a login switch must never write while its app runs.
- Reading the session list before binding made the socket miss `ensure_daemon`'s 3 s wait, which killed the daemon, and the app read files for good. Now: locks, bind, read; `sessions.list` waits up to 4 s, under the client's 5 s.
- A reply can take over 5 s, and an error shown while it still arrived made the user send it twice: session calls wait 60 s. Accounts ops waiting on Keychain or network answer within 4.5 s and finish by event.
- One big Antigravity permission diff passed the 1 MiB line and failed `prompts.list` for every prompt. Cut payloads to fit: diffs to 400 lines or 128 KB, `agy.conversation` to the newest 512 KB with `truncated`.
- A `claude` exiting with output nobody read waits for its tty to drain, and SIGKILL can't end that: waiting with the pty master open hung `folder.trust`. Hang up and close the master first. A child that stops reading blocks writes forever, so `Terminal::write` gives up after 10 s.
- Locks held across blocking work hung things: ACP's writer lock blocked killing a stuck agy, ptyhost's delivery lock let one slow client stall all, the vault's cache lock waited on Keychain, a switch listener on a Keychain prompt held up `settings.set_switch` (now 500 ms at most). Never hold a lock across I/O, a pipe or a Keychain call.
- `security -i` reads 4 KB lines, and Claude Code's login item also holds MCP logins, so as hex it passed that and every switch was refused. It goes as quoted text on stdin, never argv; long saved logins split over several items.
- The daemon once read `acting` from `notchlingd-settings.json`, so a file write and a restart turned it on. No file turns a switch on in the daemon; that one saying on is audit-logged (`file_said_on_ignored`).
- Over a fixture root a Codex turn inherited the daemon's `CODEX_HOME` and wrote to the real `~/.codex`. Children get the folder the daemon reads; a fixture root runs only `<root>/.local/bin/codex`.
- Chat with a working session took a core: the kit spinner's GPUI animation asked for a frame every vsync, and each frame laid out every message (52 ms a frame on a 60-turn conversation, 19 fps). A spinner is now a small view of its own ticking ten times a second (`kit::ui::icons`), the conversation is a cached view (`chat/view/conversation_view.rs`, below), and a change shown only outside it redraws through `ChatView::redraw_chrome`, not `cx.notify()`, which draws the conversation again. GPUI redraws a notified view's ancestors, never its siblings, and a `window.refresh()` drops every cache. `NOTCHLING_RENDER_BENCH=<s>` on `--render` prints frames, conversation draws and CPU.
- Still about 11 ms a frame after that, with ~40 sidebar rows and the Details Panel open: the root view draws every frame (GPUI never caches a window's root), so everything not in a cached view was laid out at the spinners' ten frames a second, and a spinner inside a cached view draws that view again (its ancestors). The Sidebar and the Details Panel are cached parts too (`chat/view/pane.rs`), and a spinner laid out in a part leaves a slot that one `SpinLayer` after the parts paints and turns (`kit::ui::spin_layer`; a part is a host through `host_spinners`, placed with `spin_host`). A cached view's box comes only from the style given to `cached()`: it never measures its content, so a part needs a size from outside (a width, `flex_1`). On a notch `--render`, the bench moves the pet as the live tick does.
- Chat's state was one entity every part observed (decision 0018, measured in `docs/perf/chat-state-split-bench.md`). Typing called `cx.notify()` and laid out the whole conversation per keystroke (44 ms a frame); a terminal or simulator frame did the same up to 30 times a second; scrolling and hovering did it on every wheel step, since GPUI notifies the view an element is in; each reload drew the Sidebar and the Details Panel. Rules that came out of it:
  - A cached part draws only when its own model or input changes. A new field a part shows goes into its model (`SidebarModel`, `DetailsModel`, `ConversationInput`); a draw function never reads `ChatView`.
  - Anything computed in `ChatView::render` that feeds the conversation's input must reach it through `refresh_conversation`, or the column shows the old value until something else draws it.
  - Never `window.refresh()` in a handler: it drops every view cache in the window and lays out everything again. Notify the view captured at paint (selection and the scroll bar do), or use `redraw_chrome` (`redraw_sidebar`, `redraw_details`, `redraw_conversation` for one part). One is left: the Details Panel's expand-all-subagents fold (`inspector.rs`).
  - Never read the conversation entity (or any part's) from code running inside an update of it or of `ChatView`: GPUI panics on the double borrow. A part's `refresh` takes `&ChatView` for that reason; pass what you need in.
  - Count-based bench tests hold all this (`bench_chat.rs`: a terminal frame, typing or a menu draws no part; a scroll, hover or append builds only rows on screen). Run them after touching what a part observes.
- Scrolling up from the end did nothing for the first ~0.8 s: `ListRows::sync` runs in every draw of the conversation and put the list back at its end whenever it was within `follow::TOLERANCE` (24 pt) of it, so each 1 to 5 pt trackpad step was undone by the next draw until one step alone passed the tolerance. A sync goes to the end only when something under a reader at the end changed, or when a send or a pick forces it (`goes_to_end`). A draw that changes nothing must never move the scroll position. `bench_scroll`'s `scroll-start` holds it (47 stalled steps before, 0 after). On real sessions a draw while scrolling costs 1 to 5 ms of the main thread; only a row of about 25,000 characters of Markdown (40 sections with tables and code) costs 17 to 20 ms in every draw it is on screen, because GPUI's list lays a visible row out whole each frame (`layout_as_root` is 15 of those ms), and once when it first enters the overdraw. Recent real replies are under 7,000 characters; split a row into blocks if that ever matters.
- GPUI's `list` (the conversation, decision 0018; probe `chat/view/list_probe.rs`, `list_probe_run.rs`, notes in the bench doc's list-spike section) has facts that are not in its docs:
  - Use `ListAlignment::Bottom` and `ListSizingBehavior::Auto` with a sized style. The default `Infer` lays visible rows out twice (4 to 5 times the `render_item` calls).
  - A row nothing has laid out has no height, so scroll extents and the bar's thumb are approximate, and `scroll_by` from the end can't jump past the rows measured so far. Decide "at the bottom" from the list's own state (`logical_scroll_top().item_ix == item_count()`, `Scroll::at_bottom`), never from sums of pixels.
  - A list that follows the bottom has `logical_scroll_top() == None`, and `bounds_for_item` is `None` for every row then. Read a row's place from what it painted.
  - A splice of the row at the scroll top resets its offset: save `logical_scroll_top()`, splice, `scroll_to(saved)` (`ListRows::remeasure`). A splice above the first visible row needs nothing. A width change measures every row again by itself.
  - A list at its end counts as scrolled a viewport past the last position: a `scroll_by` smaller than that leaves it following. The bar's own offset (`set_offset_from_scrollbar`) moves it from where it stands; drag-select's autoscroll uses that.
  - A row that asks for autoscroll makes the list prepaint twice, so a spinner slot pushed in a list row is counted twice (probe gate G6 fails). A list row draws a plain spinner view or none: a running step shows none, the live line below the list has the spinner.
  - A `canvas` placed to record bounds needs `.absolute().size_full().top_0().left_0()`, or GPUI puts it after its siblings and the bounds are wrong.
- The notch's 2 s poll and Chat's reloads read up to 30 Codex rollouts each time: each one's 256 KB tail (`turn_open`) and, while it had no title, up to 3 MB of its head (`meta`), nearly always unchanged. Both keep their answer until the file's size or time changes (`transcript/codex/stamped.rs`).
- `&id[..8]` panics inside a multi-byte character, and ids from files hold anything. Cut by `chars()`.
- Base64 images filled the 4 MB tail read and pushed a Codex session's first prompt out. Lines over 100 KB don't count toward it.
- A `dequeue` line doesn't say which queued entry it took (Claude Code 2.1.322 took a notification before older ones); the user line after it corrects the guess (`transcript/conversation/queue.rs`).
- A second `agy acp` on a session a delegation holds replays only part, and a reply through it stops the other's work. The daemon finds holders with `lsof` on the brain folder and reads the log instead (`elsewhere::from_lines`: your messages, thinking, tool calls with their results and replies; its item ids come from the line's place in the log, since `step_index` restarts with the session; Chat shows it working from the reply's `working`, and Stop stays off, since `agy.cancel` can't reach another `agy`).
- `write_private` follows symlinks so a lane's shared files stay shared; for a file Notchling owns use `write_private_no_follow`, which refuses a planted link.
- `Settings::set` refuses a key missing from `settings/keys.rs` ("unknown setting chatUsedSessions"). Add the key, or `set_unchecked` for the app's own.
- An inbox item raised again under an id that had closed was dropped with its responder, so the waiter never heard the answer. Every event raises a fresh id. A phone and the Mac answering together showed whichever came second: the answer is recorded only when the waiter takes it (`Responder` returns a bool).
- A fixture's mtime is the checkout's, so anything shown by file age (Codex rows) differs between machines. macOS caps socket paths at 104 bytes: keep test sockets in short `/tmp` folders. A Unix-only helper or test breaks the Windows leg without `#[cfg(unix)]`.
