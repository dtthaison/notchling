# Data and logs

Where Notchling keeps its data, every log it writes, and the log event registry ([log-kinds.md](../log-kinds.md) lists the kinds).

Part of the Rust app's notes, moved from `crates/AGENTS.md`; the index is in the root `AGENTS.md`. Keep it true: change the note with the code, and add what bites you under Things that bit before.

- **Data.** `<data>` is `~/Library/Application Support/Notchling`. `notchling delegate` called from a Claude Code session (`CLAUDE_CODE_SESSION_ID`) also writes `<data>/delegations/<tool>-<session>.json` (`engine::delegate::record`; the command is its own short-lived writer, so the folder is neither the daemon's nor the app's): Chat lists those jobs as the session's subagents (`chat/delegated.rs`, now wrappers over `engine::contract::flows::delegate_jobs`, which the daemon's phone list uses to leave the jobs' rows out too; matched by transcript id and the ones a `/clear` ended, `Subagent.origin`) and leaves their Codex/Antigravity rows out of the Sidebar and the notch (Search still finds them; opening one there uses it, which brings the row back). Before `agy acp` starts, a folder Claude Code trusts (`~/.claude.json` `hasTrustDialogAccepted`, itself or a parent) is added to agy's `trustedWorkspaces` (`delegate::agy_trust`). Codex children are found by `<data>/daemon/codex-children.db` (the daemon's index of rollout heads, keyed by path, size and mtime; `codex.children` is an `APP_QUIET` op), and without a daemon by reading at most two day folders (`DayFolders`). `notchling.db` holds settings, drafts, `docs` rows, the `inbox` table and the `outbox` table (schema version 4, class Node: a node's mailbox stays on it and never reaches the cluster's shared data; the daemon is its only reader and writer, the app sees rows through `outbox.*` and the `outbox` topic; a row is deleted when it is Sent, Removed, Dropped, Discarded or its session is removed, and nothing expires by age; an older daemon opening a version-4 file ignores the table) and the `asks` table (schema version 5, class Node: a node's questions stay on it and reach the cluster only as an Inbox item; the daemon is its only reader and writer, the app sees rows through `ask.*` and the `asks` topic; an open or answered row lives until it closes, a closed one is deleted 24 hours after it closed with its answer text, and nothing open expires by age; an older daemon opening a version-5 file ignores the table); the daemon's files go under `<data>/daemon/`, the app's under `<data>/app/`, apart from the Swift app's (`lanes.json`, `pages.json`, `vault.json` stay JSON, decision 0014). The bridge keeps `~/Library/Application Support/AgentConsole/` so paired phones survive. Panics go to `<data>/logs/crash.log`.
  - `<data>/daemon/search.db`: the text index (FTS5, 0600). It is only an index: rebuilt when `fts.rs::SCHEMA` changes or the file is damaged.
  - `<data>/daemon/vectors.db`: the meaning index, made only while Semantic Search is on and kept when it is turned off; a damaged file is set aside as `vectors.db.damaged`.
  - `<data>/models/granite-97m-r2/`, `<data>/models/static-mrl/`: the downloaded models (private folders); a `.part` file is an unfinished download kept for resume.
  - `<data>/daemon/exited-sessions.json`: the sessions that exited in the last 24 hours, so a restart keeps their rows. It is rewritten only when the set of ids changes. A session that ends while the daemon is down is not recorded.
- **Logs.** `<data>` below is `~/Library/Application Support/Notchling`.
  - `<data>/audit/YYYY-MM.jsonl`: the Audit, one sealed line per event, written only by the daemon's `AuditSink` (`notchlingd/src/log_audit.rs`). A month's file is kept a year by default and the folder is capped at 500 MB (`log_retention.rs`). `audit/legacy/` holds the old `audit.jsonl` and `.1`, moved at the first start and never rewritten. The sealing key is a Keychain item (`dev.notchling.audit`, `engine/src/logs/keys_mac.rs`, behind the `KeyStore` trait: tests and a fixture root use a file, `daemon/audit-key`, or a fake) and the newest seal is a second item (`dev.notchling.audit.head`).
  - `<data>/daemon/events.db`: the Activity store (`engine::activity::EventsDb`, WAL), the same events with their group and title, read through `activity.list`; rows expire by kind. It can be rebuilt from the months (`rebuild_from_months`).
  - `<data>/daemon/usage.db`: the usage ledger (`engine::cost::ledger`, WAL, owner-only). `calls` holds one row per API call, 30 days: time, tool, session id, agent id, main or helper, agent type, model, effort, the five token counts, whether the transcript split its cache writes, and the cost (`NULL` when the model has no price). `rollups` holds one row per day, tool, role and model, 1 year. `files` holds each transcript's read offset. Ids, counts and model names only: no prompt, command, reply or spawn description reaches it. It is its own incremental pass over the transcripts, beside the cost cache's, and it can be deleted: the next pass rebuilds 30 days of rows.
  - `<data>/notchlingd.log` (+ `.1`): the daemon's stdout and stderr. Opened by `ensure_daemon` (`spawn.rs`) or by the `dev.notchling.daemon` LaunchAgent (`StandardOutPath`/`StandardErrorPath`), never by the daemon itself, so `log_rotate::StderrLog` renames it to `.1` and dup2s a new file onto fds 1 and 2 when the daemon starts and then once a minute when it passes 5 MB. It only touches fds that are that file (same device and inode), so a daemon run in a terminal is left alone.
  - `~/Library/Application Support/AgentConsole/bridge/remote-log.jsonl`: only the phone bridge's fallback (`engine::bridge::net::audit`), written when no daemon event sink is attached; the daemon imports it once into the Activity store. While the daemon runs a phone's change is a `phone.*` event with the device id.
  - `<data>/account-log.json`: the old record of which account was active (the Swift app's format: `at` is seconds since 2001). The daemon no longer writes it: an account switch is an `account.switched` event, and cost reads the file's older rows plus the recorded ones (`cost::account_log::merge`, the daemon's `DbSwitches`).
  - `<data>/logs/crash.log`: the app's panics (`app/src/crash_log.rs`).
  - `<data>/permission-screen.txt`: the last permission screen the daemon could not read, kept to improve the reader.
  - `<data>/reply-screen.txt`: the last reply the daemon could not type (`notchlingd/src/reply_screen.rs`): the job, why, the message's length, what each wait saw and the screen it ended on, with the input box's text masked, so the message is not in it.
  - The Activity page (Settings > Activity) reads the first four through `activity.list` and shows refusals and failures first; it never reads `notchlingd.log` or `crash.log`.
- **Log events** (`crates/events/`, decision XXXX, [the design](../superpowers/specs/2026-11-13-logging-design.md)). What Notchling records is a typed event of a registered kind, never a line of text. Phase 1 is only the registry: nothing depends on the crate and nothing writes an event yet. A kind is declared once with `kinds!` (`src/kinds/<group>.rs`): its title, what it records and why that matters, its lock, sinks, retention and fields. A field's type must implement the sealed `LogField` (`field.rs`), a closed list with no free text (`String`, `&str` and `serde_json::Value` can't), and choices come from `log_choice!`, which adds `other` so a reader never fails on a value it doesn't know. `LINT-LOG-NO-TEXT` holds both, and `LINT-LOG-ONE-WRITER` keeps `eprintln!`, `tracing` and `log` out of every crate but `events` (today's 72 uses are in the lint baseline, which only shrinks). `crates/events/tests/golden/log-kinds.json` and `docs/log-kinds.md` are generated from the registry (`NOTCHLING_UPDATE_GOLDEN=1 cargo test -p notchling-events --test golden`); a change to a kind's fields changes both, and a settings key added to `engine/src/settings/keys.rs` needs its line in `SettingKey` (`tests/settings_keys.rs` fails until it has one). The crate's `AGENTS.md` has what a change could break, by file.

## Things that bit before

- A new ad-hoc-signed build made the Keychain ask about `dev.notchling.audit.head`, and until the user answered `notchling status` said "the daemon isn't running": `AuditSink::new` read the checkpoint on the start path, before `Server::bind`, and a `SecItem` read that needs a prompt blocks its thread until someone clicks. The same call sat in three more places: `write_head` under the audit lock on the bus thread (a flush and every `commit` behind it waited, then failed at 2 s), `create_key` under the lock for `log.chain.start`, and `read_head` in `log.verify`, an agent-tier op. Every `KeyStore` call can block for as long as a person takes: it runs only on `notchling-log-key` and `notchling-log-head` (`notchlingd/src/log_keys.rs`), and nothing waits for them except `log.chain.start`, which asks for it. `uptimeSecs` in `status` counts from `Server::bind`, not from the process start, so a daemon whose start was held by a prompt read 7 s when asked after the prompt was answered; with nothing before the bind that can wait it is now close to the process age. Held by `log_audit_keychain_tests.rs` and `daemon_tests::the_socket_answers_while_the_keychain_is_blocked` over `MemoryKeyStore::hold`, which never touch the real Keychain.
