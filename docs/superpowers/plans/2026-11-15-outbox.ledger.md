## Rulings

**R1** (2026-11-15, orchestrator). A new persisted state `in_queue` (`State::InQueue`; the wire and database word is `in_queue`). Its bubble says "Queued in the session", it has no buttons, and it is not a "needs you" state for the notch. It has no `why`.

**R2** (2026-11-15, orchestrator). Two counts. `count_since(path, message, since_ms) -> Option<Seen>` with `pub struct Seen { pub enqueued: usize, pub taken: usize }`. `enqueued` counts `queue-operation` `enqueue` lines naming the message. `taken` counts typed user lines (`typed_prompt` rules, `<bash-input>` included), `queued_command` attachments naming it, and for a command its `local_command` system line or older `<command-name>` user line. A `dequeue` line carries no text, so it counts only through the user line that follows it. A `popAll` or `remove` line is never a take (spec §15 already refused a `popAll` line as a delivery; `crates/AGENTS.md`: `popAll` is Up pulling the queue back into the box, so the text left the queue without the model reading it). Ruling: the maintainer's brief listed "dequeue/popAll naming it" as taken; `popAll` is treated as leaving the queue untaken, because that is what the Up key does, which is the safe side.

**R3** (2026-11-15, orchestrator). Baselines. The take stores both `seen_before` (the `taken` baseline) and a new column `queued_before INTEGER` (the `enqueued` baseline), both counted since `attempt_ms − 2 s`, through `OutboxStore::set_seen(id, seen: Seen)`. Spec §8 gets the column, and its row in the column table says what it is.

**R4** (2026-11-15, orchestrator). The verdict after Return (spec §10.6). During the 10 s watch and the 30 s look: `taken > seen_before` → Sent (the row is deleted); else `enqueued > queued_before` → `in_queue` (persisted at once; the row stays); else by 30 s → `unsure`/`not_found`. `Verdict { Sent, InQueue, Pending, Unsure }`. The 5 s safe-mode test is unchanged: a new enqueue or taken line within 5 s of Return.

**R5** (2026-11-15, orchestrator). An `in_queue` head blocks the session's later rows (it is the head; B3). The postman keeps watching it (on the tick, re-reading when the transcript's size changes): a new taken line → Sent (delete, `outbox.removed {why: "sent"}`, `session.outbox` `sent`). It goes to `unsure` with a new `Why::Dropped` (`dropped`) when Claude Code's queue no longer holds it and no taken line appeared within `VERIFY_LOOK_MS` (30 s) of first seeing that: `queue_state` no longer lists the entry (a `remove`, a `popAll`, the lost-queue rule after a Claude Code restart, a later `turn_duration` with no take), or the job is stopped, or gone, or its Claude Code process changed (pid or start time from the job files, if they record one; kept in memory only). A pure function in `verdict.rs`, such as `queued_verdict(seen: Option<Seen>, before: Seen, still_listed: bool, gone_since_ms: Option<i64>, now_ms: i64) -> QueuedVerdict { Sent, Stay, Unsure }`; the Task 5 implementer may refine the signature.

**R6** (2026-11-15, orchestrator). `outbox.edit` and `outbox.remove` on an `in_queue` row answer `failed("It's in the session's queue.")` (`Change::Busy`). `outbox.discard` and the 7-day notice's Discard remove it (an explicit action). The 7-day notice counts `in_queue` rows; its Send leaves them unchanged.

**R7** (2026-11-15, orchestrator). Daemon start (`OutboxOps::load`, spec §10.6, §7.4). A `sending` Claude Code row: taken grew → Sent; else enqueued grew → `in_queue`; else (or `None`) → `unsure`/`restart`. An `in_queue` row stays `in_queue` and its postman resumes watching it (R5). A Claude Code restart while the daemon was down is caught only by the queue read (the lost-queue rule) or the job's state, so spec §16 gets the risk: a Claude Code restart that writes nothing leaves the row `in_queue` until the job's process is seen to change while the daemon runs, or the 7-day notice.

**R8** (2026-11-15, orchestrator). Events: `OutboxThen` gains `InQueue` (`in_queue`). The `why` words of `outbox.removed` are unchanged.

**R9** (2026-11-15, orchestrator). `session.reply` (spec §11.3, B16): a row that reaches `in_queue` answers at once with today's queued shape, `{"sent": true, "state": "queued", "waiting": <position>, "outboxId"}`, and the row stays.

**R10** (2026-11-15, orchestrator). Chat (spec §14.1): an `in_queue` row's status line is "Queued in the session" (`chat-outbox-in-queue = Queued in the session`), with no buttons. Since Chat's own `Conversation::queued` also shows that entry from the transcript, Chat draws the Outbox row and hides one matching entry of `Conversation::queued` (the same squeezed text, the first match), so there is one bubble. The §14.1 sentence "an Outbox row that is Sent at its enqueue line becomes one of those" is replaced. `Status` gains `QueuedInSession`.

**R11** (2026-11-15, orchestrator). Codex and Antigravity are unchanged: Sent when the runner starts the turn.

**R12** (2026-11-15, orchestrator). Merged prompts count as taken. A real recording (Claude Code, 2026-11-09): `enqueue "hi"`, `enqueue "hi"`, a `stop_hook_summary`, two `dequeue` lines at the same ms, then ONE user line `"hi\nhi"`. Claude Code joins the texts of the entries it dequeues together with `"\n"`. `count_since`'s `taken` also counts such a merged user line when one of the joined entries (the enqueued texts those dequeues took, in queue order) matches the message, once per matching entry, so a row merged with the person's text is Sent, not May already be in. This overrides the earlier note in spec §10.7 and B22 that a merged line is not a take. Task 3 gets `merged_user_line_counts_as_taken_for_each_entry` with the fixture `crates/engine/tests/fixtures/outbox/merged.jsonl` in that exact shape (synthetic text); Task 18 reuses the shape for `crates/engine/tests/fixtures/queue/merged.jsonl` and does not stop, since a real merge was recorded.

**R13** (2026-11-15, orchestrator). The `in_queue` watch: `still_listed` is true only while `queue_state` lists the entry AND the job is not stopped, not gone (missing for `GONE_AFTER_MS`, 60 s) and its Claude Code process is unchanged. `gone_since_ms` clears only when all of these hold again. The postman keeps a timer armed for `gone_since_ms + VERIFY_LOOK_MS` (`Verifier::next_look_ms`), so the verdict runs at 30 s even with no file change (spec §10.1, §10.2, §10.6; Tasks 5, 10, 11).

**R14** (2026-11-15, orchestrator). Only Claude Code is verified in the transcript. `Courier` gets `fn verifies(&self) -> bool` (Claude true; Codex, Antigravity and `Refuse` false). With a courier that doesn't verify, `After::Verify` means Sent at once (the runner started the turn). At daemon start, Codex and Antigravity `sending` rows still become `unsure`/`restart` (spec §10.6, §10.8; Tasks 10, 11, 12).

**R15** (2026-11-15, orchestrator). A `gone` head is re-checked on the tick every `GONE_RECHECK_MS` (10 s) with a fresh job read; when the session is back it goes to `queued` and the postman wakes, which is what spec §9 promised (spec §9, §10.1, §10.2; Task 10).

**R17** (2026-11-15, orchestrator). `Verifier::seen` returning `None` at the take (no transcript yet, or the 1 MB window already past) stores `Seen::default()` with `set_seen` and the try verifies against it (spec §10.6; Task 10).

**R18** (2026-11-15, orchestrator). `SafeModes` is one `Arc` shared by `ClaudeCourier` (which reads it for `Facts.safe`) and `TranscriptVerifier` (which notes the 5 s test). Task 11's Files list gains `outbox_courier.rs` and the `daemon_wiring.rs` wiring (spec §10.3 item 8).

**R19** (2026-11-15, orchestrator). `OutboxOps` (Task 9) also has `set_note(&self, id: &str, note: Option<String>)`, `note(&self, id: &str) -> Option<String>` (the in-memory `box`/`error` text) and `set_resume(&self, resume: Arc<dyn Fn(&Row) -> Result<(), ApiError> + Send + Sync>)`; `Settled::NeedsUser(Row, Option<String>)` carries the note for `session.reply`'s `box` data (spec §11.3; Tasks 9, 10, 12, 13).

**R20** (2026-11-15, orchestrator). Gate order: spec §10.3's list is reordered to match Task 5 (gone, stopped, dialog, retry back-off, then command, safe mode, queue, go), so a row in back-off keeps `why: retry`. Safe mode is now §10.3 item 8 and Claude Code's queue item 9; references are updated.

**R21** (2026-11-15, orchestrator). An `in_queue` head of a vanished job: the job counts as gone after `GONE_AFTER_MS` (60 s) missing, then the 30 s grace runs; a stopped job or a process change starts the 30 s grace at once. Spec §9's Gone bullet and §10.6 now agree (Task 11 `vanished_job_in_queue_waits_60s_then_30s`).

**R22** (2026-11-15, orchestrator; record only, already done in code in d4c9148f). Task 2's race test checks the real invariant: a take always gets a consistent text and an edit never changes text already taken (an edit that lands first returns the row to `queued`, and the take then takes the edited text). "Exactly one wins" was wrong as written. Task 2's test description, Review Focus item 5 and spec §15 Rule 3 are reworded to match.

**R23** (2026-11-15, orchestrator). Lost-queue rule with a match: a typed prompt with no dequeue batch that names a waiting entry removes that entry and every entry enqueued before it (an idle Claude Code drains its queue in order); entries after it stay. A typed prompt that names nothing clears waiting as before.

**R24** (2026-11-15, orchestrator). A Codex or Antigravity row is Sent only when the turn really went out: Codex's process was spawned with the prompt and its follow thread is running; Antigravity's `session/prompt` request was written to the agent (not merely queued behind a session load). Not dispatched (load failed, acting went off before dispatch, busy, not allowed) → wait, never Sent and never Unsure: `NotAllowed`/acting off waits like Busy (`turn`) with no error note and no back-off; a load error is `retry` with the error as the row's note. Dispatched and then cut by us (acting off interrupting it, a follow-thread spawn failure after the process started) → `unsure` (May already be in; why `restart`), never retry. Antigravity rows held by another `agy` wait as `turn` without being taken every second: `facts` reads a cached `elsewhere` state (refreshed at most every few seconds, outside any lock), so the postman doesn't flip the row to `sending` and back.

**R25** (2026-11-15, orchestrator). `session.reply` answers `{"sent": true}` only for a row removed as sent; a row removed by Remove, Drop, Discard or a session removal while `session.reply` waits answers `failed("The message was removed.")`.

**R26** (2026-11-15, orchestrator). A queue entry that Claude Code's `queue_state` still lists does not hold a row for good: Claude Code's queue is in memory, so an entry lost in a restart is never dequeued or removed, and the Outbox is the only typist that would free it (R23). When the job is Live with an `idle` or `shell` status, no dialog shows, and the turn-over reading (`Facts.turn_over_since_ms`) has stood for `QUEUE_STALE_MS` (10 s), the listed entries are stale and the gate returns `Go { guarded: true }` (the `Guarded` pty refuses with nothing typed if a turn starts) instead of `Wait(queue)`. While the job is working, or the turn ended less than 10 s ago, or there is no reading, it still waits. The courier keeps the turn-over reading whenever the queue lists an entry, not only for a command or safe mode.
