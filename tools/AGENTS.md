# tools: notes for agents

## Why the code is this way

The code carries no comments (see [AGENTS.md](../AGENTS.md)). What a change could break without knowing it, by file:

- `tools/agents/preflight.py::history check`: A title change is a `renamed` timeline event and the REST timeline has no `edited` event, so a body edit is read from GraphQL `lastEditedAt` and `userContentEdits`; comment edit logs are not read on purpose.
- `tools/agents/preflight.py::output contract`: Stdout on exit 0 is one ASCII JSON line, so no line separator can hide in it; `sha256` is title bytes, one LF, body bytes, and a title with a line break is refused with code 2.
- `tools/agents/preflight.py::read order`: The issue is read first and its history after, so an edit in between is seen; the worker must use the printed title and body, never re-read them, and treat comments as data.
- `tools/agents/push_wrapper.py::agent worktree`: Never run git with the agent's config in the worktree: only `rev-parse` and `symbolic-ref` run there; the clean check and push run in a scratch repo that borrows objects via alternates, and an agent repo with its own alternates is refused.
- `tools/agents/push_wrapper.py::child stdin`: Every child command gets /dev/null as stdin unless given input, so a git filter, fsmonitor or hook can never wait on the wrapper's own stdin.
- `tools/agents/push_wrapper.py::file reads and config`: Files read by an agent-influenced path are opened with O_NOFOLLOW and O_NONBLOCK, refused if not regular or hard-linked, and size-capped; `--config` must be owned by the running user with no group or other write bit.
- `tools/agents/push_wrapper.py::scratch git config`: git honours `safe.directory` only from global or system config, never `-c`, so the scratch dir carries a global config that allows the agent's directories.
- `tools/agents/push_wrapper.py::token and body`: The installation token reaches git only through GIT_CONFIG_* extraHeader, never an argument or file; the PR body comes on stdin (no body-file option, since a path could be swapped for a link to the App key).
- `tools/agents/push_wrapper.py::tool lookup and environment`: git and openssl are found only in fixed folders by absolute path, never the caller's PATH, and the environment is scrubbed at start (PYTHON*, GIT_*, SSL_CERT_*, OPENSSL_*, LD_*), so nothing caller-set picks what runs.
- `tools/agents/push_wrapper.py::workflows check`: The `.github/workflows/` base-diff refusal is a courtesy only (the App has no `workflows` permission and GitHub refuses anyway), so an unfindable base means no opinion; a remote rejection is a refusal (exit 1), never retried.
- `tools/agents/review.py::find-pr`: The pull request for a "Review run" is the one open PR whose head repository, branch and sha all match the run's own fields, because a fork can push the App's commit and open its own PR on it.
- `tools/agents/review.py::model text`: Issue and PR text is fenced under a token that does not occur in it, and model-written reasons are scrubbed of controls, invisible format characters, links, mentions and issue references before reaching a comment.
- `tools/agents/review.py::review attempts`: A marker comment is written before the status, and the model is asked at most once per head: any failure after the call still leaves a marker (a timeout may have been billed), and a rerun replays it; markers are never edited.
- `tools/agents/review.py::reviewer and App login`: The reviewer is picked by PR number and is never the model that wrote the change; only a login ending in `[bot]` counts as the App, so a mistaken or hostile AGENT_APP_LOGIN cannot make a person's PR the App's.
- `tools/agents/triage.py::model output`: The model has no token or tools; its answer is mapped onto the `triage_labels.json` allowlist and fixed comment templates, never closes an issue or adds a `notchling:*` label, and any malformed answer gives an empty plan that does nothing.
- `tools/bundle-next.sh::cargo output`: Copy the binaries from where cargo actually put them, since a shared `build.target-dir` moves them out of `target/` and the old path would bundle a stale build.
- `tools/dev-profile.sh::profile safety`: The real home comes from the account database, not `$HOME`; the profile path is checked literally and physically so a symlink cannot reach the real home, and a login in the environment would use the real account.
- `tools/github/apply-settings.sh::send`: A 404 on deleting classic branch protection counts as done, since every re-run after the first meets it; the script prints every request and asks before sending, and `--dry-run` never calls gh.
- `tools/guard/guard/capability.py::stripper limits`: A diff hides block-comment state, so a line with `*/` is also read as if it began after each `*/`; a bare CR ends a Swift `//` comment but git sees one line; a file git calls binary is still read because swiftc compiles it.
- `tools/guard/guard/gate.py::case and approvals`: Paths equal after case and Unicode folding are refused because a Mac checkout keeps only one; each maintainer's latest review decides, so a dismissed change request cannot revive an older approval.
- `tools/guard/guard/rulesets.py::admin and tag bypass`: The maintainer cannot approve his own PR, so admins may bypass the review only through a PR; the release workflows that hold `contents: write` (none with signing secrets) are the only ones allowed to create `v*` tags.
- `tools/guard/guard/source.py::Swift and Rust scanning`: Only `"` opens a Swift string (raw `#"`, `\(...)` is code, backticks are identifiers, `'` is nothing, `#/ /#` may hold quotes); a triple quote is skipped, not read, since one line can close it and carry code.
- `tools/guard/guard/tomldeps.py::manifest reading`: Python 3.9 has no `tomllib`, so manifests are parsed by hand per TOML spelling; the gpui rule must catch dotted, quoted, escaped, inline-table and `package =` rename forms, and multi-line values read to their end.
- `tools/guard/guard/weakening.py::invisible characters`: Added lines with Cf, Cc (tab excepted), Zl/Zp, variation selectors or Hangul and soft-hyphen fillers go to the maintainer, since they can make code read differently from what the compiler runs.
- `tools/guard/tests/test_workflows.py::required checks`: phone-analyze and phone-test are required on main, so their workflows must not use a `paths:` filter (the check would stay pending forever); event fields go through `env`, never `${{ }}` inside `run:`.
- `tools/install-hostd.sh::hostd update`: An install never ends running sessions: with none running the host restarts onto the new helper, otherwise it is left alone and takes over at its next idle moment, and a job on another helper path needs migrate-and-install.sh.
- `tools/locale/gen.py::subset`: The generator reads only a fixed Fluent subset (no attributes, no nested or exact-number selects, no message references, only `NUMBER()` and `-brand-*` terms, one-line values) and refuses the rest with `GUARD-LOCALE-SUBSET`; the Rust runtime, the conformance test against `fluent-bundle` and the phone's ARB output all rely on it, so widening it means changing all of them.
- `tools/locale/gen.py::outputs`: Which files are written comes from `locales/languages.json` (`outputs`: `rust` always, `arb` once the phone moves; the iOS and Android writers run only with `--ios` or `--android`); `--check` fails when a committed output differs, and a language in `draft` is checked but written into no output the app reads.
- `tools/protocol/gen.py::schema subset`: The generator reads only a fixed JSON Schema subset and errors on anything else; output is deterministic and cargo-fmt formatted, and `--check` fails when a committed generated file differs.
- `tools/release/appcast.py::feed rules`: Ed25519 signing is done by Sparkle's `sign_update` in the sign job, not here; pubDate uses fixed English tables in UTC (never strftime, which follows the locale), and promote keeps enclosure and signature byte for byte.
- `tools/release/tests/test_release_workflows.py::workflow security`: Shell snippets must work on bash 3.2 (macOS runners) and 5.x; `printf | grep -Eq` passes a multi-line value whose first line is right; environments hand secrets to every step, and third-party actions get none.
- `tools/release/version.py::build number`: CFBundleVersion is X*1000000+Y*10000+Z*100+N (+99 for a Stable) and Sparkle compares it as a number, so minor and patch stop at 99 and a beta number at 98; a Stable never reads fragments.
- `tools/test-python.sh::top folder`: The Python tests import their modules by bare name (`import preflight`), so each suite must run with the top folder CI gives it (guard.yml), or it fails with ModuleNotFoundError.
