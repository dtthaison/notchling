# The Rust app: notes for agents

The Cargo workspace in `crates/` is Notchling now: a GPUI app (`notchling-app`) over an always-on daemon (`notchling daemon`), both built on one engine library. Since 2026-11-11 it is `/Applications/Notchling.app` on the maintainer's Mac and owns every resource in decision 0011's table; the Swift app in `legacy/macos/` is retired and stays the reference for behavior a port matches ([its notes](../legacy/macos/Sources/AGENTS.md), read on demand). The root [AGENTS.md](../AGENTS.md) has the layers, checks, the line and safety rules; [ARCHITECTURE.md](../ARCHITECTURE.md) and [docs/decisions/](../docs/decisions/) say why; [docs/feature-map.md](../docs/feature-map.md) names each feature's files and tests. Keep these notes true: when you change what a note describes, change the note, and when something bites you, add it under Things that bit before.

## Crates

| Crate (package) | What it is | Builds | Used by |
| --- | --- | --- | --- |
| `protocol` (`notchling-protocol`) | The phone bridge's wire types, `src/generated.rs`, written by `python3 tools/protocol/gen.py` from `protocol/agentconsole.v1.schema.json`. Never edit it by hand (`GUARD-PROTOCOL-GEN`; skill `add-protocol-field`) | library | engine |
| `platform` (`notchling-platform`) | OS adapters behind `cfg`: data folders (`paths`), file watching (`watch`), keep awake, notifications, private writes (`files`), running apps (`apps`); a missing one returns `Error::Unsupported` | library | engine, local-api, notchlingd, app |
| `engine` (`notchling-engine`) | Everything with no UI, half the code (below) | library | notchlingd, ptyhost, app |
| `local-api` (`notchling-local-api`) | Daemon to client socket: framing, peer identity, tiers, audit log, `Client`, `ensure_daemon` (decision 0007) | library | notchlingd, app |
| `notchlingd` (`notchling-notchlingd`) | The daemon and the command line (decision 0004) | `notchling` | bundled beside the app |
| `ptyhost` (`notchling-ptyhost`) | Terminal host, a port of the Swift `agent-console-hostd` with its `hostd.sock` contract | `notchling-ptyhost` | bundled in `Contents/Helpers` |
| `kit` (`notchling-kit`) | Design kit: tokens (every system), GPUI widgets and `KitGallery` (macOS) | library | app |
| `app` (`notchling-app`) | The GPUI app, and the Machines window | `notchling-app`, `notchling-machines` | nothing |

The code has no comments, so each crate's `AGENTS.md` (`app`, `engine`, `notchlingd`, `kit`, `local-api`, `platform`, `ptyhost`) holds what a change could break without knowing it, by file. The wire shapes of the daemon's ops are in [docs/local-api-ops.md](../docs/local-api-ops.md).

GPUI 0.2.2 (with `runtime_shaders`: no Metal Toolchain here) is a dependency of `kit` and `app` only under `[target.'cfg(target_os = "macos")'.dependencies]` (`LINT-GPUI-MACOS-ONLY`); everything else builds and is tested on macOS, Linux and Windows, and off macOS `notchling-app` says it isn't supported and exits 0. `[patch.crates-io]` swaps in `vendor/gpui/` (one fix, `vendor/gpui/NOTCHLING.md`). Rust 1.99.1 is pinned; `deny.toml` allows only permissive licenses (decision 0008). `app` and `kit` deny `unwrap`/`expect` outside tests. Files stay under 1,000 lines, 600 with a warning (`LINT-FILE-SIZE`): tests go in `<module>_tests.rs` or `tests_<area>.rs`.

## Build, run, test

```sh
cargo test --workspace --locked             # CI runs it on macOS, Linux and Windows
cargo clippy --workspace --all-targets -- -D warnings   # CI's clippy runs on Linux and never sees GPUI code: run it on the Mac
cargo fmt --all --check
cargo deny check
cargo test -p notchling-app -- --ignored    # the render tests: they open windows (a Mac with a display)
cargo build --release -p notchling-app -p notchling-notchlingd -p notchling-ptyhost
cargo run -p notchling-notchlingd --bin notchling -- daemon   # the `notchling` binary; set NOTCHLING_DATA_ROOT first (below)
```

- Look at and click GPUI only in a release build: debug GPUI is far too slow to judge. Unit tests are fine in debug.
- The target folder may not be `target/`: a `build.target-dir` in `~/.cargo/config.toml` can share one across checkouts, and two builds then wait on one lock. Give each parallel agent its own `CARGO_TARGET_DIR`; find binaries with `cargo metadata --format-version 1 --no-deps` (`target_directory`). Paths below assume the default.
- A picture of a view: `notchling-app --render <view> --out /tmp/v.png` (`--help` lists them; each area's `renders.rs` adds its own), over `--data-root <dir>`, else `NOTCHLING_DATA_ROOT`, else `crates/app/fixtures/`, never `~/.claude`. `NOTCHLING_RENDER_APPEARANCE=light|dark`; other `NOTCHLING_RENDER_*` variables force a state (grep `crates/app/src`).
- Chat's bench: `NOTCHLING_RENDER_BENCH=<seconds> NOTCHLING_RENDER_BENCH_MODE=<mode> notchling-app --render chat` over a generated 200-turn root (`chat::bench_fixture`) keeps the window up, drives one kind of activity into it (`mac/bench.rs`, `bench_events.rs`) and prints a `bench:` line and one `bench-json:` line with frames, CPU and the counters: draws of the root, conversation, Sidebar and Details Panel, rows built, bytes parsed, `at_end`, `forced`. Modes: `idle`, `scroll`, `scroll-fade`, `hover`, `select`, `typing`, `terminal`, `reload`, `menu`, `sending` (`append` is `idle` while the test adds a line every 500 ms). `crates/app/tests/bench_chat.rs` runs them and holds the counts (ignored by default; a Mac with a display): `cargo test --release --locked -p notchling-app --test bench_chat -- --ignored --nocapture --test-threads=1`, in release and one at a time, since the numbers are CPU time. `NOTCHLING_BENCH_SECONDS` sets each mode's length. Judge a change by the counts; `ms/frame` moves with the Mac's load. Results and what each phase of decision 0018 changed: `docs/perf/chat-state-split-bench.md`. Smoothness of a scroll is held as counts too (`tests/bench_scroll.rs`, modes `scroll-start`, `scroll-slow`, `scroll-fling`, `scroll-momentum`, same command with `--test bench_scroll`): a recorder (`chat/view/scroll_probe.rs`, judged by `chat/scroll_trace.rs`) notes where every row painted in each draw and compares it with the wheel steps the bench injected (stalls, jumps, reversals, drifts, lost frames), and times each draw in the main thread's CPU time (`draws` in the `scroll` object: over 8.3 ms misses a 120 Hz frame, over 16.7 ms a 60 Hz one, with rows built and what the draw cost before the end of the list's layout). A script runs all its steps however late the Mac gets to them. `NOTCHLING_BENCH_SCROLL_DUMP=<file>` writes every frame (and `<file>.draws` every draw); `NOTCHLING_BENCH_REAL=<transcript>` runs `a_real_transcript_scrolls_by_the_wheel` over a copy of a real session (copied to the temp folder, never printed). `tests/render_blocks.rs` runs `NOTCHLING_RENDER_CHECK_BLOCKS=1` (the selectable texts against the model's blocks) and `tests/render_list_probe.rs` the list probe (`--render chat-list-probe`, gates G1 to G7); both ignored by default. `tests/bench_subagents.rs` runs `reload` and `idle` over 40 generated subagents (3 MB each, 2 running; `chat::bench_fixture::subagent_files`) and holds that no subagent file is read in a steady state (`parsed_bytes` at most 1 MB).
- A locked screen or a sleeping display sends a window no frames, so a bench reads `frames: 0` and a `--render` shows what loaded after its first frame never. The bench then draws frames itself, on a timer, through AppKit's `displayLayer:` (`bench_events::FrameDriver`; `NOTCHLING_BENCH_FORCE_FRAMES=1` always, `0` never; the line says `"forced":true`). A plain `--render chat` needs `NOTCHLING_RENDER_FORCE_FRAMES=1` there. Forced frames cost more, so compare counts, not `ms/frame`, between forced and unforced runs. A busy Mac adds a stray draw of every part now and then: repeat a run before believing a single 1.
- `notchling-app --data-root crates/app/fixtures/chat --open-chat` runs the app over a fixture; a fixture root and every render read files only, never a daemon. Over the real folders the app starts the `notchling` beside it and turns back on every switch the user had on (`switches/restart.rs`), so a dev app there acts on real sessions: the maintainer's call. Its menu bar item often hides behind the notch; `--open-chat` opens Chat.
- Stop a dev app with `pkill -x notchling-app`. `-f` matches whole command lines, so it also kills a shell whose command names the app, such as one running the daemon with `NOTCHLING_APP_TIER_PATHS=…/notchling-app`.
- `tools/bundle-next.sh` builds `build/next/Notchling.app` (signed ad hoc, bundle id `local.notchling.next`). Never pass `--install`: it quits the running app and replaces `/Applications/Notchling.app`. Only the maintainer installs.

The `notchling` binary (`crates/notchlingd`) is the daemon (`notchling daemon`), its clients (`notchling status`, `notchling sessions [--json]`, `pages`, `page`, `secrets`, `secret`, `secret-request`, `delegate`, `delegate-models`; all but `secret` and `secret-request` take `--json` for machine-readable output) and `notchling service install|uninstall|print [--dir <folder>]`. In dev, run the daemon over a copy of a fixture, never over your real folders: `cp -R crates/app/fixtures/notch /tmp/nl-root`, then `NOTCHLING_DATA_ROOT=/tmp/nl-root` for the daemon and the clients alike (socket, lock and `audit.jsonl` land in `/tmp/nl-root/notchling`). `--socket <path>` moves the socket and puts its lock and the audit log beside it; over the real folders the daemon still locks `notchlingd.lock` in the data folder, one daemon per data folder. `NOTCHLING_APP_TIER_PATHS` (read once at daemon start, and only by a daemon run from a cargo target folder) lists executables that get the app tier; `ensure_daemon` never passes it on. `service install` only writes the file and prints the `launchctl`/`systemctl`/`schtasks` command; don't run that command, and in tests always pass `--dir`.

`notchling hook [--socket <path>]` is Claude Code's hook under the daemon: it reads the hook JSON on stdin, asks the daemon (`hook.request`) and prints what the Swift `--hook` prints, or nothing (a pass, exit 0) when there's no daemon, no app attached, a socket error, a `claude -p` session, its 290 s deadline, an event over the local API's 1 MiB line (a Write of a big file: Claude Code then asks in its own terminal; the cap stays 1 MiB for every op, `hook.request` included), the daemon refusing it (its process must descend from the Claude Code process whose `sessions/<pid>.json` holds the event's session, read from the socket's peer, never from arguments), or the daemon's `acting` switch off. Acting is off at every daemon start, whatever any file says, until the app sends `settings.set_acting` (decision 0007's note of 2026-11-08); since the handover (decision 0011's note of 2026-11-11) the app sends it by itself when the user had it on. Only the app's Install Hook (Welcome, through `install.apply`) writes the hook into `~/.claude/settings.json`: never add it yourself (E13, M6). The code that can (`notchling_engine::install`, behind the daemon's `install` switch, which is off at every start: `install.plan` reads only, `install.apply` and `install.remove` answer the dry run) is tested against temp copies only; its roots are parameters, so a test never reaches the real `~/.claude`, `~/.codex` or `~/.gemini`. Try it with a fixture event: `NOTCHLING_DATA_ROOT=/tmp/nl-root target/debug/notchling hook < crates/notchlingd/tests/fixtures/hook/permission-request.json`. The Artifact tool's events (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`) never reach the daemon: `notchling hook` answers them itself (`notchlingd/src/hook_pages.rs`, over `engine::pages::hook`) from `<data dir>/pages`, the folder `notchling pages` and the pages window read, so saving a page needs no daemon, app or `acting` switch (the Swift hook handled them "before the app-running check" too). A publish is recorded under flock, a whole-page read of a saved link is denied with the local copy's path, and a failed read gets it as context; a first publish is saved under the lane's account (`CLAUDE_CONFIG_DIR` and `lanes.json`) or the main login (`~/.claude.json`). Any error, a panic or 8 s is a pass. Publishing to a page another saved account owns (`pages::owner`) is not wired: it has no login source or network yet, and the `accounts` switch lives only in the daemon, which a hook process can't ask without a new op.

## Architecture in one pass

- **Processes.** `notchling-app` (app tier) and `notchling daemon` talk over the local API; the hook and the command line are agent-tier clients. The app starts the daemon from the `notchling` beside it, or the `dev.notchling.daemon` LaunchAgent that `notchling service` writes does. Phones reach the daemon's bridge (TLS on 47821, the tunnel origin on loopback 47822). `notchling-ptyhost` holds terminal ptys under the `local.agentconsole.hostd` LaunchAgent, which nothing here installs. The daemon owns everything that acts or lives long; the app reads transcripts itself, read-only, for speed (decision 0004).
- **Local API.** `<data dir>/notchlingd.sock` (0600), one JSON object per line, `hello` first. The tier comes from the peer's executable (macOS: its audit token, read at accept, at `hello` and per app-tier request, against the exec race; Linux: `/proc/<pid>/exe`, best effort; Windows' pipe is a stub). Op and topic names are constants in `wire.rs` (`ops`, `topics`); each op has an `OpSpec`: `AGENT`, `APP`, or `APPROVAL` (fails closed with no app attached). Refusals and app-tier calls go to `audit.jsonl` (rotates at 5 MB, one old copy `audit.jsonl.1`), except the successes of an `OpSpec::APP_QUIET` op: a read the app asks on a timer (Details Panel's `git.*` every 5 s; `activity.list`; the list and status polls in `quiet_ops::QUIET_READS`: `bridge.status`, `bridge.devices`, `bridge.tunnel.status`, `accounts.list`, `lanes.list`, `providers.list`, `providers.usage`, `limits.status`, `limits.usage`). A poll that asks for a sync (`sync` or `refresh` true) is still logged (`Handler::loud`), and failures and refusals always are. Never quiet an op that acts, writes or touches the vault: a test classifies every op name in `wire.rs` as quiet or never quiet. Calls wait `CALL_TIMEOUT` (5 s) and check who serves the socket (`server_trusted`) first; 64 clients, 4 kept for the app.
- **Daemon.** `daemon.rs` locks, binds, then reads the session list (`engine::sessions::Monitor` on `platform::watch` batches under `jobs/` and `sessions/`, and every 5 s) for `sessions.list` and `sessions.changed`. `daemon_wiring.rs` builds every area per run: acting (`acting_ops.rs`, `control_ops.rs`, the terminal in `attach.rs`, the hook in `hook_ops.rs`), `codex_ops.rs`, `agy_ops.rs`, `bridge_ops.rs`, `pages_ops.rs`, `git_ops.rs` (`git.status`, `git.diff`: app tier, read only, no switch), `settings_ops.rs` (agents read every setting and change one by its class: `free` at once, `ask` through the Inbox, `never` not at all; decision 0020), and `OpGroup`s (`op_group.rs`) for switches, accounts, install, providers, limits and cost, catalog and vault. Command-line modes: `clients.rs`, `pages_cli.rs`, `vault_cli.rs`, `delegate_cli.rs`, `hook.rs`, `service.rs`.
- **Switches.** Five, off at every daemon start whatever any file says, since an agent with a shell can write any file: `acting` (`settings.set_acting`: replies, answers, session control, Codex and Antigravity turns, the hook), the bridge (`bridge.set`: no port bound until on), and `accounts`, `vault`, `install` (`settings.set_switch`, `switches.rs`). Only an app-tier call in that run turns one on. An area checks its `SwitchFlag` before touching anything and answers `forbidden` with the off message. Under a fixture root every login effect is a fake or refused.
- **Engine.** Pure where it can be: planners return a plan; effects sit behind traits with fakes (`Launcher`, pty, Keychain, HTTP, spawners). `transcript` (Claude Code, Codex rollouts, ACP, the phone's chat view, subagents, shells; `locate` finds a file and its `/clear` successor), `sessions`, `terminal` (emulator, `ask_dialog`, `permission_dialog`, keys, `pty/`), `reply` (keys and timings pinned to the Swift app by `pin_tests.rs`), `control` (new, stop, remove, move, Move All, Trust Folder, slash commands), `git` (a session folder's status and diff, read only, for the Details Panel's Git section), `tools` (`codex`, `agy` over `acp`), `delegate`, `bridge` (router, hub, `net/`) and `viz`, `pages`, `search` (`fts.rs`: `daemon/search.db`, FTS5, bm25), `accounts`, `providers`, `lanes`, `limits`, `cost`, `catalog` (`data/catalog.json` and live lists, decision 0016), `vault`, `machines`, `install`, `settings` (`keys.rs` lists every key), `store` (`notchling.db`) and `docfile` (decision 0014).
- **App.** Each area keeps a pure model, tested everywhere, beside GPUI views under `#[cfg(target_os = "macos")]` (`view*.rs`, `window.rs`) and `src/mac/` (shell, tray, Dock, hot key, `--render`). Areas: `chat/` (`chat/view/tool/`: one adapter per tool behind `ChatTool`, decision 0015), `notch/`, `search/` (a global hot key, ⌃⌥P by default and set in Settings > Search Shortcut: `search/shortcut.rs`, stored as `searchShortcut` like `ctrl+alt+p` or `off`; ⌘⇧P is only an in-app key binding, `OpenSearch` in `mac/dock.rs`, because a system hot key reaches Notchling before any app and took VS Code's Command Palette), `pages/` (`wry` windows and Chat's page panel, decision 0013), `accounts/`, `vault/`, `phone/` (pairing over `bridge.*`), `sheets/` (New Session, Settings, Second Opinion), `tools/` (Codex, Antigravity), `welcome/` (first run, About, updates, Install Hook), `switches/`, `machines/` (`notchling-machines`: no ssh or `gh` without `--live`, no vault value without `--vault`). `session_source.rs` gives Chat and the notch their rows from a background thread; UI threads never touch the socket. `actions.rs` sends ops; session calls wait `SESSION_CALL_TIMEOUT` (60 s). Daemon calls block: make them off the UI thread.
- **Chat's parts** (decision 0018, `chat/view/`). `ChatView` (`mod.rs`) is the controller: sessions, the selected row, drafts, tools and panels. `root.rs` is its draw (the header, panels, reply box, overlays) and `load.rs` its loads. Three parts are cached views drawn from their own model, and each draws only when that model differs from the last (`PartialEq`): the Sidebar and the Details Panel are `ModelPart`s (`pane.rs`) over `SidebarModel` (`chat/sidebar.rs`) and `DetailsModel` (`inspector.rs`), and the conversation is `ConversationView` (`conversation_view.rs`) over a `ConversationInput` and its own state (scroll and follow, open groups, hover, Copy's check, selection, the Markdown cache). A draw function reads its model, never `ChatView`; what a model can't see (the appearance, a fold) is redrawn on purpose through `redraw_parts`/`redraw_details`/`redraw_conversation`. `redraw_chrome` redraws only the window's outer parts (typing, terminal and simulator frames, the notch's state); `cx.notify()` on `ChatView` makes each part compute its model again. The conversation's rows are a GPUI list (`conversation_list.rs`, `ListRows`): a load's `chat::log::Change` becomes splices of the rows it touched, so the rest keep their measured heights, and a draw builds only the rows on screen plus 600 pt of overdraw. The engine hands out `Arc<Conversation>` (`transcript::conversation::read_shared`, `read` is an owned copy; an unchanged file is the same `Arc`), the loader diffs it with the last one off the main thread (`log::diff`: `Same`, `Items` splices, or `Reset` when ids don't line up) and the view only checks the pointer the change starts from. The open question is `Conversation::pending_question`, from the same read. Selection is anchored to the model: an end names a row id, a block and a byte (`row_select.rs`), `chat::blocks::plain_blocks` gives a row's selectable texts, `row_blocks.rs` feeds Copy from them, so rows not drawn are copied too. `view/select.rs` (draw-order notes) now serves only the file panel. Copy (⌘C, the Edit menu, the right-click menu `copy_menu.rs`) is the `Copy` action handled on `ChatView`'s root (`copy.rs`): the conversation's selection, else the file panel's, else the reply box's. GPUI sends a key or an action to the focused element's ancestors only, and with nothing focused (the reply box is off for a session the app can't type into, or was never clicked) that path is the window's outermost node, so a handler on the root never ran and nothing could be copied; `copy::Keys` is a focus handle on a zero-size child that takes the keyboard when nothing has it (the root can't track focus itself: an element that tracks focus takes it on every click inside it, pulling it out of the reply box). `NOTCHLING_RENDER_CHECK_COPY=key|action|menu` with `tests/render_copy.rs` checks the whole path in a real window. The kit's overlay scroll bar follows a div or a `ListState` (`kit/src/ui/scrollbar.rs`, `scrollbar_track.rs`, `scrollable_list`). Spinners in a part are slots a `SpinLayer` paints (`kit/src/ui/spin_layer.rs`). The Details Panel's Git section is its last, so no other section moves when it appears: its data is `DetailsModel::git` (an `Arc<GitModel>`, from `view/repo.rs`), asked of the daemon off the UI thread (`chat/git.rs::Gate` says when), and a clicked file opens its diff in the file panel (`view/diff_panel.rs`).
- **Chat's panel sizes and window frame** (`chat/panels.rs`, `chat/view/panels.rs`, `window_frame.rs`, `mac/window.rs`, `kit::ui::panel_edge`). The Sidebar and the Details Panel are as wide as `ChatView::panels.preferred` says, in points, drawn through `panels::shown`: each clamped to its limits (Sidebar 200 to 420 (its footer wraps to two rows under about 270), Details 240 to 520, defaults 272 and 260) and, when the window leaves the conversation less than `COLUMN_MIN` (360), both taken down toward their minimums in proportion to what each has above it (a window too small even then squeezes the column, as before). A hidden panel is 0. The widths reach the parts only as the style given to `cached()` (`Parts::sidebar(width, ..)`, `details(width, ..)`), and the parts' own root div is `size_full()`, never a fixed width: a width change re-lays out the part (one draw of it) and measures every conversation row again, nothing more. The root sets `panels.drawn` each frame (`lay_out_panels`); everything else that needs a panel's width (the new-session button, the page, terminal and simulator panels, the account menu) reads it (`sidebar_width()`, `details_width()`), never `SIDEBAR_WIDTH`. A drag is a `SideEdge` GPUI drag from `panel_edge` (a 9 pt hit zone over the panel's inner edge, a 2 pt accent line on hover and while dragging, the kit's left-right cursor, and a full-window overlay with that cursor while the drag runs); the root listens (`follow_panel_drags`), `panels::dragged` clamps the pointer's x and keeps the column's minimum against the other panel, and a double click on the edge sets the default. The saved form (`chatPanels` in the settings: `sidebar` and `details` as a ratio of the window's width, absent for a panel at its default, and `sidebarHidden`, `detailsHidden`) is read once in `with_source` (`restore_panels`: the width is the ratio times the window's width then, clamped) and written 400 ms after the last change on a background thread, and at quit and when the view is released; a fixture root never reads or writes it. `NOTCHLING_RENDER_SIDEBAR_WIDTH` and `NOTCHLING_RENDER_DETAILS_WIDTH` force a width in `--render chat`. The `panels` bench mode wiggles the Sidebar's width: it draws the Sidebar and the conversation, never the Details Panel.
  - The window's frame is `chatWindowFrame` (`window_frame::Frame`: the display's UUID, `CGDisplayCreateUUIDFromDisplayID`, stable across runs, and x, y, width and height relative to that display, which is what GPUI's mac window reports). `mac/window.rs` reads it when Chat opens (`open_main_window`, behind the menu bar item, the Dock, `--open-chat`, and every `open_chat_*`), `window_frame::place` decides: the same display found, the same size and place clamped onto it (a smaller resolution pulls it in); the display gone or no UUID, the same size clamped to the main display and centered there; nothing saved, the default size centered. It is written 400 ms after a move or resize stops, on a background thread, and flushed (pending frame only) when the window asks to close and at quit.
  - It was silently never saved before 2026-11-13: `Settings::set` refuses a key not in `settings/keys.rs` and the save only printed the refusal, so `chatWindowFrame` never reached `notchling.db`. Any key the app writes with `set` needs its line in `keys.rs` (the key count is held by a test in `settings/migrate.rs`); `window_frame::tests` and `panels::tests` write and read back through a real store.
- **Chat's history budget** (`chat/history.rs`, `engine/src/transcript/tail.rs`, `sheets/settings.rs`). How much of a conversation's file Chat parses is the `chatHistory` setting, Settings > Chat > Conversation history to load: 2, 4 (the default), 8 or 16 MB (`history::bytes`; the key's `allowed` list and `history::CHOICES` say the same thing, a test holds it). It is the engine's `CHAT_TAIL`, one process-wide number (`chat_tail_bytes`, `set_chat_tail_bytes`) that three `Cursors` follow because they are built with `Cursors::chat`: Claude Code sessions, the subagent a user opens, and Codex rollouts. The app reads the store once, in `mac/shell.rs::run` before any window opens (`history::apply`; a store it cannot read keeps the number it has, never 4 MB), and a load never opens SQLite. A change in Settings applies at once: `SettingsView::apply` emits `SettingChanged`, `ChatView::open_settings` hears it, `history::on_change` sets the number and, only when it changed, `reload_now` makes the one load that parses again, so the reset happens while the user is in Settings, not while they read. Each cursor remembers the budget it was built with and a read under another one drops it and parses again; an unchanged budget and file read nothing. Never in its reach: the subagent rows and their `glance` tails (small, fixed), the notch's snapshot (`TAIL_BYTES`, 2 MB), Search's index, the daemon and the phone (they never set it, so they keep 4 MB). The 64 MB look-back for lines over the parser's cap stays. The parser keeps at most 500 items (`KEEP_ITEMS`), so a bigger budget shows more only where the budget, not the 500, was the limit: sessions of long tool results.
- **Details Panel rows** (`chat/paging.rs`, `chat/subagent_rows.rs`, `engine/src/transcript/glance.rs`, `chat/loader.rs`). A model compute and a draw do no file I/O and start no process: the subagent rows are built by the loader off the main thread and arrive as `Loaded::subagent_rows` (data, with `subagent_counts`), and the view only keeps them. A row shows two facts that come from the subagent's transcript: its context tokens (the last assistant `usage`) and, for a running one, its doing line (the newest step). Both come from one small tail read, never the 4 MB chat tail: `glance::peek` reads the last 64 KB, widens to 256 KB then 1 MB only for what it has not found, and stops at that cap (`Window`, `widen`; the doing line runs the normal parser over the first window that holds a step, and later windows only look for the number). The inspector takes the subagent counts once, from `inspector_listed`'s argument. The engine's subagent and Codex `Cursors` (limit 30 files, LRU) are for a subagent the user opens and for Codex sessions; a row never uses them, so no number of subagents can thrash them. `SubagentRows` keeps each read by file size and mtime, so an unchanged file is never read again and a changed one is read once. `Page` (`paging.rs`, used by subagents and by shells) decides which rows exist at all: on open every running subagent and only those, else the 3 newest; a row not shown is not read and not drawn; `Load N More` (10, newest first) bumps `more_subagents`, asks for a load and the loader reveals and reads the next ones; a subagent that appears later goes to the top and the shown rows stay; running ones that finish stay shown; another session starts the first page again. The section title counts all of them (`SubagentCounts`). Shells follow the same rules, over the transcript's own record and then the probe (`shell_list.rs`: `ShellPage` over a shell's `finished_agents` entry and the probe's answer for its output file): a shell the transcript never ended (a crashed or exited session) is unfinished until the probe says no process writes its file, so the first page is made only once every unfinished shell has an answer. Until then the listing is `waiting`: the 10 newest, no `Load N More`, and the probe asks about every unfinished shell that has no answer. After that a shell with no writer counts as ended for paging and is never asked about again; the first page is the ones with a writer, else the 3 newest ended; `Load N More` reveals the next 10 at once in the view (`ChatView::load_more_shells`, no load needed), a new shell goes to the top and is probed, and shown shells stay shown. `chat/view/shell_probe.rs` asks `lsof` in one call per 100 paths (`-F pcan`; `shells::parse_writers_by_name` reads the names back for that chunk: a path matched by itself, its real path or a file name nobody else shares, and every writing line when the chunk holds one path), never one process per shell, and a failed spawn records nothing (an lsof that cannot run must not mark every shell ended); a result that changes the listing redraws the Details Panel. A shell not probed yet shows Running, as before, and only shown shells are ever in the model. The Output tail is read on the click (`open_shell_output`), never in a compute. The opened subagent's header takes its tokens from the conversation the open read already parsed.

## Things that bit before

- GPUI 0.2.2's text element truncated its runs in place, so a resize measured an elided label again and sliced a string mid-character: a crash. `vendor/gpui` fixes it; its `NOTCHLING.md` says when to drop the patch.
- GPUI's `truncate()` never draws the ellipsis (`nowrap` keeps the first measurement). Use the kit's `elide()`.
- GPUI swaps a state's whole text style on hover and press, so a hover that set only a color made the words grow. Give each state the full style (kit buttons do).
- GPUI sets the arrow cursor after every draw when nothing asks. Clickable elements need `.cursor_pointer()` (kit buttons have it); resize cursors come from `kit::ui::resize_edges`.
- GPUI resigns a window that became key while the app wasn't active with the window's lock held: the app hung. Call `cx.activate(true)` before opening a window from the menu bar.
- Every pixel of a GPUI window is Metal drawables plus MSAA textures: a screen-wide notch canvas cost 93 MB. `notch::layout::canvas_size` sizes it to the largest shape.
- Polling lstat'ed every file each second, a third of a core on a real `~/.claude` (53k files). macOS uses FSEvents (`platform::watch`; `examples/watch_cpu.rs` measures). Its debounce restarts on every change, so steady writes flush only through `max_latency`; Chat coalesces reloads (`chat::reload::ReloadGate`) and watches a folder reached twice through lane symlinks once.
- The daemon has no main run loop, so `NSWorkspace`'s running apps go stale there. `platform::apps::is_running` reads the process table; a login switch must never write while its app runs.
- Reading the session list before binding made the socket miss `ensure_daemon`'s 3 s wait, which killed the daemon, and the app read files for good. Now: locks, bind, read; `sessions.list` waits up to 4 s, under the client's 5 s.
- A reply can take over 5 s, and an error shown while it still arrived made the user send it twice: session calls wait 60 s. Accounts ops waiting on Keychain or network answer within 4.5 s and finish by event.
- One big Antigravity permission diff passed the 1 MiB line and failed `prompts.list` for every prompt. Cut payloads to fit: diffs to 400 lines or 128 KB, `agy.conversation` to the newest 512 KB with `truncated`.
- A `claude` exiting with output nobody read waits for its tty to drain, and SIGKILL can't end that: waiting with the pty master open hung `folder.trust`. Hang up and close the master first. A child that stops reading blocks writes forever, so `Terminal::write` gives up after 10 s.
- Locks held across blocking work hung things: ACP's writer lock blocked killing a stuck agy, ptyhost's delivery lock let one slow client stall all, the vault's cache lock waited on Keychain, a switch listener on a Keychain prompt held up `settings.set_switch` (now 500 ms at most). Never hold a lock across I/O, a pipe or a Keychain call.
- `security -i` reads 4 KB lines, and Claude Code's login item also holds MCP logins, so as hex it passed that and every switch was refused. It goes as quoted text on stdin, never argv; long saved logins split over several items.
- The daemon once read `acting` from `notchlingd-settings.json`, so a file write and a restart turned it on. No file turns a switch on in the daemon; that one saying on is audit-logged (`file_said_on_ignored`).
- Over a fixture root a Codex turn inherited the daemon's `CODEX_HOME` and wrote to the real `~/.codex`. Children get the folder the daemon reads; a fixture root runs only `<root>/.local/bin/codex`.
- Chat with a working session took a core: the kit spinner's GPUI animation asked for a frame every vsync, and each frame laid out every message (52 ms a frame on a 60-turn conversation, 19 fps). A spinner is now a small view of its own ticking ten times a second (`kit::ui::icons`), the conversation is a cached view (`chat/view/conversation_view.rs`, below), and a change shown only outside it redraws through `ChatView::redraw_chrome`, not `cx.notify()`, which draws the conversation again.
