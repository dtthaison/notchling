# Recording phase: reply behaviors and their fixtures

Before E3 (terminal and replies) moves to Rust, every reply behavior in `legacy/macos/Sources/AGENTS.md` ("Things that bit before") gets terminal byte fixtures, while the Swift app can still produce them ([design spec](superpowers/specs/2026-11-07-agent-run-open-source-design.md), Parts). E3's port is done when its Rust code reproduces these behaviors against the same bytes, and the live-test mode (`crates/engine/tests/live_reply.rs`) passes against a real job.

Paths are from the repository root. `Sw` = `legacy/macos/Sources/Notchling/`, `T` = `legacy/macos/Tests/NotchlingTests/`, `F` = `T` + `Fixtures/terminal/`.

## How to record

`tools/record-reply-fixtures.sh` (untried) runs `RecordReplyFixturesTests/testRecordReplyFixtures`. `tools/record-reply-fixtures.sh --prepare [<folder>]` first makes the scratch folder to start the jobs in (default `$TMPDIR/notchling-record-<time>`; it runs `git init` and puts the `.notchling-record-scratch` file in it, and prints the path). The test does nothing unless `NOTCHLING_RECORD=1`, and it refuses any job whose `cwd` is not a scratch folder, and any output folder inside `~/.claude`. A scratch folder is one whose own name is `notchling-record` or starts with `notchling-record-` (`..` and symlinks resolved, so a link named that way to a real project fails) and that holds the `.notchling-record-scratch` file as a regular file. The `cwd` is read from the copy of `jobs/<id>/state.json` that `claude attach` will run in: the newest copy, picked as `AgentMonitor.environment(forJob:)` picks it (a session moved to another account leaves a stopped copy in the folder it left, which may be the first config folder's). It writes `<behavior>.bin` (every byte read) and `<behavior>.json` (the keys sent with the time and byte offset, phase offsets, the final screen, notes) to an output folder; the script copies them into `F`. Only the maintainer runs it: it types replies into the scratch jobs, each costing a model turn.

The recorder owns its attach (a forkpty, the sizes and env the app uses, every byte teed), because `ReplySender` and `TerminalSession` keep the bytes to themselves and are protected files. The keys, pauses, parsers and dialog check it uses are the app's own, and `testRecordedKeysAreTheAppsOwn` fails if `clearInput` or the paste wrapper changes, so a stale recording is noticed.

Recordings are made with the Claude Code version installed that day (the json records it). Review each `.bin` for an account email in the banner before committing it.

## What is left after recording

Names above that say *record* have no file in `F` until the maintainer runs the script. `crates/engine/tests/fixtures_terminal.rs` loads every `.bin` there (non-empty, has an escape sequence, and its `.json` agrees with its bytes), so a new recording is covered without a change. The emulator port and the replay assertions are E3. The live checks are listed in `crates/engine/tests/live_reply.rs`, switched on with `NOTCHLING_LIVE=1`.

Rulings:

- The recorder's scratch rule is the job folder's own name being `notchling-record` or starting with `notchling-record-` (not a substring: `notchling-recorder` is refused), the `.notchling-record-scratch` file in it, the check made on the copy attach will use, a simple job id, and an output folder outside `~/.claude`. The always-on tests in `RecordReplyFixturesTests` pin each of these (`testScratchFolderRule`, `testAScratchFolderNeedsTheSentinelFile`, `testALinkIsNotAScratchFolderOrASentinel`, `testTheJobCheckReadsTheCopyAttachWillUse`); they build their folders in the temp folder and never read a real job.
- The opt-in tests (Swift and Rust) return early with a printed reason instead of using the test frameworks' skip and ignore markers, which the guard's skip check flags in added lines.
- Production code is untouched; the recorder duplicates the attach setup rather than adding a byte tap to the protected `ReplySender` and `TerminalSession`.
