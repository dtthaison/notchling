# XXXX: Workers get their own tool logins

## Context

`XXXX-workers-follow-the-mac-on-click` let the user bring a Worker's Claude Code, Codex and Antigravity to the Mac's versions. It left two gaps in "adding a Worker leaves it working like the Mac". A tool the Worker doesn't have (m1 had no Codex) stayed missing, and a tool it has but isn't signed in to stayed unusable. The first answer to the second was a how-to ("in your own terminal on m1 run codex login --device-auth"), and the login steps in Machines said "Notchling never signs a tool in".

Codex and Antigravity can't share the Mac's login. Their refresh tokens rotate: a copy on a second machine signs one of the two out the next time either refreshes. Root `AGENTS.md` already says never to refresh a token in use, and the vault and `security` rules say what Notchling may read from the Mac's logins.

On 2026-11-18 the maintainer decided that adding a Worker should leave it working like the Mac, with each Worker holding its own login for the same account, approved by the user in their browser on this Mac.

## Decision

- **Each Worker has its own login per tool.** Codex signs in on the Worker with `codex login --device-auth`, run over the existing ssh runner as the worker user. The user opens the link on this Mac and enters the one-time code there. The Worker's login is a separate grant on the same account; it is never the Mac's.
- **Never copied.** No auth file, token, cookie or Keychain item moves between machines, in either direction. Nothing is read back from `~/.codex` or any auth file on the Worker; Notchling learns the result only from the tool's own status command (`codex login status`) and the exit code. This Mac's logins are never touched by this.
- **The link and the code live in one place.** They are read from the command's output, held in memory for the sign-in sheet on this Mac, and shown only there. Masking does not depend on recognising them: every byte the device login prints is withheld from the Fix log, the audit line, events, errors and the card, from the first byte on, and the log keeps only the exit code and one fixed note. The parser takes the first link and the first code after the "one-time code" marker and then locks, so the phishing-warning line can't re-arm it. The code is offered only from a complete line (or after a short pause with no more bytes), never as a half code. Lines are split on newline and carriage return, the link may be plain text or a terminal hyperlink, and a line past 4 KB is cut and never logged. The login run keeps no raw output after it ends and no `Debug` path prints a command's output. The sheet's data is dropped when the sign-in ends or is cancelled. The link is opened only if it is an `https` address on openai.com or chatgpt.com.
- **The Worker classifies its own status.** The status command's text is never sent back: for a file-backed API key Codex prints the first and last characters of the key. The remote script reads `codex login status` and prints one fixed word (`signed_in`, `signed_out`, `api_key`, `unknown`), and the engine reads only that word. The Machines "Codex signed in" step and the sign-in share the script.
- **Only the tool's own status is read back.** After an install or a sign-in Notchling re-runs the tool and login checks and nothing else. The worker's `~/.codex` (including `config.toml`) is never read back to this Mac, so the self-update probe is not part of these actions.
- **The Worker is the one on the card.** Before an install, a sign-in or a Check Sign-In, Notchling asks the Worker over ssh for its node id and refuses unless the command exits 0 and the whole reply is the card's node: a name that now points to another host changes nothing, and a reply with extra content is not read for a match.
- **Busy is checked on the Worker, right before.** The card's job count (which comes from a capped list) is only a first filter. Right before the command runs the app refreshes the cluster and the engine runs the same process probe as a tool update on the Worker; a running job or a running Codex refuses, and an unreadable probe, a probe that does not exit 0, or a cluster refresh that fails refuses too.
- **A sign-in replaces the login the Worker has.** `codex login --device-auth` clears an existing login first, and an API-key login is reported Unknown. So Sign In is offered only when the status is definitely Signed Out. For an Unknown status the card offers Check Sign-In, which only reads. The status is read again inside the same ssh run as `codex login --device-auth`, right before it, and the script exits without logging in unless the word is `signed_out`. The sheet says that signing in replaces the login the Worker has.
- **Bounded and cancellable.** The wait ends after 10 minutes, on Cancel, or when the command exits. The engine checks the cancel flag before each step, so a Cancel during the checks never starts the login. Cancel clears the code and the sheet at once and stops the local ssh, and the card says Stopping until the old ssh has ended; only then are the buttons back and the status read again separately. Each run has an id and only the current one updates the card, the login mark or the sheet. The remote command also stops itself after 10 minutes and when the code expires. The sheet's state is kept with the run, so closing and reopening the Cluster window keeps it.
- **Success is what the status check says afterwards.** The command's exit code alone is not success. After it, the same status read as the Codex login step runs (for Antigravity on a Mac, the one that also looks in the Keychain), and only a signed-in answer counts. The result shows on the card.
- **Antigravity has no headless sign-in Notchling can start.** `agy` signs in through its own interface with the same Google login as the Antigravity app, and no device flow is documented. The Sign In button on its line shows what to do on the Worker and a Check Again button that reads the login status; when a Check stays Unknown the how-to opens again. Notchling doesn't guess a flow for it.
- **Claude Code keeps the long-lived setup token from the Vault.** Its login on a Worker is the cluster's, set up as before. This record changes nothing for Claude Code.
- **Missing tools are installed on the user's click.** A Worker's card offers Install Codex or Install Antigravity for a tool shown as Not Installed. Codex installs the Mac's usable reference exactly (the standalone installer's `--release x.y.z`, or `npm install -g @openai/codex@x.y.z` when curl is missing), as the worker user with no sudo, with the version validated as three plain numbers. Antigravity's installer takes no exact version, so the newest is installed and the card says so. The install refuses while the Worker runs a job and runs behind the install switch. It succeeds only if the tool is found afterwards, and for a pinned install only if its version equals the target.
- **Sign-in is gated by the accounts switch.** It changes a login, so it runs behind the Switch for accounts, checked again at the click.
- **A tool the Worker doesn't have shows Not Installed.** A tool counts as installed only when its program is there, not when a manifest, package record or empty folder is: the node's own report is read from files (`versions/mac.rs`, which also accepts a Homebrew cask's `bin/codex` and takes the newest version folder that has its program) and a left-over manifest used to make a removed Codex show its old version. The Cluster card trusts the Worker's own `command -v` read from Machines, or an install or login result from a click, over a node report that disagrees, but only while that evidence is newer than the node's last changed report for that tool (or login) and at most 20 minutes old; a newer report from the node wins, and an install mark also gives way to a newer ssh probe that finds the tool missing. The app keeps the time of the last change per node and tool: a tool first seen counts as 0 (so a read from before the app started, such as one loaded from `notchling.db`, still wins over it), and it is stamped with the time only when a print later changes. A sign-in's login mark is stamped after its status re-check returns, and the run stays Stopping until that check ends. Machines loads its last read of each Worker's tools from `notchling.db` at start, so this holds after a restart.
- **Recorded like any Machines Fix.** Each install and sign-in is one Fix with its log lines and one `machines.fix` audit line with the machine and the tool's title; neither the link nor the code is in them.

## Consequences

- It amends `XXXX-workers-follow-the-mac-on-click`: installing a missing Codex or Antigravity and signing a Worker in are now actions Notchling takes on the user's click, beyond updating a tool that is already there.
- It amends the Codex how-to in `crates/engine/src/cluster/logins.rs`: the sentence "Notchling never signs a tool in" is gone, since Notchling now signs Codex in on a Worker. "Never renews a login" stays: Notchling doesn't refresh a token.
- It adds one allowed write on a Worker: the tool's own login, made by the tool itself through its device sign-in. `docs/goals.md` and `docs/policies/privacy.md` list it, and that the link and one-time code pass through this Mac's memory and the sign-in sheet; the maintainer changes them.
- A cancelled sign-in may leave the command running on the Worker for up to its own timeout. Approving a stale code after a cancel would sign the Worker in; that is harmless but unplanned.
- Antigravity workers stay a manual step until the CLI documents a headless sign-in.
- The Machines window is unchanged: its login steps still only read, and its how-to now points to the Cluster sheet for Codex.
