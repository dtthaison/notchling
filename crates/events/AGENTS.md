# events: notes for agents

## Why the code is this way

`notchling-events` is the registry of what Notchling records: the envelope every event wears, the closed list of field types, every kind with the texts the Logs page will show, and a test sink. It is a leaf crate (`sha2` and `base64` only): `engine`, `local-api`, `notchlingd`, `ptyhost` and `app` will depend on it, so it can't depend on any of them. Phase 1 of the logging plan (decision XXXX, [the design](../../docs/superpowers/specs/2026-11-13-logging-design.md)) adds it and nothing writes an event yet.

The code carries no comments (see [AGENTS.md](../../AGENTS.md)). What a change could break without knowing it, by file:

- `crates/events/src/field.rs::LogField`: The trait is sealed (`sealed::Sealed` is `pub(crate)`) and implemented only for the closed list of types, none of which can hold free text. `String`, `&str` and `serde_json::Value` don't implement it, so a text field in a kind does not compile. Never implement it for a new type outside `field*.rs`: `LINT-LOG-NO-TEXT` fails the build, and a type that can hold text defeats the point of the crate. A new type goes on the list here, in the design (6.2) and in the golden together.
- `crates/events/src/field.rs::token`: A `Version`, `Exe`, `Tool`, `CodeLoc` or `Hex` that fails its charset or length becomes the token `unknown`, never an error: a producer must not be able to lose an event by passing a bad value, and a bad value must not reach a line. `Exe::from_path` keeps the file name only, and `.` and `..` are `unknown`.
- `crates/events/src/field.rs::Op`, `ErrorCode`: `&'static str` made from a known list, because this crate can't depend on `local-api`. A string off the wire is parsed against the list (`Op::parse(text, known)`, `ErrorCode::parse`) and an unknown one becomes `unknown`. `ERROR_CODES` must equal `wire::ErrorCode`'s names; Phase 2 adds the test that holds them equal.
- `crates/events/src/field.rs::Hex::from_bytes`: Cuts to 64 characters and pads with `0` to 8, so it always returns a valid `Hex`.
- `crates/events/src/field.rs::List`: Cuts to 16 items at construction. `Event::new` cuts again if the event would pass the size (see `value.rs::Fields::fit`).
- `crates/events/src/field_ref.rs::Ref`: An identifier (a session id, a folder, a secret's name) comes from files and callers that can write anything, so a `Ref` replaces control characters with `?` and cuts at 256 characters by `chars()`, never by bytes. How it is written depends on the sink: `RefMode::Plain` writes the id as it is (Audit and Activity), except for a kind whose `ALWAYS_HASHED` is true (`Item`: an inbox id can hold a vault ticket); `RefMode::Hashed` writes `h:` and 8 hex of `SHA-256(salt || kind || 0x00 || id)` (Diagnostics, Metrics and bundles). The salt is per data folder and is never written; `Salt::id` is the first 8 hex of its own hash.
- `crates/events/src/field_macros.rs::log_choice!`: Every choice enum gets an `Other = "other"` value, and `choice_or_other` turns a name the registry doesn't list into it. A reader built before a new value existed sees `other`; it never fails the whole event. Adding a value needs no version bump.
- `crates/events/src/kind_macros.rs::kinds!`: One invocation per kinds file, because it makes `pub const KINDS`. It makes a struct per kind (named by the kind in CamelCase, as later phases construct them), its `KindSpec` and the `FieldSpec`s from each field type's `DESC`. `retired:` is optional and defaults to false.
- `crates/events/src/kinds/*`: A kind is never deleted, only marked `retired`, so old Audit lines stay readable. A field removed, renamed or changed in meaning bumps `kv` and changes the golden (`tests/golden/log-kinds.json`), which is a protected test edit. Adding an optional field or a choice value changes the golden too, but no `kv`. `docs/log-kinds.md` is generated: after a change run `NOTCHLING_UPDATE_GOLDEN=1 cargo test -p notchling-events --test golden` and read the diff. Titles are Title Case, `records` and `why` are one or two sentences ending in a period, `Always` kinds are on by default with a reason, and the registry tests hold all of that.
- `crates/events/src/kinds/settings.rs::SettingKey`, `SettingValue`: One value per key in `crates/engine/src/settings/keys.rs`, and per allowed choice any key lists. `tests/settings_keys.rs` reads that file and fails until the lists are equal, so a new settings key needs a line here. A text value is never written: it goes in as `value_chars` and `value_hash`; an unknown key goes in as `unknown` with `key_hash`.
- `crates/events/src/kinds/security.rs`, `secrets.rs`, `settings.rs`: The `Always` kinds, the commit kinds (`registry::COMMIT_KINDS`) and the owner kinds (`registry::OWNER_KINDS`) are held by `registry_tests.rs`. Unlocking an owner kind means editing that list and its test, which the maintainer sees.
- `crates/events/src/value.rs::Fields::write_json`: Keys are written in byte order of their names, `Null` fields left out, with our own writer: `serde_json`'s `preserve_order` is on for macOS (through GPUI) and off on Linux, so a map would order keys differently per platform. The golden's writer (`doc.rs`) does the same. The seal's input is these bytes from Phase 2 on: never reorder, rename or change how a value is written.
- `crates/events/src/value.rs::Fields::fit`: An event is at most 4 KB as JSON. `Event::new` budgets 512 bytes for the envelope and the rest for fields; if the fields are over, lists first cut their refs to 64 characters, then drop items from the end, and last every ref is cut to 32. Phase 2's writer checks the real line, since an actor's refs can pass the 512.
- `crates/events/src/envelope.rs::write_body`: The key order `v, kind, kv, ts, ts_rx, seq, host, proc, pid, boot, op_id, actor, outcome, repeat, spooled, f` is fixed and the Audit line wraps it. Never reorder it. Absent optional parts are left out, and `actor.session` is only for an agent-tier caller (the daemon fills it, never the client).
- `crates/events/src/emit.rs::Emit`: `push` never blocks and never fails the caller; `commit` returns an error when the event could not be written and flushed, and only a kind in `COMMIT_KINDS` may use it. `NoEmit` is for code that has no sink (its `commit` succeeds); `MemorySink` is the test double and can fail commits on demand.
- `crates/events/src/doc.rs`: `golden_json` and `markdown` are the only places that turn the registry into text for people. `notchling log kinds --markdown` (Phase 6) prints `markdown()`.
- `crates/events/tests/golden.rs`: Compares the registry to `tests/golden/log-kinds.json` and `docs/log-kinds.md`, and runs on Linux and Windows CI as well. `NOTCHLING_UPDATE_GOLDEN=1` rewrites both.
