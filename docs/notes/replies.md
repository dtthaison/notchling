# Replies

Typing into a session from Chat, the notch or the phone: when a reply waits, how it is typed, pictures, and every way it failed before. The Swift app's reply and question notes are in `legacy/macos/Sources/AGENTS.md`, its recorded fixtures in [recording.md](../recording.md).

Part of the Rust app's notes, moved from `crates/AGENTS.md`; the index is in the root `AGENTS.md`. Keep it true: change the note with the code, and add what bites you under Things that bit before.

## Things that bit before

- Replies from Chat were held for good ("can't send messages any more") on a session that was not working. Claude Code writes `status: "busy"` in `sessions/<pid>.json` while the model works *or* a background task runs (a `run_in_background` shell, a subagent, a monitor), so a turn that ended with a task still going (the maintainer's job had three `until ! pgrep -f bundle-next.sh` loops that match their own command line and never end) kept the row Working with `state: "done"` in `jobs/<id>/state.json` and `inFlight.tasks: 3`; `Held::route` held every reply and `ready` flushed only `completed` rows, so the text sat as one Queued bubble until the tasks ended. Two rules came out of it: a row's group says what the session is doing, not whether typing would start a turn, so reply routing reads `Agent::turn_running()` and `Agent::takes_held_text()` (flag `at_prompt`, set from the live status and `inFlight.tasks`, `engine/AGENTS.md`), never `group == Working`; and held text must never depend on a state that can last for hours, so it also goes into a row that ended its turn asking in text (Needs input with a live idle or busy-with-tasks status), and waits only for a dialog (`waiting`). The Stop button and `session.interrupt` still read the group (Esc on a session with only tasks running is a different question); a stuck-looking Working row with no turn is the thing to check first when a reply is held. Fixtures: `engine/src/sessions/jobs_prompt_tests.rs` has the real shapes with synthetic values.
- A held reply was typed into a turn that had just started, and went out as a different message (2026-11-15, 05:57). The session's four `until` shells never end, so its live status is always `busy`. The row was held at 05:55:52 and sat held for 80 s with the turn over (why it was held then is not known; nothing keeps the job file). At 05:57:14.9 the user typed their own prompt in the terminal; 0.7 s later the daemon flushed, because the job file moved unevenly at that turn's start: `inFlight.tasks` was up, so `turn_is_over` (busy, `blocked`, tasks > 0) said the turn was over, while `state` stayed `blocked` for the whole 43 s turn (`timeline.jsonl`: `blocked` with the new prompt as `detail` at 05:57:15, `working` only at 05:57:58, for the next queued prompt). Then `claude attach` took 15.0 s before the first look at the box (`reply-screen.txt` trail: first note at +15041 ms): `wait_quiet(500 ms, 15 s)` returns only after 500 ms without output, and a running turn's spinner and counters never leave such a gap, so the wait ran its whole timeout. By then the user was typing the next prompt in the same box (the attach shares it; the cursor walks from column 3 to 22 over 8 s in the trail). The old checks passed whatever the box held (`Input::holds` is "not empty"), so the clear keys and the paste went into their text, an Enter went out on a box of 1 character, not the 2 of the message (the transcript has `d` queued 15.6 s after the flush began), and the wait after the Enter saw typed text for 8 s and failed as `not_sent` though the message had gone; the put-back typed it again six seconds later. Rules that came out of it:
  - Nothing reads `state` or the cached row alone to say a turn is over. A held text goes only when a fresh read of the job and live files (`sessions::fresh::job_row`) takes held text, a transcript tail read (`transcript::restart`) shows no turn after the last `turn_duration`, the reading has stood for `SETTLE_MS` (3 s) on the 1 s tick (`Held::ready`), and once more at the first key (`held_guard::Guarded`, a failure `not_idle` with nothing typed). The transcript is asked only for the inference (a row Working with `at_prompt`); live `idle` is trusted. A direct reply asks it only in the same case, so a reply to an idle session stays at once.
  - A reply never types over or beside text it did not put in the box. The box must be empty (or hold exactly the message, a leftover of an earlier try) before the clear keys; after the paste it must show the message and nothing else (`Input::fill`: `Whole`, or a folded `[Pasted text #N +M lines]`) before Enter. Any other text is `NotCleared` (nothing typed) or `Mixed` (pasted, no Enter), unless the clear was meant: what an earlier try of Notchling's own left there, or the person's "Clear Box and Send" (2026-11-15, below). The Swift app cleared a draft silently; this one clears only those two. A held flush that fails never drops the message: it stays held and shown (`session.held` carries a `note`, Chat shows it with a Discard link), is retried no sooner than 30 s later, and one that may already be in the box (`Mixed`, `not_sent`) is typed again only when the transcript shows no user line with its text since the attempt (`transcript::sent`); when the transcript cannot say it is never retyped by itself.
  - After the Enter the reply is sent when the box no longer carries the message (`Input::carries`), whatever else is in it, so a person typing again cannot turn a sent message into a failure.
  - The attach wait gives up on a screen that keeps redrawing after `ATTACH_BUSY_MS` (2 s) once the prompt's box is up (`Pty::wait_attached`), not after 15 s; a quiet screen still ends it after 500 ms, and a screen with no box yet is waited for up to 15 s. The recording `Fake` pty of `exec_tests` keeps the pinned `wait_quiet(500, 15000)` call.
  - Open: a held reply can still wait while the turn is over when the job file says busy with nothing in flight and the transcript says over; a release from the transcript alone is not done.
- Replies to a session were held for good while it sat at its prompt (2026-11-15, job 9f3883da, `session.reply_held` at 05:56 and 06:41, never sent). Its live status was `shell`: Claude Code 2.1.322 writes `shell` when the model is idle and a background shell runs (`status = idle && backgroundShell ? "shell" : status` in the binary), and `turn_is_over` treated it like no live session, so the row was Working and not at its prompt, `Agent::turn_running()` held every reply and `takes_held_text()` never let one go. `shell` now counts like `idle` for `at_prompt` (`sessions/jobs.rs`); the held logic's own guards stay on for such a row because its group is Working: a fresh read of the files, the transcript's last `turn_duration` (`transcript::restart`) and the settle time. A status value the code does not know is the first thing to check when a reply is held and the transcript says the turn is over (`strings` on the `claude` binary finds the list: `busy`, `shell`, `idle`, `waiting`). Tests: `engine/src/sessions/jobs_prompt_tests.rs` (the job's exact shape, synthetic values) and `notchlingd/src/held_race_tests.rs` (reply at once, held text goes in, a new turn is still waited out).
- Replies to a session were held for good while its model sat idle and subagents ran (2026-11-15 10:11, job be50d36a, session fee7356b: `session.reply_held` then `sent_at_turn_end`, never sent; a model running six background subagents for hours). Claude Code keeps the live status `busy` while any background agent or task runs, and the job file stays `state: working`, `tempo: active` with `inFlight.tasks` up (`{tasks: 7, queued: 0, kinds: [artifact_watch, local_agent], drainableMonitors: 1}`), so the row was Working with `at_prompt` false: `turn_running()` held every reply and `takes_held_text()` never let one go. The shell fix above had not covered it: `turn_is_over` took `busy` as the turn being over only when `state` was `done` or `blocked`. Now `busy` with `inFlight.tasks > 0` sets `at_prompt` whatever `state` is (`sessions/jobs.rs`), and the flag means only "may be at its prompt", exactly like the `shell` case: the display group stays Working (notch, keep-awake, phone), and everything that acts on the flag goes through the checks already listed above, so the transcript decides. A direct reply asks `Rest::restarted` (`new_turn_since`): a prompt, tool result, assistant line or `<task-notification>` after the last `turn_duration` holds it, otherwise it goes at once; held text goes after a fresh read of the files, `restart::restarted` false, the `SETTLE_MS` settle and the guard at the first key. A running turn is still waited out, since its transcript ends in a prompt or assistant line, never in `turn_duration`; a `busy` row with nothing in flight keeps `at_prompt` false (it is the turn, and the open item above stands). What this now trusts the transcript for: a turn whose transcript has not been written for `STALE_MS` (10 min, one long tool call) reads as over, so a reply may go into it; Claude Code queues a prompt typed into a working session, as it does for a Chat reply sent mid-turn. A job file saying `working` with tasks in flight is no longer proof of a running turn by itself: tests that used it as the new-turn signal (`held_race_tests`, `fresh_tests`) now use `inFlight.tasks: 0` or a prompt in the transcript. Tests: `engine/src/sessions/jobs_prompt_tests.rs` (the job's exact shape, synthetic values) and `notchlingd/src/held_race_tests.rs` (`subagents_*` fixtures: reply at once, held text goes in after the settle, a prompt after the last `turn_duration` still holds, a turn starting inside the settle is waited out, no `inFlight` unchanged).
- A held message with a picture showed as one Queued bubble with a tall empty gap. Chat adds attached files to a message as `text\n\n<paths>` (`drops::with_attachments`), and the held text joins messages with a blank line, so `split_images` cut the path out of the middle and left `text\n\n\n\nmore`, three blank lines. `split_images` now keeps at most one blank line in text it took a picture out of; text with no picture keeps every blank line, and the join drops each earlier message's trailing whitespace and the next one's leading newlines (`engine/src/reply/held.rs`). Held messages still show as one bubble because they are one message when typed.
- Every Chat reply to a background job failed with `not_cleared` and the session could not be reached from Chat or the notch (2026-11-15 10:11, job 3dc1c4be). Its input box held a 33-character line (`reply-screen.txt`: 1 row, holding text, the cursor at its end, the status line under it): a message of ours that had gone in and not been sent (earlier that day replies failed as `not_taken` and `mixed`) or something typed in the terminal. The rule above made `require_free` refuse any text that was not the whole of the message being sent, and nothing in the app could empty a box, so the draft stayed until someone cleared it in the terminal. Three changes came out of it. (1) The daemon keeps the last five texts it tried to put in each session (`notchlingd/src/reply_attempts.rs`, in memory, 12 hours, dropped for a session when a send of it goes through) and hands them to the executor as `Clearing::earlier`; a box that holds the whole of one, or a start or an end of one of at least `MIN_PART` letters and digits (image chips ignored, a folded `[Pasted text #N +M lines]` never), is cleared with the usual keys and the new message goes on without asking. (2) Any other text is still never typed over: the reply fails as `not_cleared` with `data: {"why": "not_cleared", "box": <the text, cut at 1000 characters>}` on the error (`ApiError::data`, additive), and the text is in no file or log (`reply-screen.txt` stays masked). (3) `session.reply {clear_box: true}` clears with the same safe keys (Ctrl+E, Ctrl+U, Backspace per line; never Ctrl+K, Esc or Ctrl+C), waits until the box is empty (a box that does not empty, or one a person typed into meanwhile, is `not_cleared` again with nothing pasted and no Enter), then types and sends as usual. Chat shows the failure above the reply box with the text and a Clear Box and Send button that sends what is in the reply box that way (`chat/box_holds.rs`, `view/composer.rs::box_holds_row`); the Rust notch has no reply box yet, and the phone and CLI can pass the same flag. A held flush still waits on foreign text in the box (`BOX_NOTE`): Clear Box and Send does not reach it. The list in memory is lost when the daemon restarts, so a leftover from before a restart is foreign and takes the button. Held by `engine/src/reply/exec_leftover_tests.rs`, `engine/tests/reply_leftover.rs` (recorded screens) and `notchlingd/src/reply_clear_tests.rs`.
- Every Chat reply that carried a picture failed as `Mixed` while the text sat in the session's box, and the message went in later when something else pressed Return (2026-11-15 13:25, job be50d36a, text `i want click refresh it will refresh is it ok?` plus a dropped screenshot whose path has spaces, so it is quoted). Claude Code 2.1.325 turns a pasted line that is a readable path ending in .png, .jpg, .jpeg, .gif or .webp (quoted or not; several on one line are split before ` /`, ` '/` and ` X:\`; a line that mixes words and paths stays text) into an `[Image #N]` chip: the chips go in first (the first with no space, the next ones after one), then the rest of the paste, with the picture lines and the blank lines gone, so that paste shows as `[Image #48]i want click refresh it will refresh is it ok?` and the transcript's user line is that text. A path it can't read (or is refused) stays as text, and when none can be read the paste goes in unchanged (read it in the binary: `strings` on `~/.local/share/claude/versions/<version>`, then `tengu_paste_image` and `input_image_drag`). `Input::fill` (b3b97c7c, 2026-11-15 06:26) compared the letters of the box with the letters of the message: `Image48` and the path's letters made the box `Foreign`, so `await_paste` ended `Mixed` at its first look, with no Enter, on a box that held the whole message. The fakes pasted the text as it was and never made a chip, so every executor test passed; `leftover_of` had learned to drop chips (1a73db2e) but still compared with the whole text, so a short message with a picture (`ok` and a path) was foreign too. How it was told: `audit.jsonl` has two `session.reply` failures 3 s apart (`not_sent`, which `acting_events.rs` gives `NotSent` and `Mixed` alike) and nothing after them; `reply-screen.txt` (masked) has the last try's box as one row of 57 characters in words of 6, 5, 4, 5, 7, 2, 4, 7, 2, 2 and 3, its first note `clearing what an earlier try of ours left in the box` with the cursor at the same column, so the second try cleared the first's text (no double) and left its own; the transcript has the user line `[Image #48]…` (no queue operation) 17 s after the second failure and no `[Image #47]`. Notchling writes Enter only in `submit`, after `Whole` or `Folded`, so that Return came from outside the reply path, most likely pressed in the terminal as the error says; the logs can't name who. A false failure that also delivers makes the person send again, and had the first try's text still been in the box when they pressed Return, the second send would have gone out twice. Now `fill`, `carries` and `leftover_of` read an `[Image #N]` chip as one of the message's picture paths (`input_box.rs::Message`): with N chips the box must equal the message with N of its picture paths taken out, whichever N (a path that couldn't be read stays in the box), up to 8 pictures and, beyond that, all or none. A picture path is a token on a line of nothing but path tokens, in the form Chat writes (`drops::with_attachments`: `text`, a blank line, then the paths separated by spaces, each bare or `'…'` with `'\''` for an apostrophe; the phone's `"…"` form too), each with a directory (`/dir/…`), and a picture extension. A path inside a sentence, a slash command (`/fix the bug in a.png`), `/review /tmp/a.png` and a phone caption line (`hello /tmp/x.jpg`) are text, as in Claude Code, so a chip never stands for them. The line is read piece by piece, as the 2.1.325 paste handler does (in the bundle, the paste handler that logs `input_image_drag`: it splits each line before ` /`, ` '/`, ` "/` and ` X:\`, and with more than one piece every piece must look like an absolute path or the whole line stays text; then each piece with a picture extension is read and the others stay in the paste as text), so `/v1/users /tmp/shot.png` becomes `[Image #5]/v1/users` and that box is the message. A re-review took that for a false positive and asked for every token to be a picture; that would block a screenshot dropped with a `.rs` or `.pdf` on one line, and the box it reads as ours is the one Claude Code makes. A chip is the person's, and the box is `Foreign` (or not a leftover), when there are more chips than pictures: a leftover is never matched against the whole text any more, which had let a foreign `[Image #5]` beside words like ours be cleared as ours. A message that names a chip in words (`why does [Image #1] fail?`) and has no picture path is compared raw: no chip is taken off either side, so the box must hold the same words with the same chip text, number and place, `Part` is a raw start of it and a long one is `Folded` as before. An earlier version took the literal chips off both sides by count, and then a chip of the person's stood in for the message's own (`[Image #1]` against a box holding `[Image #5]` was `Whole`, and `why does fail?` after `[Image #5]` was `Whole` and a leftover), so Enter would have gone to text the person wrote. A message with such words and picture paths both is never taken for ours: the chips Claude Code makes can't be told from the ones it names, so `fill` is `Foreign` for any box that isn't empty, `carries` and `leftover_of` say no, and the reply ends `Mixed` before any Enter (rare, and a blocked send is safe). Chips with no words yet are `Part`; chips and a `[Pasted text #N +M lines]` are `Folded`; a chip alone is never a leftover (it may be a picture the person pasted). Held by the unit tests in `input_box.rs` and `input_box_picture_tests.rs`, `tests/fixtures/input-box/picture-after-words.txt` (the recorded screen of `pictures-left-unsent.txt` with this incident's box row; `terminal_input_box.rs`, `reply_leftover.rs`), `FakePrompt::reading_pictures` (the same paste transform in the fake, its chip numbers never repeat) with `exec_send_tests.rs` and `exec_leftover_tests.rs`, and `notchlingd/src/reply_clear_tests.rs`.
