# Chat's Details Panel and Changes

The Details Panel's rows (subagents, delegated jobs, paging), its Git section, and the Changes and Branches panels.

Part of the Rust app's notes, moved from `crates/AGENTS.md`; the index is in the root `AGENTS.md`. Keep it true: change the note with the code, and add what bites you under Things that bit before.

- **Details Panel rows** (`chat/paging.rs`, `chat/subagent_rows.rs`, `engine/src/transcript/glance.rs`, `chat/loader.rs`). A model compute and a draw do no file I/O and start no process: the subagent rows are built by the loader off the main thread and arrive as `Loaded::subagent_rows` (data, with `subagent_counts`), and the view only keeps them. A row shows two facts that come from the subagent's transcript: its context tokens (the last assistant `usage`) and, for a running one, its doing line (the newest step). Both come from one small tail read, never the 4 MB chat tail: `glance::peek` reads the last 64 KB, widens to 256 KB then 1 MB only for what it has not found, and stops at that cap (`Window`, `widen`; the doing line runs the normal parser over the first window that holds a step, and later windows only look for the number). The inspector takes the subagent counts once, from `inspector_listed`'s argument. The engine's subagent and Codex `Cursors` (limit 30 files, LRU) are for a subagent the user opens and for Codex sessions; a row never uses them, so no number of subagents can thrash them. `SubagentRows` keeps each read by file size and mtime, so an unchanged file is never read again and a changed one is read once. `Page` (`paging.rs`, used by subagents and by shells) decides which rows exist at all: on open every running subagent and only those, else the 3 newest; a row not shown is not read and not drawn; `Load N More` (10, newest first) bumps `more_subagents`, asks for a load and the loader reveals and reads the next ones; a subagent that appears later goes to the top and the shown rows stay; running ones that finish stay shown; another session starts the first page again. The section title counts all of them (`SubagentCounts`). After a `/clear` the list also holds the subagents of the transcripts the clears ended (`engine::transcript::subagents::list_across_clears`, called by `ClaudeSubagents::list`, so `Registry::subagents` has them with the rest: `chain` follows `locate::predecessor` at most 4 transcripts back, the same walk `delegate_jobs::parent_ids` uses, and `list_chain` lists the folders newest first; `chat/cleared.rs` re-exports `chain` and `list_across_clears` as `subagents`). An agent id in several folders is one row, from the newest folder (what opening it reads), with the description, type and model of the first `meta.json` found, since a subagent running at the clear goes on in a new file in the new folder with no `meta.json`; showing both halves of it is a limit. The earlier transcripts cost no Chat parse and no shared cursor: their endings come from `engine::transcript::finished::read`, a streaming scan of the last 4 MB (`WINDOW`) that parses only the lines carrying a `<task-notification>`, an agent's tool result, or a TaskStop/KillShell call and its result, with the parser's own rules (`subagents::result_end`, `shells::Stops`, which records a stopped shell or agent as `stopped`), cached by file size and mtime, and a completion that lies before the window or in a `continued-in` ancestor is not seen (the "report delivered" check in the subagent's own file still ends it). The endings of the whole chain and of the current conversation are merged before any folder is judged, since a notification lands in whichever transcript was current when it arrived. They sort by start time with the rest, so they sit below the current transcript's and follow the same paging. The engine's `subagents::list_chain` remembers its "report delivered" tail check by file size and mtime, so listing many old folders each load reads no unchanged file; `tail::RAW_BYTES` counts the bytes those two raw reads take (`PARSED_BYTES` never sees them), and `tests/subagents_before_clear.rs` holds that an unchanged second load adds none to either counter. The list is a tree since provider contract P1: `Registry::subagents` returns every tool's native children and the delegated jobs in one list with `depth` and `parent` (a Codex child with a job of its own is two levels), and `paging::Tree` pages it: depth one as above, a row with children starts collapsed (a disclosure with the count at its right end; `ChatView::toggle_group` asks for a load), an open row's children are paged the same way under it (`Page` per group, `Load N More` by `more_under`), collapsed children are counted and never read, so only shown rows are glanced. `open_groups` and `more_under` clear when another session is selected. A Search hit for a Codex child opens its parent and then the child's row (`PendingChild`, three loads at most). Shells follow the same rules, over the transcript's own record and then the probe (`shell_list.rs`: `ShellPage` over a shell's `finished_agents` entry and the probe's answer for its output file): a shell the transcript never ended (a crashed or exited session) is unfinished until the probe says no process writes its file, so the first page is made only once every unfinished shell has an answer. Until then the listing is `waiting`: the 10 newest, no `Load N More`, and the probe asks about every unfinished shell that has no answer. After that a shell with no writer counts as ended for paging and is never asked about again; the first page is the ones with a writer, else the 3 newest ended; `Load N More` reveals the next 10 at once in the view (`ChatView::load_more_shells`, no load needed), a new shell goes to the top and is probed, and shown shells stay shown. `chat/view/shell_probe.rs` asks `lsof` in one call per 100 paths (`-F pcan`; `shells::parse_writers_by_name` reads the names back for that chunk: a path matched by itself, its real path or a file name nobody else shares, and every writing line when the chunk holds one path), never one process per shell, and a failed spawn records nothing (an lsof that cannot run must not mark every shell ended); a result that changes the listing redraws the Details Panel. A shell not probed yet shows Running, as before, and only shown shells are ever in the model. The Output tail is read on the click (`open_shell_output`), never in a compute. The opened subagent's header takes its tokens from the conversation the open read already parsed.
- **Changes** (`chat/branch.rs`, `chat/branch_rows.rs`, `chat/view/changes.rs`, `chat/view/changes_panel.rs`, daemon ops `git.branch_diff_stat`, `git.branch_diff_file`, `git.branches`). A click on a row of the Details Panel's Git section (see Git section below) opens the Changes panel for that worktree, which takes the Details Panel's place (a window-drawn panel at the file panel's width, drag edge and `Page Panel` slot, and the file panel opens over it: closing the file panel shows Changes again). The stat comes in the same background task as `git.status`, after it and only for a repository, so it has the Gate's cadence; `repo::State::branch` holds the session's own `Arc<BranchModel>` (the Git section's current row reads its totals and base) and an unchanged one is dropped before the panel hears of it. The stat covers merge-base..HEAD plus uncommitted work (each file says `uncommitted`, the header says how many); the base is the nearest base (the stat is asked with `pick: "nearest"` and names it in `base`; the Git section's "vs main" is that name) until the user picks one from the base menu (`git.branches`, asked when the menu opens), kept in `base_choice` and forgotten when the folder changes; a base the daemon refuses falls back to the nearest base. `ChangesPanel` is its own entity drawn as a cached part: a model pushed in by `ChatView` (`set_model`, `set_slot`, `set_branches`), its own filter (a single-line `TextEditor`), the expanded files (`open`, a `Slot` each: loading, ready chunks, failed) and a GPUI `list` over `branch_rows::rows` (File rows and diff chunk rows, 80 lines each, from `git::chunks`), so only the rows on screen are built, and a change replaces only the rows that differ (`branch_rows::splice`; a filter resets the list). Nothing in a draw or a compute reads a file or the socket: an expanded file's patch is asked on the click (`toggle_change_file`, off the UI thread), and a stat that changes a file's counts asks again for the open ones only (`branch_rows::refetch`). Rules: the panel's own handlers never call `ChatView` inside an update of the panel (they are `on_click` closures over a `WeakEntity<ChatView>`), and `ChatView` never updates the panel from inside one; the list's row closure reads only the `Arc`s it captured. The file panel's open action for a branch file sets `repo::State::diff_via` (the base and the rename's old path), so its refresh asks `git.branch_diff_file` instead of `git.diff` (a committed file is not a `git.diff` file); `open_git_diff` clears it. `NOTCHLING_RENDER_CHANGES=1|expanded|menu` with `--render chat-git` shows the panel, a file open and the base menu over made-up data. Changes has a target (`chat/changes_target.rs`): the session's own folder, another worktree (`worktree: <path>`) or a branch with no worktree (`ref: refs/heads/x` or `refs/remotes/origin/x`, committed work only, so the counts line says no uncommitted files and the base menu leaves out the branch's own name). The session's own `BranchModel` and `base_choice` stay in `repo::State` and keep feeding the Git section; another target has its own `TargetState` (`repo::State::other`: its `BranchModel`, `base_choice` and a `refused` reason), used only by Changes and cleared when Changes closes or the selected folder changes (`on_close`, `on_folder_change`), so closing Changes never leaves another branch's numbers on "this session" (`closing_other_target_keeps_own_numbers`). `shown_branch` picks which one the panel draws. The Gate's background task asks the target's stat after the session's own, while Changes shows; a reply for a target or base that is no longer asked is `Ignored` or `Retry`, an answer that arrives while the target changed asks again (`needs_ask_again`), and a target the daemon refuses (a worktree removed meanwhile, a branch deleted) shows "Nothing to compare." with the reason and stops asking until Changes closes. An open file's patch and the file panel's refresh go through `DiffVia` (the target, base and rename source), so `git.branch_diff_file` reads the right tree. A new `.html` file's page is offered only for the session's own target (`offers_page`).
- **Git section** (`chat/worktrees.rs`, `chat/view/worktrees_ask.rs`, `chat/view/repo_section.rs`, `chat/git_gates.rs`, daemon ops `git.status`, `git.worktrees`, `git.branch_diff_stat`). One line of numbers per worktree of the session's repository and no file list (files are in Changes). First the session's own worktree ("this session": the one `git.worktrees` marks `current`, from its `worktreePath` when the session ran EnterWorktree, else its `cwd`, and the session appears once), then one row per other worktree (running ones first, then by path, at most `SHOWN_WORKTREES` = 6), then one "›" row. Every right side is the worktree's work against its nearest base, uncommitted included; the current row takes it from the stat and moves its uncommitted count and lines into its sub-line (`5 uncommitted +52 −9 · last 2 m ago · even with origin · vs main`); another row's sub-line is `23 files · 2 ahead`, then `running 41 m` with the working dot when a session or subagent works there, `needs input`, or `last 6 m ago`. A worktree whose work was never read shows its branch and "2 ahead" with no line counts; a missing folder shows "folder missing" and does nothing on click; a branch with no common history shows "no common history". The title is "Git" with one worktree and else `counted_title` ("Git · 2 running", "Git · 3"). The "›" row reads `main and 39 branches ›` (the default's short name and `no_worktree`), `39 other branches ›` when a worktree has the default's short name checked out, `4 more worktrees · main and 39 branches ›` past six rows, and `4 more worktrees ›` alone when no other branch is left (the hidden worktrees are counted somewhere); it opens Branches. Everything in the model is pure over data (`section`, `occupancy`, `owner`): a draw and a compute do no file I/O and start no process, and an unchanged reply is dropped before the part hears of it (`WorktreesState::apply`). Which session or subagent is in a worktree is matched in the app, with no I/O: a session's folder (`worktrees::session_folder`) or a running subagent's `cwd` (the newest transcript line's for Claude Code, the rollout's `session_meta` for a Codex child or delegated job; an Antigravity subagent has none) belongs to the worktree whose `path` or `real` is its longest component-wise prefix, so lanes under `.claude/worktrees/` inside the main checkout work; the state comes from the live session list, so the dot changes as soon as the Sidebar does. The cadence is a `SlowGate` of the Gate's shape, one per op (this one and the Branches feed's), so opening Branches never waits on a Details call: at once when the panel opens or the folder changes, after a turn ends or when a matched worktree's occupancy kind changed (1 s floor, those paths named in `fresh`, at most two, by `fresh_after`: only paths present before and after whose kind changed; a new worktree is not "fresh", the daemon reads missing ones first anyway), every 15 s on the tick, one call in flight, and only while Details shows and `git.status` said it is a repository. The ask after a session list change runs from `apply`, once the sessions and subagent rows are stored (asked from the tick it saw the old rows and the floor swallowed the real ask), and the first reply seeds the kinds. A failed call keeps the last good rows. Ages ("last 6 m ago", "running 41 m") are computed from a clock rounded down to the minute (`minute_ms`) and under a minute read "just now", so a running clock never redraws the part; the tick rebuilds the Details model once when the minute changes while Details shows (`MinuteGate`), so an idle session's ages move. A `git.status` answer asks `git.worktrees` only for the first answer of a folder or while no rows are held (`opened_wanted`); after that the 15 s tick sets the cadence. `--render chat-git` shows the section over `worktrees::preview()`, which is clock-free (`PREVIEW_NOW_MS`).
- **Branches** (`chat/branch_list.rs`, `chat/branches_state.rs`, `chat/branches_preview.rs`, `chat/view/branches.rs`, `chat/view/branches_panel.rs`, daemon op `git.branch_list`). Read-only: the panel takes the slot Changes takes (a window-drawn panel at the file panel's width, drag edge, `Page Panel` slot, part tag "Branches Panel"), is its own entity drawn as a cached part with its model pushed in by `ChatView` (`push_branches`), and has three tabs that are views, not a partition (`in_tab`): Working (every worktree, and the bases that have none), Not Merged (a branch not merged into a base, or a worktree with uncommitted work; never a base) and Merged (merged into a base, with no worktree or a clean one whose work was read, so a worktree whose work was never read waits; never a base), a filter (every word anywhere in the branch name, worktree path, session name or subject, any case), and groups Worktrees (this session's first, then running, then by path) and No Worktree (newest commit first). The bases (the default and the integration branch) are never classified, so `main` does not read "merged into agent-run-oss". Merged comes from the counts (0 ahead of a base), never from `for-each-ref --merged`. A row's right side is its work against its base: a worktree's `work` (uncommitted included), else the branch's committed `lines`, "…" while pending, empty for a merged branch or a base. A click opens a row's button line (one at a time, no hover-only buttons): Changes (off for a name `clean_ref` refuses and for a missing folder), Open Session (only with a matched session or subagent), Show in Finder (only a worktree whose folder exists, `cx.reveal_path`). Commit subjects and remote branch names are other people's text: plain one-line labels, never markdown or a link, already cut by the daemon at 120 characters. Changes opened from here replaces Branches in the slot and closing it shows Branches again (`changes_from_branches`, `after_close_changes`); closing Branches shows Details; "Hide Details" closes the file panel, then Changes, then Branches, then Details (`hide_step`). Two states hold the feed: `Feed` (the last list for one folder, the last error, a gate of the 15 s `SlowGate` that asks again after `PENDING_AGAIN_MS` = 2 s while the list has pending rows, and a generation) and `Shown` (the tab, the filter, the open row, the model the panel draws). A session switch with Branches hidden forgets the feed and bumps its generation, so another repository never shows the old list; with it shown the panel reloads for the new folder, resets the open row and the filter, and closes when the new session is in no repository. A reply of an older generation is `Stale` and never touches the gate; `list_for(folder)` and `failed_for(folder)` hand out nothing for another folder. `Shown::set_input` keeps the last list when an error arrives after a good reply. The panel makes no call from a render root or a fixture root, and hidden it asks nothing. `NOTCHLING_RENDER_BRANCHES=working|not-merged|merged|open-row|loading|error|empty` with `--render chat-git` shows each state over made-up data.

## Things that bit before

- Opening one large Claude Code session made Chat sit at 87% CPU: the Details Panel's model compute (every `cx.notify()` on `ChatView`) built each subagent's row on the main thread by parsing its transcript's 4 MB tail (`inspector::subagent_row` into `read_subagent_shared` and `codex::read_shared`) for two small facts, and the engine's cursor cache holds 30 files, so a session with more than 30 subagents or Codex jobs missed on every file at every compute (116 MB parsed per compute in the reproduction: `crates/app/tests/subagent_reads.rs`). A model compute and a render read no file: facts a row needs are read by the loader, from a small tail, only for rows shown, and cached by size and mtime. No listed rule covers this (the `CAP-*` rules look at writes, processes and network, not reads on the draw path): proposed as `LINT-NO-IO-IN-MODEL`, a `model` or `render` function in `chat/`, `notch/` or `search/` that names `std::fs`, `File::open`, `Command` or an engine `read_*`/`Cursors` reader fails the lint; its bad example is the old `inspector::subagent_row`.
- Switching sessions in Chat took seconds after the providers' subagent walk (`Registry::subagents`) arrived: it asks the Codex child source once per delegated Codex job, and the app's source opened a new daemon connection per ask (about 28 ms each: 289 jobs, 9 s a load; the fixture fallback `DayFolders` re-read two day folders' heads per ask, 7.5 s). A load holds the one `Loader`, so a switch waited for the selected session's load and then its own. Now the asks share one connection per walk (`chat/codex_children.rs::Kept`, closed by `ChildSource::done`), `DayFolders` keeps heads, and a switch's first load is partial (no subagents; the full one follows at once). Measured on a copy of real data (`crates/app/tests/switch_reads.rs` holds the counts): 9,085 ms to 34 ms a load for 322 subagents, a switch shows its conversation in 5 to 20 ms. A new per-row ask in a walk must not open a connection or read a folder per row.
- A Claude Code background job showed "no running subagent" while its status line said "1 agent": the main thread had brought a finished background agent back with `SendMessage` (the result says `Resuming agent`, `toolUseResult.resumedAgentId`), and the agent's first `<task-notification>` (`completed`) stayed in `finished_agents` for good, so `subagents::status_of` said Completed for a file still being written. A resume now writes the word `resumed` under the agent's id (`subagents::resume_end`, called by the conversation parser and by `finished::read`, so an earlier transcript in the chain is read the same way); `status_of` takes any word it does not know as "not ended" (Running while the file is fresh, else Quiet), and a later notification replaces it. The "report delivered" check of `handed_back` has the same shape: a resumed agent's file still holds the old `Report delivered to your caller` line, so it counts only when no `user` or `assistant` line and no half-written line follows it (44 of 47 finished agents in the reproduction end exactly on it; a resumed one has its coordinator message and work after it; housekeeping records after it, such as `turn_duration`, do not matter), and never for an agent whose parent recorded `resumed`. A `resumed` agent is cut work again for a cluster promote (`outward::agent_reported` skips the word). Fixtures `engine/tests/fixtures/background-job/`, tests `transcript_agent_resumed.rs` and, through the loader with a job row whose transcript is its `resumeSessionId` file, `app/tests/subagent_resumed.rs`. No rule in `docs/rules.md` covers transcript meaning, so none could have caught it.
- Shells showed nothing for a job whose subagent had started them: a Bash call that outruns its timeout is not a `run_in_background` call, and its result says `Command was moved to the background (ID: …) after running for 180s. Output is being written to: …output`, not `Command running in background with ID: …`, so `shells::launch` never saw it (`transcript_shell_moved.rs`). Not yet: shells a subagent starts live only in that subagent's own transcript (a sidechain, never read for the main conversation's `shells`), so the Details Panel still lists none of them. Claude Code's job `state.json` has a `fan` list of what is in flight (`id`, `kind` agent or shell, `label`, `startedAt`), and the transcript tail of each running subagent has the launches; reading either for every row costs a read per running subagent on every load (`app/tests/subagent_reads.rs` holds that only shown rows are read), and a finished subagent's shells need a "still alive" answer, which today only the output-file probe gives.
- Branches would have shown one repository's list on another session, and a late reply of the old folder cleared the new call's in-flight flag, so two `git.branch_list` calls ran at once: with the panel hidden a session switch kept the feed's list, and a reply called `skip()` on a gate that had been reset. Found in review before it shipped. A hidden switch now forgets the feed and bumps its generation, an older reply is `Stale` and leaves the gate alone, and the feed hands out nothing for another folder (`hidden_switch_forgets_the_old_folders_list`, `stale_generation_reply_leaves_the_gate_in_flight`, `list_for_another_folder_is_none` in `chat/panels_tests.rs`). The Details Git section had the same shape: its worktrees ask ran on the tick before `apply` stored the new session list, so the occupancy it compared was the old one and the 1 s floor then swallowed the ask that should have followed (`fresh_uses_the_sessions_after_they_are_stored`). Ask after the data is stored, and give every in-flight call the identity of the folder it was asked for.
