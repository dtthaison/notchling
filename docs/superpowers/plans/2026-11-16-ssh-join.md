# Add Machine over SSH Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** From the Cluster sheet, the maintainer types an SSH address (or presses Join Cluster on m1 or vps-sing-1); Notchling checks the machine, shows one plan, and on one click installs only the headless `notchling` daemon as a service (a LaunchDaemon on a Mac, a systemd user unit with linger on Linux) and joins it to the cluster with an invite the primary accepts without a second click. When this Mac's Notchling changes, Update N Machines brings the others to the same build.

**Architecture:** The flow runs in the app's process on the engine's Machines library (registry, steps, `SetupEngine`, `ProcessRunner`), so it is app tier. The engine's Machines steps gain a node-only profile, a Mac node install (bundle-shaped path, this Mac's own daemon binary, a LaunchDaemon), a Reaches the Primary check and a join through an invite. The cluster core gains invites: join tokens bound to one node id, made only through the new app-tier op `cluster.invite`, which the primary approves on arrival. A build id (`NOTCHLING_BUILD`) in every binary and in `Versions.build` drives the update offer. `tools/build-node.sh` makes the static Linux builds.

**Tech Stack:** Rust (engine, notchlingd, local-api, events, GPUI app), shell (`tools/`), GitHub Actions (`rust.yml`), Fluent locale files.

**Spec:** `docs/superpowers/specs/2026-11-16-ssh-join-design.md`. Every implementer reads the sections its task names. The Builder's calls B1 to B18 are settled and not reopened. The spec's "Needs the maintainer" answers may change Tasks 9 (LaunchDaemon, question 2), 12 and 15 (Tailscale, question 5), 4 and 5 (the invite, question 1) and 12 (the Acting default, question 6); a task touched by an open question waits for its answer.

**Base and branch:** build on `agent/ssh-join` from the latest `origin/agent-run-oss` **after lane E wave 3 (`agent/cluster-v1-e-wave3`) has merged** (see Order). Never commit to `agent-run-oss` or `main`; never force-push; the maintainer merges.

## Global Constraints

- Packages: `notchling-engine`, `notchling-notchlingd`, `notchling-local-api`, `notchling-events`, `notchling-app`. One test filter per `cargo test` run.
- No comments in code, doc comments included (`python3 tools/strip_comments.py --check`); the why goes in the crate's `AGENTS.md`.
- Files under 1,000 lines (600 warns). `crates/app/src/cluster/view.rs` (744) and `model.rs` (666) only gain the few lines named; new code goes in new files. Tests in `tests_<area>.rs` (engine machines) or `<module>_tests.rs`.
- Tests never run ssh, scp, `gh`, `launchctl`, `systemctl`, `tailscale` or `claude`, and never read the real `~/.claude`, `~/.ssh` or Keychain. Fakes: `ScriptedRunner` (`engine/src/machines/runner.rs`), the Machines fakes (`fakes.rs`, `fakes_b.rs`), `NoCluster` and test `ClusterTokens`, the core's test transports and simulator (`cluster/sim/`), e2e daemons with `NOTCHLING_DATA_ROOT` over copied fixtures and `NOTCHLING_CLUSTER_LOOPBACK=1`.
- Secrets travel only in `Call::stdin` (the join token, the admin password); the Fix context refuses a call whose argv or env holds one (`runner.rs::Call`). Nothing writes a token or password to a log, an event, the Audit, the Activity, `cluster.status` or a Fix log.
- Anything a machine reports is untrusted: only a value that passed `shell::is_safe_machine_path` or an alphabet check enters a script, path, argv or file.
- The local API changes additively: one new op `cluster.invite` (`OpSpec::APP`) in a new block at the end of `wire.rs`'s `ops`; new optional fields only. `cluster.join.token` and `cluster.join` keep their shapes and tiers.
- No daemon switch is turned on by a file or a service file argument. The service files carry only `daemon`.
- User-facing words short and plain, buttons in Title Case, in `locales/en/mac/cluster.ftl` (checked by `tools/locale/gen.py`); the Machines engine's step titles stay where they are.
- Never run `./build.sh --install` or `tools/bundle-next.sh --install`; only the maintainer installs and merges.

## Review Focus

1. **No approval without the person.** An invite can only be made at the app tier, from this Mac or a client at App origin (`CLIENT` rule), and admits only its node id; a token without an invite still raises the Inbox's Add. (Task 4 `invite_from_its_node_approves_without_join_request`, `invite_from_another_node_is_refused_and_spent`; Task 5 `agent_cannot_invite`, `standby_without_app_cannot_forward_invite`; Task 10 `machines_binary_falls_back_to_token`.)
2. **Nothing runs before the click.** Check, Refresh and Join Cluster's check record no Fix call; Install and Join refuses when a shown display changed. (Task 12 `check_runs_no_fix`, `run_refuses_changed_display`.)
3. **The join token and the admin password stay on stdin.** (Task 10 `invite_token_only_on_stdin`; Task 9 `launchdaemon_fix_password_only_on_stdin`; Task 5 `status_invites_hold_no_token`.)
4. **A Mac node's daemon is one its own clients trust.** The binary is inside a `*.app/Contents/MacOS` folder and the plist names the real path. (Task 9 `mac_node_path_is_allowed_by_server_trusted`, `todays_mac_path_is_refused`.)
5. **An update never kills work.** Machines with running shell jobs are skipped unless Update Anyway; the plist abandons the process group; Linux keeps `KillMode=process`. (Task 11 `running_shell_jobs_skip_the_machine`; Task 9 `plist_abandons_process_group`.)
