# Reading transcripts

How much of a transcript is read, queued and dequeued entries, and a session continued under a new id.

Part of the Rust app's notes, moved from `crates/AGENTS.md`; the index is in the root `AGENTS.md`. Keep it true: change the note with the code, and add what bites you under Things that bit before.

## Things that bit before

- Base64 images (a Read of a .jpg is one line of 0.5 to 1.8 MB) filled the 4 MB tail read and pushed a Codex session's first prompt, then a Claude Code session's whole conversation, out of Chat. A window is a budget of parsed bytes, not of file bytes: `Cursors::skipping_lines_over` (Claude Code's Chat, subagent and notch readers) neither holds nor counts a line over the parser's cap (`transcript/scan.rs` streams past it) and looks back at most 64 MB of file for the budget; Codex's `long_lines_free` counts only lines up to 100 KB but still reads the rest. A skipped tool result still finishes its step (`Parser::consume_oversized`). The search index's tail works the same way. Not yet: the phone's `chat::read_window` and `viz::facts` take a plain byte tail.
- A `dequeue` line doesn't say which queued entry it took (Claude Code 2.1.322 took a notification before older ones); the user line after it corrects the guess (`transcript/conversation/queue.rs`).
- A bash-mode message (`! git branch`) sat as "Queued" for good: Claude Code queues it as plain `git branch`, but the user line that takes it is `<bash-input>git branch</bash-input>`, so the correction never matched and the guess (the oldest entry) stayed the one removed. An older entry nothing ever removes made the guess wrong: an `<agent-message>` is delivered inside a tool result line or behind "Another Claude session sent a message:", with no `remove`, and Chat hides entries starting with `<`, so it sat unseen at the head. `Queue::user_line` now reads a `<bash-input>` line as its command; the phone's `chat::parse` takes the waiting entry on a bash input and on `popAll`. Entries still unmatched stay in `Queue::items` unseen; a new kind of wrapped user line needs a case in `queue::names`. No rule in `docs/rules.md` could have caught it (they check structure, capabilities and weakened tests, none reads transcript meaning); a fixture with the real shape does (`engine/tests/fixtures/queue/`, `transcript_bash_input.rs`).
- A message sat as "Queued" for good after Claude Code restarted: its input queue is in memory, so an entry enqueued while it was busy is lost with the process, and no `dequeue`, `remove` or `popAll` is ever written for it. A typed prompt line that no `dequeue` just before it explains means Claude Code was idle, and an idle one drains its queue first, so `Queue::user_line` (and the phone's `chat::parse`) drop every entry enqueued before it; entries after it stay. `transcript/typed.rs::typed_prompt` says which lines count: not `isMeta`, `isSidechain` or `isCompactSummary`, no `tool_result` block (an agent-message delivery rides in one), not `<local-command-…>`, `<command-name>` or `<task-notification>`, not an interrupt; plain text and `<bash-input>` do. A new kind of wrapped user line is safe until it looks like plain text; fixture `engine/tests/fixtures/queue/lost-queue.jsonl`, `transcript_lost_queue.rs`.
- Claude Code can move a running session into a new session id (sending it to the background): the old transcript ends with a `continued-in` record and the new one starts with only an `ai-title` and an `agent-name`, so Chat said "No transcript yet" and the notch row had no history, while `/clear`'s successor lookup (by agent name) never saw it. `transcript::continued::earlier` follows the record back, and `conversation::read_shared` and `snapshot::read` put the earlier sessions first, but only while the new one has no messages of its own: once it gets going Claude Code copies the old messages into it, and joining then showed them twice. The app's `Locator` falls back to the newest earlier file while the new one doesn't exist. The daemon's `transcriptPath` for such a row is still null (the engine only knows a job's `linkScanPath`; the app finds files by id), and the phone's chat view (`chat::read_window`) does not join yet.
