# Ask

An agent asks you a question with `notchling ask` and gets your answer back, without the main model relaying it.

Part of the Rust app's notes; the index is in the root `AGENTS.md`. Keep it true: change the note with the code, and add what bites you under Things that bit before. The ops, arguments and exact refusal words are in [local-api-ops.md](../local-api-ops.md#ask_opsrs); why it is built this way is [the decision](../decisions/XXXX-ask.md) and [the design](../superpowers/specs/2026-11-16-ask-design.md); the probes behind the rulings below are `crates/engine/tests/fixtures/ask/`.

- **What it is.** `notchling ask [--choice <text>]... -- <question>` saves a row in the `asks` table of `notchling.db` (class Node, schema 5; `engine/src/ask/store.rs`, the daemon its only reader and writer) and waits. The question shows as a card under the asking session in Chat, in the notch and in the Inbox (so on the phone), naming the agent, its branch and how long it has waited. Your answer goes to the waiting command, which prints `Answer: <text>` and exits; the model is not involved. A waiting agent spends no tokens.
- **The three rules** (decided in the source design, not reopened).
  1. Notchling works out who asked; the agent is given no token.
  2. Only you answer by default. The main session may answer a question from its own subagents or delegated jobs only when the asker passed `--main-may-answer`; the card then says "Answered · main session". No agent answers a question meant for you, and no agent of another session answers at all.
  3. A restart doesn't lose a question. The waiting `ask` reconnects with the same id; an answer given while the daemon was down, or before the command reconnected, waits in the table until it is handed over.
- **Who waits how.**
  - A Claude Code background subagent runs `ask` with Bash `run_in_background: true` and ends its turn. The command's exit wakes it and it reads `Answer:`. Its report reaches its caller only through SubagentHandback, so it calls SubagentHandback again after the answer; plain text at the end of a woken turn is not delivered (the skill says so; it never says to call SubagentHandback to wait, which ends the run). Current Claude Code has no foreground subagent.
  - The main session does the same: background command, end the turn, the exit wakes it (P3, P6). It sees its subagents' questions it may answer with `notchling asks --wait` in the background and answers with `notchling answer <id> --choice <n>` or `-- <text>`. Notchling never types a question into the main session (M5).
  - A Codex or Antigravity job under `notchling delegate` runs `ask --wait` in the foreground and blocks inside its turn: no background command wakes those tools. `--wait` stops by itself 60 s before the delegate's deadline (exit 124); the delegate gives its child `NOTCHLING_DELEGATE_DEADLINE_MS` (`codex_run.rs`, `agy_run.rs`) and `ask --wait` sends `min(own timeout, that - 60 s)` as `deadlineMs`. The `--wait` default is 900 s; without `--wait` the command waits without end.
  - A read-only Codex job can't ask: its sandbox denies the process listing and the unix socket (EPERM), so `ask` exits 3 (P4, M4). Only `--write` jobs ask; the sandbox is not widened. The skill says so for Codex.
  - A process in no Claude Code session (a Codex or Antigravity session Chat runs, a shell) is refused: `Notchling can't tell which session is asking.`
- **The agy allow (M3, R2).** The delegate declines every agy `session/request_permission` except edits with `--write`. `delegate/agy_ask.rs::allows` adds one: an `execute` request whose command line (`toolCall.rawInput.CommandLine`, else `args.CommandLine`, never `title`) is exactly this notchling's absolute path (`Deps::notchling_binary`, `current_exe()`), then `ask`, `--wait` and words, as one simple command, and made only of letters, digits, spaces, `-_./,:@+%` and quoted text without `$`, a backtick, `!` or a newline outside single quotes. It is allowed once, never always. The bare name `notchling` is not accepted (it runs whatever `PATH` finds first, R2; the maintainer confirms), and an empty or relative binary matches nothing. Everything else is declined as before. The agy skill note gives the full quoted path and single-quoted words.
- **How the asker is found.** The session comes from the kernel: the peer's parents are walked (16 steps, `notchlingd/src/caller_session.rs`, moved out of `hook_ops.rs::session_of`) to the Claude Code process whose `sessions/<pid>.json` names a session. Facts about the process (start time, command line, executable, the path of its stdout, working folder) come from `notchlingd/src/process_facts.rs` through `vault_caller::Processes`; its macOS constants (flavor 2 of `proc_pidfdinfo`, 1200 bytes, the path at offset 176) were checked on a real file, and its Windows side answers `None`. Which agent inside the session asked comes from the transcripts (`engine/src/ask/find.rs`, `notchlingd/src/ask_find.rs`): a stdout file `….output` that a transcript's background-launch result names, else the Bash command line (P1, P2, P7). It is a label, not proof: any agent of a session can write its transcripts, so a forged line could make a sibling look like the main session (M1, accepted for v1; only questions that opted in with `--main-may-answer`, only inside one session). The card, the Inbox title and the event say what the transcript says and nothing more. Details:
  - A foreground Bash command's stdout is also a `….output` file, so a `.output` stdout alone never means background: only a transcript whose launch result path equals it does (P1). Under Codex stdout is a pipe, under agy a pty.
  - The assistant line holding a Bash `tool_use` is stamped 0.9 to 1.5 s before the command starts; the background launch result at about its start, so it can land after `ask.open` (P2). The finder therefore keeps looking until `FIND_MS` (10 s), on each file event or every 500 ms, and an unmatched ask settles as `unknown` ("This session or one of its subagents"). A command matched to a `tool_use` id another open question holds is skipped; two unclaimed matches are `unknown`.
  - The output path is absolute and canonical (`/private/tmp/claude-501/<slug>/<session id>/tasks/<task id>.output`) but names a slug and session that can belong to another session, so the path never names the session, only the transcript that wrote the launch line (P7). Two subagents running the identical command in one second got distinct files (P8).
  - A subagent's commands are children of the main session's Claude process; a `claude -p` started inside a session that has no `sessions/<pid>.json` leaves the walk at the outer session (P9, kept).
  - A delegated job: a process on the walk whose executable is this binary and whose argv starts `notchling delegate codex|agy` makes the asker `codex` or `antigravity`; the delegating agent is found the same way and put in the label ("Codex job · delegated by «name»").
  - `ask.answer` from an agent finds the caller's own `notchling answer` command (up to `MAIN_FIND_MS`, 5 s) and needs it in the main transcript and in no subagent's.
  - The branch is read from the `ask` process's folder up to the first `.git` (a folder, or a file `gitdir:` for a worktree), its `HEAD` giving the name or the first 8 characters of a hash. No `git` process runs.
- **First answer wins, and marks.** `AskOps` keeps in memory the questions an answer or a dismiss has been taken for (`marks`, one lock, never held across I/O). Taking an answer from Chat, the notch, the Inbox's responder or the main session checks and marks there; then one `UPDATE … WHERE state='open'` persists it. A second caller gets `answered: false` with the state and the winner's `by`. A mark holds the state and `by` (the loser needs the winner's `by`) and stays for the row's life once its write landed; one whose write failed is dropped, so a daemon that stops between the mark and the write finds the question open again and never shows an answer nobody gave. The Inbox's responder takes the mark, adds the id to `pending` and queues the write in one step under the `pending` lock, and `close` sets closed under the same lock, so nothing is queued after the loop's last drain and the tick never sees a taken mark without its pending id. A store that fails both a write and the next read leaves that one Inbox item as it was; the next daemon start raises the open rows again (R1).
- **Delivery, gone, expired, dismissed.** States: `open`, `answered` (taken, not handed over), `delivered` (an `ask.wait` reply carried it), `dismissed`, `expired`, `gone`. `ask.wait` is served only to the asking process (pid and start time equal the row's); the same process asking again gets the same answer, so a reply lost on the way loses nothing. A 1 s tick (`ask_tick.rs`) ends an `open` blocking ask past its deadline as `expired` and an `open` or `answered` row with no waiter connected whose process has ended as `gone` (a row with no saved start time is alive while its pid or its parent still exists); a connected waiter is never checked, so a long wait isn't ended by a flicker, and a connect or disconnect alone publishes nothing. A session that stops takes its `ask` processes with it, and the card says "Stopped waiting". Dismissed: the next wait says so and the command exits 2. A closed row is deleted 24 hours after `closed_ms` by the hourly sweep, answer text with it (`ask.removed` is published); nothing open expires by age. `AskOps::load` (between bind and serving, after `InboxOps::load`) records `restored` for each live row and raises each open one again under a fresh id, dropping the withdrawn copy. Limits: question 2,000 characters, 2 to 6 choices of at most 120, an answer 10 KB, 20 open per session, 100 in all.
- **While `acting` is off.** `ask.open`, `ask.answer`, `ask.dismiss` and the Inbox's responder are refused; `ask.wait`, `ask.mine` and `ask.list` are served, so open questions keep waiting and an answer is taken when acting is on again.
- **The Inbox item.** One per open question, kind `question`, raised when the finder settles so its title names the agent; the question is in its detail cut to 400 characters (the privacy line is in [privacy.md](../policies/privacy.md)); actions `choice_1` to `choice_6`, Answer in Chat (`open`, Mac only) and Dismiss (`cancel`); the answer text is never in it. The phone answers through the Inbox only: a choice or Dismiss; a question without choices shows Open on Mac. See [inbox.md](inbox.md).
- **Workers (M6).** A Worker's `AskOps` runs on its own daemon; its Inbox item reaches the home and the Can Be Master members through the existing mirror, and a choice answered there is forwarded to the owner by `InboxOps::decide`, whose responder takes it as on the Mac. No new op, policy row or protocol field. Choices only: an inbox answer carries an action id, not text, so on a Worker `ask` without `--choice` is refused ("On a Worker, give choices (--choice): the answer comes from your Mac's Inbox."). Typed answers, a Chat card under a remote session and a Worker's skills are later.
- **Events.** `session.ask` carries counts only (`chars`, `choices`, `answer_chars`, `waited`, plus `then`, `asker`, `by`, `mode`), never a question or an answer (`LINT-LOG-NO-TEXT`); a test plants a token and looks everywhere.
- **Task 1's rulings, short** (probes in the ledger `docs/superpowers/plans/2026-11-16-ask.ledger.md`, fixtures real in shape with synthetic values). P1 a background command's stdout is the `….output` file its tool result names, but a foreground one is an `….output` file too. P2 the `tool_use` line is written before the command starts, the launch result at about its start. P3 and P6 a `claude -p` main thread or a `claude --bg` job's subagent that started a background command and ended its turn is woken by its exit; an interactive terminal main session is Task 22's live check. P4 Codex 0.166 `--write` can reach the socket (the delegate sets `network_access=true`) and blocks for minutes; read-only can't; agy over ACP runs commands as direct children, no sandbox, and a 60 s command ran to the end. P5 agy's permission request has `toolCall.kind "execute"` and `rawInput.CommandLine`; options `allow` and `deny`. P7 the path is canonical and names no session. P8 identical commands get distinct files. P9 `session_of` keeps today's behavior.
- **Ruled while building.** `--main-may-answer` on a question whose asker is `main` or `unknown` is kept on the row and ignored: only you answer it (B21). The delegated job's row keeps `tool_use_id` empty. A retried open (same `key`, same pid) returns the row's current state, whatever it is. A session's rows are re-keyed from the Claude Code `sessionId` to the job's key when a scan lists the session (`AskOps::sessions_changed`, called from `daemon.rs::scan`). `ask.mine` waits on one session-wide slot every publish wakes.

## Things that bit before

- Two answers at once (Chat and the Inbox) once both won because the mark was dropped after a successful write; a third caller then learned the loser's `by`. Marks stay taken until the row is deleted.
- `ask.mine` cached the session key before its wait loop, so a re-key mid-wait hid the question. Read it again on every pass.
- `Waiters::enter` bumped `connected` after dropping the slots lock and raced `release`; both now run under it.
- A zsh process substitution `=(…)`, a glob qualifier `*(e:…:)`, a brace or `~` in an agy command passed a blocklist. The allow is an allowlist over the raw text; do not turn it back into a blocklist.
- `--timeout 18446744073709551615` overflowed `seconds * 1000`; the deadline arithmetic saturates.
