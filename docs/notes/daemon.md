# The daemon and the local API

The local API's socket and tiers, the daemon's areas, the switches, and the `notchling` command line. Each op's shape is in [local-api-ops.md](../local-api-ops.md).

Part of the Rust app's notes, moved from `crates/AGENTS.md`; the index is in the root `AGENTS.md`. Keep it true: change the note with the code, and add what bites you under Things that bit before.

- **Local API.** `<data dir>/notchlingd.sock` (0600), one JSON object per line, `hello` first. The tier comes from the peer's executable (macOS: its audit token, read at accept, at `hello` and per app-tier request, against the exec race; Linux: `/proc/<pid>/exe`, best effort; Windows' pipe is a stub). Op and topic names are constants in `wire.rs` (`ops`, `topics`); each op has an `OpSpec`: `AGENT`, `APP`, or `APPROVAL` (fails closed with no app attached). Refusals, failures and app-tier calls are events (`api.refused`, `op.failed`, `op.called`, `api.unknown_peer`; `local-api/src/record.rs`) that the daemon's log bus writes to the Audit and the Activity store, except the successes of an `OpSpec::APP_QUIET` op: a read the app asks on a timer (Details Panel's `git.*` every 5 s; `activity.list`; the list and status polls in `quiet_ops::QUIET_READS`: `awake.state`, `bridge.status`, `bridge.devices`, `bridge.tunnel.status`, `accounts.list`, `lanes.list`, `providers.list`, `providers.usage`, `limits.status`, `limits.usage`). A poll that asks for a sync (`sync` or `refresh` true) is still logged (`Handler::loud`), and failures and refusals always are. Never quiet an op that acts, writes or touches the vault: a test classifies every op name in `wire.rs` as quiet or never quiet. Calls wait `CALL_TIMEOUT` (5 s) and check who serves the socket (`server_trusted`) first; 64 clients, 4 kept for the app.
- **Daemon.** `daemon.rs` locks, binds, then reads the session list (`engine::sessions::Monitor` on `platform::watch` batches under `jobs/` and `sessions/`, and every 5 s) for `sessions.list` and `sessions.changed`. `daemon_wiring.rs` builds every area per run: acting (`acting_ops.rs`, `control_ops.rs`, the terminal in `attach.rs`, the hook in `hook_ops.rs`), `codex_ops.rs`, `agy_ops.rs`, `bridge_ops.rs`, `pages_ops.rs`, `git_ops.rs` (`git.status`, `git.diff`: app tier, read only, no switch), `settings_ops.rs` (agents read every setting and change one by its class: `free` at once, `ask` through the Inbox, `never` not at all; decision 0020), `awake_loop.rs` (the power assertion that keeps the Mac awake while an app is attached: it reads `mode` and `keepDisplayOn` from the store, no switch; `awake_ops.rs` answers `awake.state`), `wake_loop.rs` (continue agents after sleep: behind `acting` and an attached app, over `engine::control::WakeResumer`), and `OpGroup`s (`op_group.rs`) for switches, accounts, install, providers, limits and cost, catalog and vault. Command-line modes: `clients.rs`, `pages_cli.rs`, `vault_cli.rs`, `delegate_cli.rs`, `hook.rs`, `service.rs`.
- **Switches.** Six, off at every daemon start whatever any file says, since an agent with a shell can write any file: `acting` (`settings.set_acting`: replies, answers, session control, Codex and Antigravity turns, the hook), the bridge (`bridge.set`: no port bound until on), and `accounts`, `vault`, `install`, `cluster` (`settings.set_switch`, `switches.rs`; `cluster`: no cluster port bound and nothing dialed until on). Only an app-tier call in that run turns one on (two exceptions, both for `cluster` and audited: `cluster.join` from an agent while no app is attached, so a headless node can join; and a headless member, as its home recorded it, rejoins its home at daemon start, `cluster_wiring.rs::rejoin_on_start`, decision 0007's note of 2026-11-14). An area checks its `SwitchFlag` before touching anything and answers `forbidden` with the off message. Under a fixture root every login effect is a fake or refused.

## The `notchling` binary

The `notchling` binary (`crates/notchlingd`) is the daemon (`notchling daemon`), its clients (`notchling status`, `notchling sessions [--json]`, `pages`, `page`, `secrets`, `secret`, `secret-request`, `delegate`, `delegate-models`, `cost report [--days N] [--plan api|subscription|auto]`; all but `secret` and `secret-request` take `--json` for machine-readable output) and `notchling service install|uninstall|print [--dir <folder>]`. In dev, run the daemon over a copy of a fixture, never over your real folders: `cp -R crates/app/fixtures/notch /tmp/nl-root`, then `NOTCHLING_DATA_ROOT=/tmp/nl-root` for the daemon and the clients alike (socket, lock and `audit.jsonl` land in `/tmp/nl-root/notchling`). `--socket <path>` moves the socket and puts its lock and the audit log beside it; over the real folders the daemon still locks `notchlingd.lock` in the data folder, one daemon per data folder. `NOTCHLING_APP_TIER_PATHS` (read once at daemon start, and only by a daemon run from a cargo target folder) lists executables that get the app tier; `ensure_daemon` never passes it on. `service install` only writes the file and prints the `launchctl`/`systemctl`/`schtasks` command; don't run that command, and in tests always pass `--dir`.

### The command line's contract

Every command but the hooks and the sidecar uses one table of exit codes (`contract.rs`): 0 ok, 1 failed, 2 bad request, 3 not running (no daemon, no answer, an untrusted socket, a daemon older than the command), 4 refused, 5 denied, 6 pending, 7 busy, 124 expired and, for `secret` only, 125 when Notchling stopped before running the command (the command's own code otherwise, 126 and 127 as `env` does). A non-zero exit without `--json` ends its stderr line with the code's name, "… (denied)". With `--json` stdout holds exactly one JSON value and nothing goes to stderr: a failure is `{"error": {exit, code, reason, message, op, switch, ask, retryAfterMs, request, never, phase}}`, with `message` fixed text (never a value). `secret --json` puts its one error line on stderr only when it exits 125.

`commands.rs` is the registry: one row per command (usage, summary, its ops with tier and whether they act, consent, exits, skill) and the lists `PLANNED`, `USER_ONLY` and `INTERNAL`, which with the rows hold every op exactly once (`commands_tests.rs`). `usage()`, `notchling help [--json]`, `notchling capabilities`, `Handler::agent_path` (the `data.reason` an agent gets for an op it may not call), `docs/agent-paths.md` and `tests/golden/agent-paths.json` all come from it; rewrite the two files with `NOTCHLING_UPDATE_GOLDEN=1 cargo test -p notchling-notchlingd commands`. A new op goes in a row, or in a list with its phase or reason: `op_kinds_tests.rs` and `GUARD-AGENT-PATH` fail otherwise. An old daemon that answers `unknown_op` to a newer command is exit 3 with reason `old_daemon`.

## Things that bit before

- Polling lstat'ed every file each second, a third of a core on a real `~/.claude` (53k files). macOS uses FSEvents (`platform::watch`; `examples/watch_cpu.rs` measures). Its debounce restarts on every change, so steady writes flush only through `max_latency`; Chat coalesces reloads (`chat::reload::ReloadGate`) and watches a folder reached twice through lane symlinks once.
- The daemon has no main run loop, so `NSWorkspace`'s running apps go stale there. `platform::apps::is_running` reads the process table; a login switch must never write while its app runs.
- Reading the session list before binding made the socket miss `ensure_daemon`'s 3 s wait, which killed the daemon, and the app read files for good. Now: locks, bind, read; `sessions.list` waits up to 4 s, under the client's 5 s.
- A reply can take over 5 s, and an error shown while it still arrived made the user send it twice: session calls wait 60 s. Accounts ops waiting on Keychain or network answer within 4.5 s and finish by event.
- One big Antigravity permission diff passed the 1 MiB line and failed `prompts.list` for every prompt. Cut payloads to fit: diffs to 400 lines or 128 KB, `agy.conversation` to the newest 512 KB with `truncated`.
- A `claude` exiting with output nobody read waits for its tty to drain, and SIGKILL can't end that: waiting with the pty master open hung `folder.trust`. Hang up and close the master first. A child that stops reading blocks writes forever, so `Terminal::write` gives up after 10 s.
- The daemon once read `acting` from `notchlingd-settings.json`, so a file write and a restart turned it on. No file turns a switch on in the daemon; that one saying on is audit-logged (`file_said_on_ignored`).
- Keep Mac Awake did nothing in the Rust app for as long as it ran: `platform::awake::AwakeGuard` was ported with its tests, the Settings sheet and the tray menu had the choice, and nothing called the guard (the tray's pick was kept in memory only). A port is not done when its adapter exists; name the process that calls it and test that path. Now `notchlingd/src/awake_loop.rs` calls it (only while an app is attached, as the Swift app did), and `notchlingd/src/wake_loop.rs` calls `PowerEvents` and `control::WakeResumer` (continue agents after sleep), which had no caller either. Still not ported and holding nothing: long `sd` runs (`RunWatcher`). No rule in `docs/rules.md` could have caught it: a `LINT-NO-CALLER` for a `pub` function in `platform` that nothing outside its crate calls is proposed.
