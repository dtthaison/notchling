# XXXX: Antigravity app (full), through its sidecar and hooks

## Context

[XXXX: A provider chooses how Notchling talks to it](XXXX-a-provider-chooses-how-notchling-talks-to-it.md) gave Antigravity three channels. `acp` (`agy acp`, the default) does everything but is the wrapping of `agy` that Google's FAQ calls "not supported under consumer plans". `app` and `remote` wrap nothing but only hand the user a draft: Notchling sends nothing, the phone can't reply, and nothing stops or approves.

Google documents two extension points of the Antigravity desktop app that need no wrapping: **sidecars** (a program the app runs, with `agentapi` on its PATH and the app's local address and token in its environment; https://antigravity.google/docs/sidecars) and **hooks** (commands the app runs before and after a tool call or a model call, configured in `~/.gemini/config/hooks.json`; https://antigravity.google/docs/hooks). Both are the app's own way for a third party to take part, so a channel built on them is not the thing the FAQ warns about.

Live-tested on Antigravity.app 2.32.2 (2026-11-18):

- A sidecar folder is picked up about a second after `config.json` has `sidecars."<id>" = {"enabled": true}`; the app adds `projectId` and `schemaVersion` itself.
- `agentapi new-conversation` prints the conversation id; with no project the app makes one named after the sidecar, with no workspace folder.
- `agentapi send-message <id> <text>` exits 0, and a wrong id also exits 0 and drops the message silently. Delivery shows as the `steps` row count growing in `~/.gemini/antigravity/conversations/<id>.db`. A message sent while the agent is busy waits until the turn ends. It shows as a collapsed "Message from System" row.
- `PreToolUse` takes `auto_approve`, `deny`, `ask` and others (30 s default timeout). `PreInvocation` takes `terminationBehavior: "terminate"`. No hook answers `ask_question`.

## Decision

- A fourth channel, `sidecar`, title "Antigravity app (full)", `Mode::Sends`. It replies, starts (with a model choice) and works from the phone. It has a **soft stop** and **approve**, two new abilities (`Ability::SoftStop`, `Ability::Approve`, with `Answer` for completeness). `agy acp` stays the default and is unchanged. `Abilities` gets the three fields; Claude's and Codex's declarations claim exactly what their tool's contract allows (the consistency test now fails a channel that claims an ability its tool marks Not applicable, and passes a channel that claims less). The channel's `gap_notes()` record what it can't do, so nobody learns it by failing:
  - **Answering questions:** no hook answers `ask_question`; the question is answered in the Antigravity app.
  - **Hard stop:** nothing cancels a running turn. Stop is soft: the daemon remembers it for that conversation for two minutes and the next `PreInvocation` returns `terminate`, so the turn ends at its next model call, not at once.
  - **A workspace folder for a new conversation:** `agentapi` has no per-conversation folder; the only documented one is the sidecar's static `workspace_uris`, which is global and restarts the sidecar when edited. A new conversation from Notchling has none, and the folder the user picked is checked and then unused. Notchling does not write Antigravity's project files to get around this.
- **The sidecar** is `notchling agy-sidecar`, a subcommand of the one `notchling` binary. Its `sidecar.json` is written into Notchling's own plugin folder, `~/.gemini/config/plugins/notchling/sidecars/sidecar/` (marked with `.notchling-plugin`; a folder that is not Notchling's is never touched), and runs the installed binary with that one argument, no shell. Plugin sidecars are named `<plugin>/<folder>`, so the id to enable is `notchling/sidecar`. The sidecar:
  - connects to the daemon over the local API as client `hook`, long-polls `agy.sidecar.take`, and runs `agentapi` with fixed arguments (no shell; conversation ids are checked as UUIDs; a model is a plain name, never flag-like; the prompt follows a `--`);
  - before a send, checks `conversations/<id>.db` exists, because `agentapi` would drop a message for a wrong id and still exit 0, and after it, waits for the step count to grow (a copy of the database is read, never the live file);
  - reports `delivered` (steps grew), `unconfirmed` (agentapi accepted it, the steps did not grow in 20 s) or `failed` (with words) through `agy.sidecar.report`. It never logs or stores `ANTIGRAVITY_LS_ADDRESS` or `ANTIGRAVITY_CSRF_TOKEN`;
  - when the daemon is gone, retries six times with a growing pause and then exits 0; Antigravity's `restart_policy: always` starts it again, and it reconnects when the daemon is back.
- **The daemon queue.** While the channel is `sidecar`, the Outbox's delivery to an `agy:` row, `agy.send` (reply or `draft_folder`) and so every Mac, phone and CLI reply and New Session queue a job instead of running `agy acp`. A job's id is the Outbox row's id and the queue is idempotent, so a retry of a delivered or unsure row never sends twice (a failed one runs again). **A message never vanishes:**
  - no sidecar has asked in 90 s: the row fails at once, "The Notchling sidecar isn't running in Antigravity", and stays in the Outbox;
  - nobody takes the job in 75 s: it is withdrawn and the row fails;
  - taken but not reported: the row is shown as unsure (`TryEnd::Cut`), not as sent;
  - `unconfirmed`: unsure; `failed`: the sidecar's words.
  Nothing is added to `agentconsole.v1`. The new ops (`agy.sidecar.take`, `.report`, `.status`, `.setup`, `agy.hook`; [local-api-ops.md](../local-api-ops.md)) are in the local API only. `take`, `report` and `agy.hook` are agent tier because the sidecar and the hooks are not the app; they answer only a client `hook` whose process tree has Antigravity above it. `session.reply`, `agy.send` and `agy.open` are not newly opened to agent tiers, `setup` is app tier and behind the `install` switch, and acting must be on to queue anything, as for every send.
- **Hooks** (`~/.gemini/config/hooks.json`). Notchling's entry is one top-level key, `notchling`, with a `PreToolUse` entry (a matcher for the tools that run commands, change files or read URLs, 120 s) and a `PreInvocation` entry (5 s). Both commands are `notchling agy-hook pre-tool|pre-invocation`; an entry is Notchling's only if its command is exactly that (the program named `notchling`, no shell characters), as Claude's hooks are matched on `--hook`. The file is edited as text so nothing else changes; a backup is kept first; other hooks stay; turning off removes only Notchling's entries; a malformed or foreign `notchling` key is left alone with the reason.
  - `PreToolUse` becomes an ordinary prompt (the same card in Chat, the notch and on the phone, answered by `session.permission`, with the session id `agy:<conversation>`) and answers `auto_approve` on Allow and `deny` on Deny. On no daemon, any error, no app to ask, or after 100 s, it prints nothing and exits 0 and Antigravity decides as it would. Always Allow is treated as Allow once: a hook has no rule store.
  - `PreInvocation` answers `terminate` once after a Stop for that conversation, and nothing otherwise.
  - The hooks do nothing unless the `sidecar` channel is chosen, so a hook left behind after the user chose another channel is harmless.
  - **Reversal of 0019 for this channel only.** [0019](0019-agent-instructions-per-tool.md) says "Notchling adds no hooks to Codex or Antigravity: the sessions it drives get their approvals over Codex's protocol and ACP." That stays true for `agy acp` and Codex. The sidecar channel has no ACP session, so for it, and only while it is chosen, Notchling adds the hooks above.
- **The "Message from System" display.** `agentapi send-message` shows in the app as a collapsed "Message from System" row, not as the user's own message. This is Antigravity's rendering of a sidecar's message and Notchling can't change it. Settings says so in one line under the row, and Chat shows the text as the user's own message, as it does for every channel, and does not hold a reply while the agent works: the app queues it until the turn ends.
- **Enabling is the user's act, with a confirmation.** Notchling never writes `config.json` silently. Picking the channel in Settings shows a row, "Turn on the Notchling sidecar in Antigravity", with its state (on, on but not started, off, partly on, app not installed, blocked) and a **Turn On** button. Turn On asks first ("This adds one line to Antigravity's config.json, keeps a backup of it, and puts Notchling's sidecar and hooks in place. Continue?"), then, behind the `install` switch and after checking everything first (plugin folder not foreign, `hooks.json` and `config.json` readable), writes: the plugin folder, Notchling's hook entries, and `sidecars."notchling/sidecar".enabled = true` in `config.json` and nothing else (an existing entry keeps its other fields; the file's other bytes stay). Each file is backed up first (`<name>.notchling-backup-<stamp>`, the last few kept). Turn Off removes the hook entries and the plugin folder and leaves `config.json` alone (the app drops the sidecar when its folder is gone). The row stays while anything of Notchling's is still in Antigravity, even when another channel is chosen. [goals.md](../goals.md) changes with this record: Notchling may edit its own entries in Antigravity's `hooks.json` and, after the user confirms, the one `config.json` key.
- **Workers (Linux nodes, m1).** The sidecar and hooks stay on the Mac. The Antigravity CLI's `--help` and the docs say nothing about the CLI hosting sidecars or `agentapi`, and the sidecar docs describe the desktop app only; the CLI binary contains the pieces (`agy agentapi`, a sidecar manager behind an undocumented flag) but Notchling does not build on what the documentation doesn't promise. So workers keep `agy acp`, as before, whatever the Mac chose: the channel is each machine's own setting (default `acp`), the Machines flow installs and sets up nothing for it, and Settings says "Worker machines keep the Antigravity CLI". A worker whose own setting is `sidecar` has no sidecar, and its sends fail with the "isn't running" words instead of vanishing.

## What is not done, and what could not be checked

- Not done: answering `ask_question`; a hard stop; a workspace folder for a new conversation; a phone Stop for `agy:` rows (the daemon's soft stop is reachable from the Mac's Stop only); the hooks for Codex or Claude Code.
- Not run against a live app (the maintainer tests these): the `--` before the prompt in `new-conversation`; whether the app finds a plugin sidecar with no `plugins` entry in `config.json` and enables it as `notchling/sidecar`; how `injectSteps` with `errorMessage` plus `terminate` looks in the Chat; how `auto_approve` interacts with the user's own approval policy (an eager policy asks nothing); and whether the CLI could host sidecars.
- The sidecar's caller check is a process-tree check (an ancestor whose executable path contains "antigravity"). It stops other agents and apps. It does not stop Antigravity's own agent, which can run `notchling agy-sidecar` as a tool: it could take a queued message or report a false result. It could already send the same message with `agentapi`, so nothing new is opened, but the check is not a boundary against it.

## Alternatives

- **Plugin hooks** (a `hooks.json` inside Notchling's plugin folder) would leave `~/.gemini/config/hooks.json` untouched, but hooks.json there is the documented place for a user's hooks and the one the app reads for every conversation. We use the user's file with Notchling's entries fenced and backed up, as for Claude.
- **Writing the sidecar id as `notchling`** (the first reading of the brief) does not match how plugin sidecars are named; `notchling/sidecar` does.
